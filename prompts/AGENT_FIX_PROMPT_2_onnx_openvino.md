## RoadScanner — ONNX / OpenVINO backend по-прежнему не работает

**Контекст**: это продолжение аудита из `AGENT_FIX_PROMPT_processing_map_cpu.md`.
Пользователь сообщает, что после предыдущих раундов правок (см. историю проекта —
`BACKEND_SELECTION_FIX.md`, `CPU_BACKEND_BUGS_FIX_REPORT.md`,
`BLOCK_M_Q_EXECUTION_REPORT.md`, `ВАЖНО_ПЕРЕЗАПУСК_ПОСЛЕ_ЭКСПОРТА.md`,
`БЫСТРЫЙ_СТАРТ_ONNX.md`) режимы `cpu_inference_backend = "onnx"` и `"openvino"`
**всё ещё не работают**.

**Важно — прочитай перед началом**: я проверил текущее реальное состояние
`configs/sign_models.py` в этой сессии (не архивный снепшот, а актуальный файл в
`/mnt/project/`). Все ранее задокументированные code-level фиксы (BUG-1: `__call__`
делегирует в `predict()`; `_predict_kwargs_with_cpu_pin`: принудительный
`device='cpu'`; `reload_all_models_if_device_changed()`: синхронизация
`ORT_DISABLE_CUDA` при каждом запуске обработки) **уже присутствуют в коде именно в
том виде, в каком они описаны как "исправлено" в истории проекта**. Это значит:
**дальнейшая правка этой же логики матчинга device/backend с высокой вероятностью
ничего не даст** — проблема, скорее всего, не (только) в коде `_LazyModel`, а в
одной или нескольких вещах ВНЕ этого файла, перечисленных ниже. Не трать бюджет
задачи на переписывание уже существующей и рабочей на вид логики, пока не пройдёшь
диагностику из раздела 1.

## 0. Как работать с этим промптом

Это НЕ обычный "найди баг и почини строку кода" промпт. Здесь основная работа —
диагностика реального окружения, а не правка алгоритмов. Порядок обязателен:
1. Сначала раздел 1 (диагностика) — с сохранением ПОЛНОГО вывода каждой команды.
2. Затем раздел 2 (структурные причины, не про код) — проверь каждую по своему
   окружению, не полагайся на предположения.
3. Затем раздел 3 (реальный, но менее очевидный код-баг с ONNX Runtime provider'ами).
4. Затем раздел 4 (то, что действительно стоит исправить в коде — "сделать fallback
   громким", чтобы больше никто — ни пользователь, ни следующий агент — не тратил
   часы на гадание "работает или нет").
5. В отчёте явно укажи, на каком именно шаге диагностики (1–4) обнаружилась
   РЕАЛЬНАЯ причина в твоём конкретном окружении — не пиши "исправлено", если не
   смог воспроизвести и подтвердить рабочий ONNX/OpenVINO инференс своими глазами
   (см. критерии приёмки, раздел 5).

## 1. Диагностика (обязательно первым шагом, до любых правок кода)

Прогони по порядку и СОХРАНИ вывод каждой команды (не пересказывай "успешно" —
приложи реальный текст):

### 1.1. Есть ли вообще исходные веса `.pt`?
```bash
find . -iname "*.pt" -exec ls -la {} \;
```
Если пусто или файлы отсутствуют — **это структурная причина, не код-баг**, см.
раздел 2.3. Никакой экспорт в ONNX/OpenVINO физически невозможен без исходных
`.pt`-весов. Остановись здесь и переходи к разделу 2.3, не пытайся чинить код.

### 1.2. Что реально в `requirements.txt` (или как ещё в проекте зафиксированы
зависимости — `pyproject.toml`, `environment.yml` и т.п. — используй то, что
реально есть)?
```bash
grep -in "onnx\|openvino\|torch" requirements.txt
pip show onnx onnxruntime onnxruntime-gpu openvino openvino-dev 2>&1
```
Зафиксируй буквально, что из этого установлено В ТОМ ЖЕ окружении, из которого
запускается `main.py` (не в каком-то другом venv, не там, где когда-то был запущен
`export_models_onnx.py`).

### 1.3. Полный, построчный экспорт (не сводка) для КАЖДОГО из 18 форматов/задач
```bash
python scripts/export_models_onnx.py --format onnx --force 2>&1 | tee /tmp/export_onnx_full.log
python scripts/export_models_onnx.py --format openvino --force 2>&1 | tee /tmp/export_openvino_full.log
grep -c "✅ Экспорт завершён" /tmp/export_onnx_full.log
grep -c "❌ Ошибка экспорта" /tmp/export_onnx_full.log
grep "❌ Ошибка экспорта" /tmp/export_onnx_full.log
grep -c "✅ Экспорт завершён" /tmp/export_openvino_full.log
grep -c "❌ Ошибка экспорта" /tmp/export_openvino_full.log
grep "❌ Ошибка экспорта" /tmp/export_openvino_full.log
```
**В истории проекта уже был случай (BUG-7, `CPU_BACKEND_BUGS_FIX_REPORT.md`), когда
итоговая сводка утверждала "✅ Все 18 моделей сконвертированы", а построчные логи
`export_log.txt`/`export_classify.txt` при этом показывали реальный провал части
моделей.** Не повторяй эту ошибку — процитируй в отчёте РЕАЛЬНЫЙ вывод
`grep "❌"`, а не количество из финальной строки "N/18 успешно".

### 1.4. Проверка, что файлы реально создались и не нулевого размера
```bash
find . -iname "*.onnx" -exec ls -la {} \;
find . -iname "*_openvino_model" -type d -exec sh -c 'echo {}; ls -la {}' \;
```
Особое внимание — `CNN_side/best.onnx` (главный детектор, самый тяжёлый шаг
пайплайна, см. `core/profiler.py`/`yolo_bbox_detection` в комментариях
`core/detector.py`) и `lane_guidance_models/arrow_detect.onnx`/`arrow_segment.onnx`
(detect/segment задачи технически сложнее для ONNX-экспорта, чем classify — если
что-то не экспортировалось, скорее всего именно они).

### 1.5. Реальный runtime-тест загрузки И инференса (не просто `_load()`, а полный
`predict()` на синтетическом кадре), для каждого backend отдельно
```python
# diagnostic_backend_check.py — временный скрипт, можно удалить после диагностики
import numpy as np
from configs.settings import get_app_settings

for backend in ("onnx", "openvino"):
    settings = get_app_settings()
    settings.use_cuda = False
    settings.cpu_inference_backend = backend

    from configs import sign_models
    sign_models.reload_all_models_if_device_changed()

    dummy = np.random.randint(0, 255, (32, 32, 3), dtype=np.uint8)
    try:
        result = sign_models.rube_modal(dummy, verbose=False)
        print(f"[{backend}] OK, реальный backend после _load(): "
              f"{sign_models.rube_modal._backend}, result={result[0].probs.top1}")
    except Exception as e:
        import traceback
        print(f"[{backend}] ОШИБКА: {e}")
        traceback.print_exc()
```
Это КЛЮЧЕВОЙ шаг: `sign_models.rube_modal._backend` после вызова — единственный
надёжный способ узнать, какой backend РЕАЛЬНО отработал (а не тот, что выбран в
настройках). Если `_backend == "torch"` при `cpu_inference_backend == "onnx"` —
значит где-то по цепочке произошёл тихий откат (см. `except Exception as e:
logger.warning(...); self._model = None` в `_LazyModel._load()`), и тебе нужно
достать текст этого `e` — временно понизь уровень логирования до DEBUG и запусти
ещё раз, либо оберни блок `try/except` в `_load()` временной точкой останова, чтобы
увидеть РЕАЛЬНОЕ исключение, а не догадываться.

## 2. Структурные причины (не про алгоритм — про окружение/поставку зависимостей)

Ниже — конкретные, проверяемые по `.gitignore`/`.gitattributes`/истории проекта
причины, которые с высокой вероятностью объясняют "не работает" ПОСЛЕ того, как
логика `_LazyModel` уже была почищена в предыдущих раундах. Проверь их все, даже
если раздел 1 у тебя прошёл гладко в твоём окружении — у пользователя окружение
может отличаться, и цель этого промпта — закрыть проблему для него, а не только для
твоей текущей сессии.

### 2.1. `openvino`/`openvino-dev`, скорее всего, НЕ входят в обычную установку

По истории проекта (`CPU_BACKEND_BUGS_FIX_REPORT.md`, раздел BUG-8): в
`requirements.txt` добавлены `onnx>=1.22.0` и `onnxruntime>=1.29.0` **без
комментирования** (значит `pip install -r requirements.txt` их поставит), а
`openvino`/`openvino-dev` явно оставлены **закомментированными** ("опционально").
Это асимметрия: ONNX-зависимости стоят "из коробки", OpenVINO — нет. Если это
по-прежнему так (проверь `requirements.txt` — см. раздел 1.2), то ЛЮБАЯ попытка
использовать `cpu_inference_backend = "openvino"` на свежей установке будет:
- либо падать на этапе экспорта (`export_models_onnx.py::main()` явно проверяет
  `import openvino` и корректно останавливается с понятной ошибкой — это ХОРОШО,
  но пользователь мог пропустить это сообщение в консоли);
- либо, если экспорт когда-то делался в ДРУГОМ окружении (например, у другого
  разработчика, который вручную поставил `openvino`), а `.xml`/`.bin`-файлы
  случайно попали в поставку — рантайм (`_LazyModel._load()`,
  `YOLO(ov_path, task=...)`) всё равно упадёт с `ModuleNotFoundError: No module
  named 'openvino'` в ТЕКУЩЕМ окружении, поймается в `except Exception as e:
  logger.warning(...)` и **молча** откатится на PyTorch — то есть OpenVINO будет
  выглядеть как "выбран в настройках", но фактически никогда не использоваться.

**Fix**: раскомментируй `openvino`/`openvino-dev` в `requirements.txt` (сделай их
обязательной, а не опциональной зависимостью — раз в UI есть выбор "OpenVINO" как
равноправная опция рядом с "ONNX"/"PyTorch", зависимость должна ставиться так же
безусловно, как `onnx`/`onnxruntime`; альтернатива — оставить опциональной, но тогда
Settings UI обязан явно и заметно предупреждать при выборе "OpenVINO" в комбобоксе,
если пакет не установлен, вместо позволения выбрать нерабочую опцию без единого
предупреждения — см. раздел 4.2). Выбери один из двух вариантов и реализуй его
целиком, не оставляй "наполовину".

### 2.2. `*.onnx` и `*_openvino_model/` — эфемерные, никогда не коммитятся артефакты

`.gitignore` (проверено — актуальное состояние на момент этого промпта):
```
# BLOCK M: Экспортированные модели (генерируемые артефакты)
*.onnx
*_openvino_model/
```
Это осознанное и правильное архитектурное решение (не класть сгенерированные
бинарники в git), но из него следует: **у КАЖДОГО, кто клонирует репозиторий или
работает в новой изолированной среде (включая ИИ-агента без доступа к ранее
экспортированным файлам), ONNX/OpenVINO backend не будет работать, пока кто-то
физически не запустит `scripts/export_models_onnx.py` в ЭТОМ конкретном окружении**.
Это не баг кода — но именно поэтому раздел 1.3–1.4 этого промпта обязателен: не
предполагай, что экспорт "уже когда-то был сделан" — предположение "раз в истории
проекта написано ✅, значит файлы есть" — ровно та ошибка, которая уже
задокументирована как BUG-7.

**Что сделать в коде** (единственное реальное действие здесь): сделать отсутствие
экспортированных файлов ЗАМЕТНЫМ пользователю ДО старта обработки, а не тихим
логом посреди работы — см. раздел 4.1.

### 2.3. `.pt`-веса — вне обычного дерева репозитория

`.gitattributes` помечает `*.pt filter=lfs diff=lfs merge=lfs -text` (Git LFS), а
`.gitignore` дополнительно **полностью исключает** директории с весами:
```
CNN_side
configs/small_models/
configs/lane_guidance_models/
```
Это означает, что даже с корректно настроенным Git LFS сами директории с `.pt`
файлами не отслеживаются как часть основного дерева репозитория — веса
поставляются каким-то ОТДЕЛЬНЫМ механизмом (архив, установщик, ручное копирование
и т.п., не описанным в предоставленных тебе файлах проекта). **Если в твоём рабочем
окружении этих директорий/файлов нет физически — раздел 1.1 это покажет, и дальше
чинить код бессмысленно: нужно получить веса от пользователя/из внешнего источника
поставки, а не пытаться исправить `_LazyModel`.** Явно напиши в итоговом отчёте, был
ли у тебя физический доступ к `.pt`-весам в твоём окружении — это критично для
интерпретации всех остальных твоих находок.

## 3. Менее очевидный, но реальный код-баг: `onnxruntime` vs `onnxruntime-gpu` и провал `reload_all_models_if_device_changed()`

Проверь и это, отдельно от разделов 1–2 — это уже касается именно логики, а не
поставки:

**Файл**: `processing/processing_controller.py`, `ProcessingController.start()`:
```python
try:
    from configs.sign_models import reload_all_models_if_device_changed
    reload_all_models_if_device_changed()
except Exception:
    pass
```
Широкий `except Exception: pass` полностью проглатывает любую ошибку внутри
`reload_all_models_if_device_changed()` — а эта функция, помимо сброса кэша
моделей, единственный код во всём приложении, который синхронизирует переменную
окружения `ORT_DISABLE_CUDA` при каждом старте обработки (см.
`sign_models.py::reload_all_models_if_device_changed`, комментарий "BLOCK M-FIX
(BUG-2)"). Если по любой причине эта функция бросает исключение до того, как
успевает дойти до строк `os.environ.pop/["ORT_DISABLE_CUDA"]`, — эта критичная для
CPU-режима синхронизация просто не произойдёт, и ты об этом не узнаешь: `except:
pass` не логирует вообще ничего.

**Fix**:
```python
try:
    from configs.sign_models import reload_all_models_if_device_changed
    reload_all_models_if_device_changed()
except Exception as e:
    logging.getLogger(__name__).error(
        f"[ProcessingController] reload_all_models_if_device_changed() упал: {e}. "
        f"ORT_DISABLE_CUDA мог не синхронизироваться с текущим backend!",
        exc_info=True,
    )
```
Не меняй поведение "не блокировать старт обработки, если это упало" — просто
перестань это молчать. После фикса прогони диагностику раздела 1.5 ещё раз и
посмотри, не начала ли эта ошибка вылезать в логах — если да, ты только что нашёл
реальную причину.

Дополнительно проверь пакет `onnxruntime`, установленный в окружении (раздел 1.2):
если стоит `onnxruntime-gpu` (а не обычный `onnxruntime`), провайдеры
`CUDAExecutionProvider`/`TensorRTExecutionProvider` физически присутствуют в сборке
и могут пытаться инициализироваться при создании `onnxruntime.InferenceSession`
внутри Ultralytics `AutoBackend`, даже если на машине физически нет рабочей
CUDA/cuDNN — это именно тот класс ошибки, который описан в
`BACKEND_SELECTION_FIX.md` ("Error when binding input... CUDA -> CPU"). Если это
твой случай — убедись, что `requirements.txt` фиксирует именно `onnxruntime`
(CPU-only пакет), а не `onnxruntime-gpu`, и если в окружении стоит
`onnxruntime-gpu` — явно предупреди об этом в отчёте (переустановка пакетов в
чужом продовом окружении — не твоя задача в рамках этого промпта, но диагноз дать
обязан).

## 4. Что действительно стоит исправить в коде: сделать fallback ГРОМКИМ

Независимо от того, что именно окажется первопричиной в конкретном окружении (веса
отсутствуют / зависимости не установлены / экспорт не запускался / реальный баг в
provider'ах) — есть один сквозной, гарантированно полезный фикс: **сейчас откат на
PyTorch происходит абсолютно бесшумно** для конечного пользователя. Он выбирает
"ONNX" в Settings, жмёт "Сохранить", запускает обработку — и получает рабочее
приложение (потому что откат на PyTorch надёжен), но БЕЗ единого намёка на экран,
что выбранный им backend не используется. Это именно то, что превращает "не даёт
ускорения / глючит непонятно как" в "не работает".

### 4.1. Явная проверка backend'а ДО старта обработки, с выводом в UI

**Файл**: `configs/sign_models.py` — добавить функцию:
```python
def verify_backend_active() -> dict[str, str]:
    """
    BLOCK FIX-4.1: принудительно грузит ВСЕ модели (если ещё не загружены) и
    возвращает {имя_модели: реальный_backend}. Вызывать один раз при старте
    обработки, чтобы явно предупредить пользователя, если запрошенный backend
    (ONNX/OpenVINO) фактически не используется хотя бы для одной модели —
    вместо тихого отката, о котором сейчас можно узнать только из roadscan.log.
    """
    all_models = {
        "model_side_detect": model_side_detect,
        "rube_modal": rube_modal,
        "model_lane_detect": model_lane_detect,
        "model_lane_segment": model_lane_segment,
        **{f"model_dict[{k}]": v for k, v in model_dict.items()},
        **{f"sub_models[{k}]": v for k, v in sub_models.items()},
    }
    result = {}
    for name, m in all_models.items():
        try:
            m._load()
            result[name] = m._backend or "unknown"
        except Exception as e:
            result[name] = f"ERROR: {e}"
    return result
```

**Файл**: `processing/processing_controller.py`, `ProcessingController.start()` —
сразу после `reload_all_models_if_device_changed()`:
```python
from configs.settings import get_app_settings
from configs.sign_models import verify_backend_active

settings = get_app_settings()
requested_backend = "torch" if settings.use_cuda else settings.cpu_inference_backend
if requested_backend != "torch":
    backend_status = verify_backend_active()
    mismatched = {k: v for k, v in backend_status.items() if v != requested_backend}
    if mismatched:
        msg = (
            f"Backend '{requested_backend}' запрошен в настройках, но реально "
            f"не используется для {len(mismatched)} моделей (откат на PyTorch "
            f"или ошибка): {mismatched}. Проверьте, что модели экспортированы "
            f"(scripts/export_models_onnx.py --format {requested_backend}) и что "
            f"установлены зависимости ({requested_backend})."
        )
        logging.getLogger(__name__).warning(msg)
        self.error.emit(msg)   # см. ниже — не обязательно error, можно завести
                                # отдельный сигнал warning, если error прерывает
                                # обработку, а этого делать не нужно (PyTorch
                                # fallback рабочий, просто медленнее)
```
Обрати внимание на комментарий в конце: `self.error` в `ProcessingController`
сейчас используется как "обработка не может продолжаться" (см. подключение в
`MainWindow._ensure_controller`: `self._controller.error.connect(lambda msg:
self.page_processing.log(msg, "error"))`) — здесь же откат на PyTorch НЕ является
фатальной ошибкой, обработка продолжится корректно, просто медленнее. Заведи для
этого отдельный `pyqtSignal(str)` (например, `backend_warning`) вместо переиспользования
`error`, подключи его в `MainWindow` к тому же `self.page_processing.log(msg,
"warn")`, чтобы пользователь ТОЧНО увидел это в консоли обработки, но приложение не
вело себя так, будто произошла ошибка.

### 4.2. Settings UI: предупреждение, если backend выбран, но не готов к использованию

**Файл**: `ui/widgets/settings_page.py` — по кнопке "Сохранить" (`_save()`), если
`self._cpu_backend_combo.currentIndex()` соответствует `"onnx"` или `"openvino"`,
запусти лёгкую неблокирующую проверку (в фоновом `QThread`, по аналогии с уже
существующим `ExportWorker` в этом же файле) вида "пакет `onnx`/`onnxruntime`
(или `openvino`) установлен? хотя бы один `.onnx`/`_openvino_model` файл физически
существует на диске?" — и если нет, покажи явный `QMessageBox.warning(...)` в духе:
"Вы выбрали backend '{X}', но он не готов к использованию: {причина}. Обработка
будет использовать PyTorch, пока вы не запустите экспорт моделей и/или не
установите зависимости." Не блокируй сохранение настроек — просто предупреди, это
чисто информационное сообщение.
