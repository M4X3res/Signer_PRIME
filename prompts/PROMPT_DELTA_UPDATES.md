# Промпт для ИИ-агента: дифференциальные обновления Signer PRIME

Скопируй всё содержимое этого файла как задание агенту (Claude Code и т.п.), работающему в этом репозитории.

---

## Контекст

Проект: RoadScanner (Signer PRIME). Система автообновлений уже реализована:
`version.py`, `version.json`, `updater.py`, `updater_main.py`, `ui/widgets/update_worker.py`,
`ui/widgets/update_dialog.py`, интеграция в `main.py`, сборка — `signer.spec` + `updater.spec` + `build.bat`,
установщик — `installer/SignerInstaller.iss`, выкладка релиза — `upload_release.ps1`.

**Проблема:** релиз публикуется как единый многотомный архив `Signer.7z.001/.002/.003...`
(весь `dist/Signer` целиком — torch, YOLO-модели, PyQt6, ffmpeg-биндинги, код, ресурсы).
`updater.py::check_for_update()` при любом новом релизе всегда предлагает скачать **все** тома архива
(`ARCHIVE_PREFIX = "Signer.7z."`), а `updater_main.py::extract_update()` просто распаковывает
архив поверх `install_dir` через `7z x ... -y`. Никакого сравнения "что реально изменилось" нет —
даже если поменялась одна python-строчка, пользователь качает 3-5 ГБ заново.

**Задача:** сделать так, чтобы при обновлении скачивались и заменялись **только изменившиеся файлы**,
а не весь `dist/Signer`. Полный архив нужно оставить только для **первичной установки** через
`SignerInstaller.iss` (там его трогать не нужно).

Заодно нужно закрыть несколько сопутствующих проблем надёжности апдейтера (см. раздел "Дополнительные фиксы").

---

## Общая архитектура решения

### 1. Манифест файлов (per-file hash manifest)

При каждой сборке релиза генерировать `manifest.json` — полный список файлов `dist/Signer`
с относительным путём, размером и SHA-256:

```json
{
  "version": "2.1.0",
  "generated_at": "2026-09-11T12:00:00Z",
  "files": {
    "Signer.exe": {"sha256": "...", "size": 12345678},
    "_internal/PyQt6/QtCore.pyd": {"sha256": "...", "size": 98765},
    "small_models/rude.pt": {"sha256": "...", "size": 22100646}
  }
}
```

Путь — всегда с `/` (posix-style), относительно корня `dist/Signer`.

### 2. Дельта между версиями (delta-package)

При публикации новой версии N агент/скрипт сборки должен:

1. Взять **манифест предыдущего опубликованного релиза** (скачать `manifest.json` с последнего
   релиза GitHub через API, если он есть — если нет, дельту не строить, публиковать только полный архив
   с пометкой "delta unavailable").
2. Сравнить с манифестом текущей сборки: получить три списка —
   `added` (новые файлы), `changed` (путь есть в обеих версиях, но sha256 отличается),
   `removed` (путь был в старом манифесте, отсутствует в новом).
3. Собрать `delta-from-<prevVersion>.zip`, содержащий **полное содержимое** всех файлов из
   `added` + `changed`, с сохранением относительных путей (обычный zip, не архив 7z — чтобы Updater.exe
   не тянул дополнительную зависимость от 7z для дельт; для больших сжимаемых бинарников можно
   использовать zip с `ZIP_DEFLATED`).
4. Сформировать `delta_manifest.json`:
   ```json
   {
     "from_version": "2.0.0",
     "to_version": "2.1.0",
     "changed_or_added": ["Signer.exe", "_internal/core/detector.py", ...],
     "removed": ["small_models/old_model.pt"],
     "archive_sha256": "<sha256 of delta-from-2.0.0.zip>",
     "archive_size": 12345678,
     "target_manifest_sha256": "<sha256 of manifest.json>"
   }
   ```
5. Опубликовать на GitHub Release как доп. ассеты (наравне с существующими `Signer.7z.*` и `checksum.sha256`):
   `manifest.json`, `delta-from-<prevVersion>.zip`, `delta_manifest.json`.

Если в будущем понадобится поддержать "прыжок через несколько версий" — просто не публиковать дельту
от версии, для которой нет манифеста; клиент в этом случае обязан упасть на full-путь (см. ниже).
Цепочки дельт (2.0→2.1→2.2 склеить в один прыжок 2.0→2.2) в этой итерации **не делать** — это
усложнение, дающее мало пользы для проекта с редкими релизами; полный fallback работает и покрывает
этот случай корректно.

### 3. Клиент: выбор delta vs full

`updater.py::check_for_update()`:
- Как и раньше, получает `data = response.json()` для `/releases/latest`.
- Дополнительно ищет в `assets` файлы `manifest.json`, `delta_manifest.json`, `delta-from-<APP_VERSION>.zip`.
- Если все три присутствуют **и** `delta_manifest.json.from_version == APP_VERSION` →
  собрать `UpdateInfo` с `is_delta=True`, `assets=[(delta_manifest.json), (delta-from-...zip)]`,
  `total_size_bytes` = размер дельта-архива.
- Иначе (нет дельты для текущей версии клиента, либо она рассчитана от другой версии) →
  прежнее поведение: `is_delta=False`, тянуть все `Signer.7z.*` + `checksum.sha256`.
- `UpdateInfo` (dataclass) — добавить поле `is_delta: bool = False` и `target_version_manifest_url: str = ""`
  (URL на `manifest.json` этого релиза, нужен для пост-проверки после apply).

### 4. Applier (Updater.exe): режимы full / delta

`updater_main.py`:
- Добавить аргумент `--mode {full,delta}` (по умолчанию `full` для обратной совместимости).
- В режиме `delta`:
  1. Распаковать `delta-from-<from>.zip` во временную поддиректорию `temp_dir/_delta_extracted`.
  2. Прочитать `delta_manifest.json`.
  3. **Перед перезаписью** каждого файла из `changed_or_added`, если он существует в `install_dir`,
     скопировать его в `install_dir/.update_backup/<relpath>` (создавая поддиректории) — это бэкап
     для отката (см. "Дополнительные фиксы", п. Rollback).
  4. Скопировать каждый файл из `_delta_extracted` в `install_dir` тем же относительным путём
     (создавая недостающие директории). Копирование делать через "написать во временный файл
     `<file>.new` рядом → `os.replace()`" — атомарная подмена, чтобы не оставить битый файл при обрыве.
  5. Удалить файлы из списка `removed` (если существуют).
  6. Опционально (см. verification) — сверить sha256 обновлённых файлов с `manifest.json` целевой версии.
  7. При успехе — удалить `.update_backup` и временную папку.
  8. При любой ошибке на шаге 3-6 — откатить уже скопированные файлы из `.update_backup` обратно,
     залогировать, показать `show_error_messagebox`, **не запускать** новый `Signer.exe`,
     запустить старый (или просто выйти с ошибкой и позволить пользователю запустить вручную —
     решить в пользу простоты: просто корректно откатить и попытаться запустить `signer_exe`
     как есть, т.к. после отката файлы должны быть в исходном рабочем состоянии).
- В режиме `full` — поведение как сейчас (`extract_update()` не трогать по сути, только обернуть
  ретраями, см. ниже).

`updater.py::launch_updater_and_exit()`:
- Определять режим на основе `UpdateInfo.is_delta` (или явного параметра),
  передавать `--mode delta` и путь к `--delta-manifest <path>` при дельта-обновлении.

### 5. UI

`ui/widgets/update_dialog.py`:
- В состоянии предложения показывать понятную метку в зависимости от `update_info.is_delta`:
  `"Быстрое обновление: {size}"` для дельты и `"Полное обновление: {size}"` для full —
  чтобы пользователь понимал разницу и не пугался маленького/большого размера.
- Остальная механика прогресса не меняется (она уже общая для списка ассетов).

`ui/widgets/update_worker.py`:
- Без структурных изменений, кроме передачи `is_delta` дальше в `launch_updater_and_exit` (через
  `main.py`, где сейчас формируются аргументы).

## Дополнительные фиксы (сделать в рамках той же задачи)

1. **Докачка (resume) при обрыве соединения.** В `updater.py::download_assets()` — при повторной
   попытке скачивания одного и того же файла проверять, есть ли уже частично скачанный `<file>.part`,
   и делать `requests.get(url, headers={"Range": f"bytes={existing_size}-"})`, дописывая в конец,
   если сервер поддерживает `Accept-Ranges` (GitHub CDN поддерживает). Финальный файл переименовывать
   из `<file>.part` в `<file>` только после полной успешной загрузки.
2. **Откат при сбое (rollback).** См. раздел 4 — обязательный бэкап изменяемых файлов перед
   перезаписью в `.update_backup/`, авто-восстановление при ошибке применения.
3. **Пост-проверка после apply.** После копирования файлов (delta или full) пересчитать sha256
   ключевых/всех изменённых файлов и сверить с `manifest.json` целевой версии; при несовпадении —
   считать обновление неудавшимся, откатить, залогировать конкретные файлы с расхождением.
4. **Атомарная запись файлов.** Все операции "заменить существующий файл" делать через
   `write tmp → os.replace(tmp, target)`, а не прямой `shutil.copy2` поверх (защита от неожиданного
   обрыва процесса/питания посреди записи).
5. **Ретраи для залоченных файлов.** DLL/exe могут на секунду оставаться залоченными антивирусом
   сразу после закрытия процесса — обернуть copy/replace/remove в retry (5 попыток, экспоненциальная
   задержка), а не падать с первой ошибки.
6. **Каналы обновлений (stable/beta).** Настройка в `AppSettings.update_channel`; при `beta` —
   запрашивать `GET /repos/{repo}/releases` (список) и брать самый свежий релиз с `prerelease=true`
   ИЛИ `draft=false`, сравнивая версии; при `stable` — как сейчас, `/releases/latest`
   (GitHub API уже не включает prerelease в `/latest`, так что это чисто аддитивное изменение).
7. **UI настроек обновлений.** См. `ui/widgets/settings_page.py` выше — тумблер автопроверки,
   выбор канала, кнопка ручной проверки, таймстамп последней проверки (хранить в
   `AppSettings.last_update_check_ts`, обновлять в `main.py` после каждой попытки проверки,
   независимо от результата).
8. **Ретраи сетевого запроса проверки обновления.** В `check_for_update()` — 2-3 попытки с паузой
   перед тем как молча вернуть `None` (сейчас — одна попытка).
9. **Явные лог-сообщения об источнике ошибки.** В `updater_main.py` логировать явно:
   "delta apply failed at file X: reason", а не только общий traceback — это должно облегчить
   диагностику через `updater.log`.
10. **Очистка мусора при старте.** `updater.cleanup_stale_update_temp()`, вызывается из `main.py`
    при каждом запуске: если `%LOCALAPPDATA%/Signer/UpdateTemp` существует и не была тронута
    (`mtime`) дольше суток — считать её мусором от прерванного обновления и удалить рекурсивно.
11. **Отчёт о размере в UI.** Использовать реальный `total_size_bytes` дельты, а не полного архива,
    в тексте диалога (уже покрыто разделом UI выше, продублировано для чек-листа).

## Формат аргументов Updater.exe (итог)

```
Updater.exe --pid <pid> --temp <tempDir> --install <installDir> --exe <signerExePath> --7z <7zExePath>
            --mode {full|delta} [--delta-manifest <path/to/delta_manifest.json>]
```
`--7z` обязателен всегда (нужен и для full-режима, и потенциально для распаковки zip тоже можно
использовать стандартную Python `zipfile`, чтобы **не требовать 7z для delta-режима вообще** —
это предпочтительнее: делает delta-путь независимым от 7z.exe/7z.dll и уменьшает точки отказа.
Реши в пользу `zipfile` из стандартной библиотеки для распаковки `delta-from-*.zip`.
