Задача: исправить сломанное соответствие "код знака → человекочитаемое название" 
в проекте Signer PRIME.

КОНТЕКСТ / БАГ:
Файл configs/sign_data.py содержит словарь NAMES_SIGNS_BY_TYPE: dict[str, str].
Его ключи (коды типов знаков, например "3.1", "3.9", "1.60") идут в одном порядке,
а значения (текстовые описания) — в АЛФАВИТНОМ порядке, а не в порядке,
соответствующем ключам. Похоже, словарь был сгенерирован так: список ключей
и список описаний собрали и отсортировали независимо друг от друга (описания —
по алфавиту), а затем сопоставили их просто по позиции (zip), а не по факту
принадлежности одному знаку. Из-за этого почти каждый код знака подписан
названием ДРУГОГО знака. Числовые коды (CODES_SIGNS) при этом корректны — 
сломаны только текстовые названия.

ЭТАЛОННЫЙ ИСТОЧНИК ПРАВДЫ:
configs/data/signs.json (и его копия signs.json в корне) — там для каждого 
знака явно указаны в одном Item: _Code (числовой код), _Key (код типа знака,
как "V3.1" — без буквы V это и есть ключ в codes_signs/type), _Description 
(человекочитаемое название), _Image (имя файла картинки). Эта структура 
не сортировалась отдельно и является правильной.

ЧТО СДЕЛАТЬ:
1. Написать (временный, можно потом удалить) скрипт, который:
   a. Загружает configs/data/signs.json.
   b. Проходит по всем MapLegend/*/Item и для каждого элемента строит пару
      (type_key, description), где type_key = _Key без ведущей буквы "V"/"L"/"P" 
      (посмотри на существующие соглашения в CODES_SIGNS — там ключи вида "3.1",
      "8.1.1" и т.п. без буквенного префикса).
   c. Сверяет получившиеся type_key с ключами CODES_SIGNS в configs/sign_data.py — 
      это гарантированно правильный набор кодов (его НЕ трогать).
   d. Строит корректный dict {type_key: description}.
2. Заменить содержимое NAMES_SIGNS_BY_TYPE в configs/sign_data.py на этот 
   корректный словарь, сохранив как можно больше существующих ключей 
   (в первую очередь тех, что реально используются, т.е. присутствуют 
   в CODES_SIGNS). Не удалять записи, для которых чёткого соответствия в 
   signs.json не нашлось — оставь их как есть, но выведи предупреждение/список 
   таких ключей в консоль, чтобы их можно было проверить руками.
3. Проверить также старый файл configs/sign_config.py (legacy, реэкспортирует 
   sign_data) — используется как compat-шим, отдельно ничего чинить в нём не надо,
   он просто импортирует из sign_data.py.
4. ВАЖНО: НЕ трогать CODES_SIGNS — там соответствие код→числовой ID верное.
5. После исправления вручную проверить хотя бы 15-20 случайных записей 
   NAMES_SIGNS_BY_TYPE, сравнив их с signs.json глазами (в отчёте показать 
   таблицу "было / стало / эталон из signs.json").
6. Прогнать grep по проекту на использование NAMES_SIGNS_BY_TYPE / 
   names_signs_by_type (ui/widgets/error_editor_page.py, server/map_server.py, 
   и т.д.) — убедиться, что нигде больше нет своей копии этого же сломанного 
   словаря, которую тоже нужно исправить таким же образом (проверь особенно 
   templates/map.html — там внутри <script> тоже зашит захардкоженный 
   JS-объект names_signs_by_type, его тоже нужно перегенерировать тем же способом).
7. Не менять коды знаков (CODES_SIGNS), картинки (sings/*.png) и логику 
   сопоставления знак→картинка — там всё верно, ломать нельзя.

Результат: NAMES_SIGNS_BY_TYPE (и его аналог в map.html) должны давать 
для каждого type ровно то описание, которое числится за этим _Key в 
configs/data/signs.json.
