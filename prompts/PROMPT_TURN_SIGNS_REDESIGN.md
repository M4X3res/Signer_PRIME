# Промпт для ИИ-агента: Переработка привязки знаков на поворотах/перекрёстках

**Дата создания:** 2026-08-24
**Приоритет:** Высокий (производительность + точность)
**Блок:** H — Геометрическая привязка знаков на перекрёстках (замена БЛОКА "Turn processing")

---

## 0. Контекст, который нужно знать заранее

Проект — RoadScanner (Signer PRIME): детекция дорожных знаков на видео с видеорегистратора,
привязка к GPS-треку (GPX), snap к дорогам OpenStreetMap через Overpass API, экспорт в GeoJSON.

Пайплайн уже содержит (см. `PERFORMANCE_OPTIMIZATION_REPORT.md`, `BLOCK_...` отчёты в корне репо):

- `core/osm_snap.py` — `OSMSnapper.snap_batch()` и `_get_ways_bbox()`: **один** запрос к Overpass
  на bounding box всего маршрута, дороги грузятся в память один раз.
- `core/final_handler.py` — `_process_straight_signs()` уже использует `snap_batch()` и работает
  быстро (batch, без сетевых вызовов на каждый знак).
- `core/final_handler.py` — `_process_turn_signs()` (или аналог для знаков в зоне поворотов/
  перекрёстков) — обрабатывается **отдельной веткой**, для которой batch-оптимизация Блока D
  не подтверждена/не применена. Это и есть узкое место по производительности.
- `core/turn.py` — класс `Turn`, отвечает за логику поворотов/перекрёстков. Внутри (по имеющимся
  описаниям) используется алгоритм + нейросетевой классификатор, определяющий, к какой из
  (обычно) 4 сторон перекрёстка относится знак.

**ВАЖНО:** прежде чем что-либо менять, агент обязан открыть и прочитать актуальный код
`core/turn.py`, `core/final_handler.py`, `core/osm_snap.py`, `core/sign_handler.py`,
`core/sign.py`, `configs/settings.py`, `configs/config.py` — описание выше основано на
исторической документации проекта и может не совпадать с текущим состоянием кода. Все шаги
ниже — это ТЗ на архитектуру, а не патч-инструкция "поменяй строку N".

## 1. Формулировка проблемы

### 1.1. Производительность
Обработка знаков в зоне поворотов/перекрёстков ощутимо медленнее обработки знаков на прямых
участках. Требуется найти корневую причину (скорее всего: сетевые вызовы Overpass на каждый
знак вместо batch, и/или инференс NN-классификатора на каждый знак) и устранить её.

### 1.2. Точность определения стороны
Сейчас "к какой из 4 сторон перекрёстка относится знак" определяется алгоритмом + нейросетью —
классификатор категорий. Это:
- требует обучающих данных и деградирует на нетиповых перекрёстках (T-образные, 5+ лучей,
  кольца, скошенные примыкания);
- по сути решает геометрическую задачу классификационными средствами, что неустойчиво и
  плохо интерпретируемо (нет "почему модель так решила").

---

## 2. Требуемое решение — геометрическая привязка через "подложку"

Заменить классификатор на **прямое геометрическое сопоставление** знака с уже загруженной
векторной сетью дорог (той самой "подложкой" — набором OSM ways, которые уже батчево грузятся
для всего маршрута в `OSMSnapper.snap_batch()` / `_get_ways_bbox()`).

Идея: не классифицировать знак в одну из 4 категорий, а вычислить **азимут (bearing) от машины
на знак** в момент кадра и **бросить луч** от GPS-позиции машины по этому азимуту через
подложку дорог. Первый пересечённый within-tolerance сегмент **и есть** нужная сторона/дорога —
задача решается геометрией, без обучаемой модели.

### 2.1. Расчёт азимута на знак (bearing to sign)

Для каждого наблюдения знака в кадре нужно:

1. **Угловое смещение знака от центра кадра** по горизонтали:
   `pixel_offset_x = bbox_center_x - frame_width / 2`
   `angle_offset = atan(pixel_offset_x / focal_px)` — либо через горизонтальный FOV камеры:
   `angle_offset = (pixel_offset_x / (frame_width / 2)) * (HFOV / 2)`
   (`HFOV` — горизонтальный угол обзора камеры/видеорегистратора, вынести в настройки, см. §4.3).
2. **Курс машины (heading) в момент кадра** — берётся из GPX-трека (уже используется для
   `gpx_azimuth` в текущем conf_placement пайплайне, см. `FIX_GPS_CONFIDENCE.md`).
3. **Итоговый азимут на знак** (мировые координаты, 0°=север, по часовой):
   `sign_bearing = (gpx_azimuth + angle_offset) mod 360`
   (знак смещения `angle_offset` зависит от того, слева или справа знак в кадре и от знака
   поворота машины — учесть при реализации и покрыть тестом на конкретных синтетических кадрах).

### 2.2. Пересечение луча с подложкой

Для каждого наблюдения:
1. Взять GPS-позицию машины в этот момент (уже есть в пайплайне).
2. Взять уже загруженный для маршрута набор OSM ways (переиспользовать `_get_ways_bbox()` —
   **не делать новый сетевой запрос**).
3. Построить луч из точки машины по `sign_bearing` длиной `MAX_RAY_DISTANCE_M` (настраиваемо,
   дефолт ~40м — знаки на перекрёстках стоят близко к границе проезжей части).
4. Найти пересечения луча с ways (сегмент-в-сегмент intersection, либо через `shapely`:
   `LineString` луча × `LineString` каждого way в пределах bbox).
5. Взять **ближайшее** пересечение — это и есть "сторона" (конкретный way/edge OSM).
6. Если пересечений нет в пределах `MAX_RAY_DISTANCE_M` — fallback на текущее поведение
   (nearest-way snap, как для прямых знаков) с понижением `conf_placement`.

### 2.3. Агрегация по нескольким наблюдениям трека

Знак трекается несколько кадров подряд (`TrackedSign`, см. `core/sign.py`). Для устойчивости:
- считать `sign_bearing` → пересечённый way для **каждого** наблюдения в треке знака;
- финальная сторона = **мода** (наиболее частый way_id) по всем наблюдениям, а не результат
  одного кадра;
- добавить метрику согласованности (`bearing_consistency` = доля наблюдений, попавших в
  победивший way) — использовать как компонент `conf_placement`, аналогично существующим
  `snap_score`/`azimuth_score` из `core/sign.py::calc_confidence()`.
- отбрасывать наблюдения, сделанные слишком далеко от перекрёстка (например, за
  `TURN_DETECTION_RADIUS_M` от ближайшего OSM-узла-перекрёстка) — это уже не относится к
  повороту и должно уходить в обычный прямой pipeline.

### 2.4. Fallback / крайние случаи

- Кольца (roundabout): считать выходящую дорогу по первому пересечению луча за пределами
  кольцевого way (way с тегом `junction=roundabout` исключать из целевых сегментов, но не из
  подложки — луч должен "проходить сквозь" кольцо до реальной дороги).
- Несколько пересечений на близком расстоянии друг от друга (скошенное примыкание): выбирать
  по минимальному углу между `sign_bearing` и направлением сегмента way в точке пересечения,
  а не только по дистанции.
- Отсутствие OSM-данных рядом (дорога не размечена) — тот же fallback, что и сейчас для
  прямых знаков без snap (сохранять как есть, с низким `conf_placement`, без краша).

### 2.5. Почему это одновременно решает и производительность

- Никакого отдельного сетевого запроса на знак/поворот — подложка уже в памяти (переиспользуем
  batch-механизм Блока D).
- Никакого NN-инференса на знак — чистая векторная геометрия (`shapely`), на порядки быстрее.
- Код для "прямых" и "поворотных" знаков можно **объединить в один путь**: разницы между ними
  с точки зрения этого алгоритма нет — luč-intersection работает одинаково хорошо и на прямом
  участке (луч почти совпадает с направлением движения и попадает в тот же way, где едет
  машина), и на перекрёстке (луч уходит в сторону и попадает в другой way). Это даёт шанс
  вообще устранить `_process_turn_signs()` как отдельную ветку кода.

## 3. Альтернативные варианты (если §2 не подойдёт по каким-то ограничениям)

Агент должен реализовать §2 как основной вариант, но при явных технических противопоказаниях
(например, азимут GPX слишком шумный на низкой скорости/в статике) — рассмотреть и явно
обосновать выбор одного из следующих вместо/в дополнение:

**B. Граф топологии перекрёстков.** Один раз на маршрут для каждого OSM-узла-перекрёстка в
bbox построить локальный граф "какие ways сходятся в этом узле и под каким азимутом от узла
уходят" (считается один раз из подложки, не требует сети/NN). Тогда для знака рядом с узлом
задача сводится не к лучу через всю сцену, а к сопоставлению `sign_bearing` с ближайшим по углу
ребром в графе этого конкретного узла — более устойчиво к шуму дистанции, чуть менее точно к
шуму азимута. Можно комбинировать с §2: пересечение луча ищем только среди ways, инцидентных
ближайшему узлу-перекрёстку, а не по всему bbox — это и быстрее, и надёжнее.

**C. Явное геопозиционирование знака (если нужна точка, а не только "сторона").** Если бизнес-
логике важна не только сторона, но и точная точка на карте — оценить расстояние до знака
(dead-reckoning по изменению bbox знака между кадрами / triangulation по нескольким
наблюдениям с разных точек трека) и спроецировать знак в абсолютные координаты, затем взять
nearest-way к этой точке (это уже есть в `OSMSnapper`). Технически сложнее §2, начинать с §2,
переходить к C только если §2 даст недостаточную точность на реальных перекрёстках.

Агент должен явно написать в итоговом отчёте, какой вариант выбран и почему (не молча
подменять §2 на B/C).

### Шаг 1 — Спроектировать модуль геометрической привязки

  - `aggregate_observations(hits: list[WayHit]) -> tuple[way_id, consistency_score]`
- Модуль не должен делать сетевых запросов — принимает уже загруженные ways как параметр.
- Покрыть unit-тестами на синтетических данных (искусственный перекрёсток "крест" с 4 ways
  под известными азимутами, знак с известным bearing → проверить, что выбирается правильный
  way; T-образный перекрёсток; кольцо).

### Шаг 2 — Интеграция в пайплайн
- В `core/final_handler.py` заменить/дополнить `_process_turn_signs()` так, чтобы для знаков
  рядом с перекрёстками (в радиусе `TURN_DETECTION_RADIUS_M` от узла-перекрёстка) side
  определялась через новый модуль вместо NN-классификатора.
- Оценить возможность полного слияния с `_process_straight_signs()` (см. §2.5) — если код

  случая одним проходом по подложке.
- `TrackedSign` (`core/sign.py`) должен по ходу трекинга накапливать сырые наблюдения
  (bbox_center_x, frame_width, gpx_azimuth, gps-позицию по кадру) в объёме, достаточном для
  §2.1–2.3, если сейчас не хранит.
- `conf_placement` в `calc_confidence()` — добавить компонент `bearing_consistency` из §2.3,
  сохранить обратную совместимость полей в GeoJSON (см. `BUGFIX_MAP_AND_CONFIDENCE.md`,
  `FIX_GPS_CONFIDENCE.md` — не ломать существующие поля `conf_cnn`/`conf_placement`/`conf_total`).

### Шаг 3 — Настройки
Добавить в `configs/settings.py` (`AppSettings`) новые поля с разумными дефолтами и
tooltip-описаниями (см. паттерн уже существующих настроек `dedup_radius_*`):
- `camera_hfov_deg: float` (горизонтальный FOV камеры/видеорегистратора, дефолт под GoPro
  Hero-подобные широкоугольные камеры — уточнить у пользователя реальную модель камеры и её
  реальный FOV, не гадать втихую; если неизвестно — оставить настраиваемым в UI с понятным

- `turn_detection_radius_m: float` (дефолт ~25 — радиус вокруг OSM-узла-перекрёстка, в котором

## 5. Критерии приёмки

- [ ] Профилирование до правок зафиксировано (Шаг 0), причина медленности подтверждена или
      опровергнута фактами, а не предположением.
- [ ] Определение стороны знака на перекрёстке не использует NN-классификатор "сторона 1..4"
      (или использование явно обосновано как fallback с указанием, когда он срабатывает).
- [ ] Определение стороны не делает сетевых запросов к Overpass на знак/перекрёсток — только
      переиспользует уже загруженную для маршрута подложку.
- [ ] Есть unit-тесты на синтетических перекрёстках (крест, T-образный, кольцо) — все проходят.
- [ ] Regression-тест на реальном тестовом видео с перекрёстками не даёт хуже результатов, чем
      было (по количеству знаков и — где можно вручную сверить — по стороне).
- [ ] Замер FPS/времени обработки поворотов "до/после" оформлен с числами, показывает
      улучшение (или зафиксировано и объяснено, почему улучшения не произошло).
- [ ] `conf_placement`/`conf_total` в GeoJSON остаются в диапазоне 0.000–1.000, формат полей не
      сломан для существующего UI (карта, редактор ошибок).
- [ ] Настройки `camera_hfov_deg`, `turn_ray_max_distance_m`, `turn_detection_radius_m` доступны
      в `AppSettings` и в UI Settings с tooltip.
- [ ] Приложение стартует и обрабатывает видео без крашей (ручная проверка по чеклисту из
      `STATUS.md`/предыдущих `CHECKLIST_*.md`).
- [ ] Создан отчёт `BLOCK_H_TURN_GEOMETRY_IMPLEMENTATION.md` с diff-описанием, числами,
      тестами (по аналогии с остальными `BLOCK_*` отчётами в репозитории).

  дороге, не про то, что за знак это такой.

## 7. Если что-то в этом промпте не соответствует реальному коду

Если после чтения `core/turn.py`/`core/final_handler.py` окажется, что текущая реализация
устроена иначе, чем описано в §0 (например, "алгоритм+нейросеть" — это что-то другое, не

отчёта** и скорректировать план по существу задачи (устранить узкое место в производительности
и заменить эвристику определения стороны на геометрическую), а не по букве этого документа.
