# Промпт для ИИ-агента: доработка RoadScanner (Signer PRIME) до многопоточной версии + фикс UI/UX

## 0. Как пользоваться этим документом

Это техническое задание для автономного coding-агента (Claude Code / аналог), работающего с репозиторием **RoadScanner (Signer PRIME)** — desktop-приложением на PyQt6 для распознавания дорожных знаков на видео, привязки их к GPS и экспорта в GeoJSON, со встроенной картой (Flask + Leaflet).

Задача разбита на 5 крупных блоков. Работай **по порядку**, не переходи к следующему блоку, не закрыв предыдущий, и после каждого блока прогоняй регрессионный чек-лист из раздела 8. Каждое изменение должно сопровождаться коротким объяснением *почему* — многие места в проекте уже "чинили" несколько раз, и часть фиксов **откатилась/потерялась**, поэтому нельзя слепо доверять `.md`-файлам в корне репозитория (`FIX_*.md`, `CHANGELOG_*.md`, `BUGFIX_*.md`, `AUDIT_REPORT.md`, `STATUS.md`, `WORK_SUMMARY.md`) — они описывают состояние, которого **сейчас в коде нет**. Всегда сверяйся с реальным кодом, а не с историей документации.

## 1. Контекст и стек

- **UI**: PyQt6 + PyQt6-WebEngine (карта встроена как `QWebEngineView`)
- **CV/ML**: ultralytics YOLO (несколько моделей: `model_side_detect`, `rube_modal`, `model_dict{...}`, `sub_models{...}`), Keras-классификатор, EasyOCR (только CPU, судя по логам `roadscan.log`)
- **GPS/Geo**: gpxpy, pyproj (EPSG:32635 ↔ EPSG:4326), geojson, OSM Overpass API (`core/osm_snap.py`)
- **Сервер карты**: Flask + Flask-SocketIO в отдельном `QThread` (`server/map_server.py`, `server/server_thread.py`)
- **Frontend карты**: чистый JS + Leaflet, один файл `templates/map.html`, без сборщика
- **Точка входа**: `main.py`, лог пишется в `roadscan.log`

Ключевые модули обработки:
- `processing/video_reader.py` — `VideoReaderThread(QThread)`, читает кадры из mp4, кладёт в `queue.Queue(maxsize=8)`
- `processing/detector_thread.py` — `DetectorThread(QThread)`, **единственный** поток: детекция → классификация → OCR → трекинг, полностью последовательно
- `processing/processing_controller.py` — связывает reader+detector, управляет start/stop
- `core/detector.py` — `Detector` класс, пайплайн YOLO→CNN→OCR на одном кадре
- `core/sign_handler.py` — `SignHandler`, трекинг знаков между кадрами (**stateful, порядок кадров критичен**)
- `core/final_handler.py` — `FinalHandler`, дедупликация + OSM snap (HTTP-запросы!) + сохранение GeoJSON
- `core/osm_snap.py` — `OSMSnapper`, блокирующие `requests.post()` к Overpass API с rate-limit (`time.sleep`) **на каждый знак**

По логам (`roadscan.log`) реальная производительность: **CUDA недоступна, CPU only, FPS 0.7–3.0**, при подключении EasyOCR FPS падает до **0.1–0.3**. Это подтверждает необходимость реальной многопоточности/многопроцессности.

## 3. БЛОК A — Многопоточная/многопроцессная обработка

### Цель
Увеличить пропускную способность детекции (сейчас 0.1–3 FPS на CPU) за счёт параллелизма, **не сломав** порядок кадров, от которого зависит трекинг в `SignHandler` (сопоставление знаков между кадрами использует `sign.pixel_vector_to(det)` и требует последовательности).

### 3.1 Архитектурное решение (обязательный минимум — Этап 1)
Реализуй **конвейерный параллелизм по стадиям** (safer, меньше риска сломать трекинг):

```
VideoReaderThread → frame_queue
        ↓
DetectStage (YOLO side-detect, потокобезопасно с ThreadPoolExecutor
             или отдельный процесс, т.к. CPU-bound)
        ↓ raw_boxes_queue (сохраняет порядок кадров!)
ClassifyStage (rube + fine classify, тоже CPU-bound)
        ↓ classified_queue
OCRStage (EasyOCR — САМАЯ МЕДЛЕННАЯ стадия, только для знаков
          из TYPE_SIGNS_WITH_TEXT/NAME_SIGNS_CITY — редкая, но блокирующая)
        ↓ result_queue (с сохранением исходного frame_number)
SignHandler.check_the_data_to_add() — остаётся ОДНОПОТОЧНЫМ и строго
        последовательным (это единственное требование трекинга)
```

Ключевое наблюдение из логов: OCR-инициализация (`easyocr Using CPU`) прямо коррелирует с падением FPS до 0.1–0.3 в `roadscan.log`. **Вынеси OCR в отдельный worker** (поток или процесс с своей очередью задач), чтобы кадры без текстовых знаков не ждали OCR вообще. Знаки с распознанным текстом можно "дописывать" в `TrackedSign` асинхронно (потребуется небольшой рефакторинг `DetectedSign`/`TrackedSign`, чтобы `text_on_sign` мог прийти позже основного кадра — например через отдельный callback/очередь по `sign_id`/`abs_frame_number`).

Обязательно сохрани **строгий порядок** входа кадров в `SignHandler` — используй `queue.PriorityQueue` или буфер переупорядочивания по `frame_number`, если стадии работают параллельно с непредсказуемой задержкой.

### 3.2 Этап 2 (опционально, если Этап 1 не даёт нужного прироста) — пул процессов для сырой детекции
Реализуй `processing/detector_process_pool.py` (модуль сейчас отсутствует, но на него ссылается `test_import.py`):
- `ProcessPoolExecutor` / `multiprocessing.Pool` с N воркерами (N = `os.cpu_count() - 1`, настраиваемо из UI, см. блок C).
- Каждый процесс лениво инициализирует **свою** копию моделей — используй существующий паттерн `_LazyModel`/`_LazyKeras` из `configs/sign_models.py`, он уже per-process safe (модели не шарятся между процессами через pickle, а грузятся заново — так и должно быть).
- На вход воркера — сырой кадр (`np.ndarray`) + `frame_number`; на выход — список `RawDetection`/`box` + `frame_number`.
- На стороне `DetectorThread`/контроллера — буфер переупорядочивания, который отдаёт результаты в `SignHandler` строго по возрастанию `frame_number`, даже если процессы вернули их не по порядку.
- Не отправляй в пул сам `Detector` целиком (он не picklable из-за YOLO-моделей) — отправляй только функцию, которая лениво инициализирует модели внутри процесса при первом вызове (top-level функция модуля, не метод класса с self, привязанным к несериализуемым объектам).
- Добавь `configs/config.py::PROCESSING_MODE` (например, `"single_thread" | "pipeline" | "process_pool"`) и прокинь выбор в UI (Settings, блок C) — оставь `single_thread` рабочим fallback-режимом на случай проблем с процессами на Windows (учти существующие `KMP_DUPLICATE_LIB_OK`/`OMP_NUM_THREADS` воркэраунды в `main.py` — они актуальны и для дочерних процессов, `main.py` уже частично это учитывает в ветке `current_process().name != 'MainProcess'`, расширь при необходимости).
- Почини/актуализируй `test_import.py`, чтобы он реально проверял новый модуль, а не падал на несуществующем импорте.

### 3.3 Предзагрузка EasyOCR
Сейчас EasyOCR грузится лениво при первом вызове `_get_ocr()` внутри `core/detector.py` — первый текстовый знак в потоке вызывает многосекундную загрузку моделей **прямо во время обработки**, роняя FPS до нуля на этот момент (видно в логах). Перенеси прогрев EasyOCR в начало `DetectorThread.run()` (до основного цикла `_process_loop()`), с логом прогресса ("Загрузка OCR-модели…"), чтобы задержка происходила один раз при старте, а не непредсказуемо посреди обработки.

### 3.4 Предзагрузка/буферизация следующего видео
`VideoReaderThread._read_all_videos()` переключается на следующий mp4 последовательно — добавь prefetch (открывать `cv2.VideoCapture` следующего файла в фоне, пока читается текущий), чтобы убрать видимую паузу при переключении видео (это тоже влияет на общий "фриз" при длинных сессиях, судя по скачкам FPS в логах на границах видео).

### 3.5 Что нельзя ломать
- Итоговый порядок и формат `TrackedSign`, попадающих в `SignHandler.result_signs` — не должен меняться относительно однопоточной версии (то есть многопоточность — это ускорение, а не смена бизнес-логики).
- Формат GeoJSON на выходе (`core/final_handler.py::_build_feature`) должен остаться идентичным по набору полей.
- UI должен видеть тот же набор сигналов от `ProcessingController` (`frame_ready`, `progress`, `stats`, `video_switched`, `sign_found`, `finished`, `error`) — если добавляешь новые (например, `ocr_lag`, `pool_status`), делай это аддитивно, не удаляя старые.

### 4.3 Завершение обработки / сохранение GeoJSON — САМОЕ ВАЖНОЕ
Это главный источник "зависания на завершении обработки", подтверждённый в п. 2.1.

Реализуй `SaveThread(QThread)` (например, в `ui/main_window.py` или отдельном `processing/save_thread.py`):
```python
class SaveThread(QThread):
    finished_ok = pyqtSignal(int)   # количество сохранённых знаков
    progress    = pyqtSignal(int, int)  # текущий индекс, всего (для OSM snap с сотнями запросов)
    error       = pyqtSignal(str)

    def __init__(self, signs, turns, parent=None):
        super().__init__(parent)
        self.signs = signs
        self.turns = turns

    def run(self):
        try:
            handler = FinalHandler()
            # прокинь progress-callback в FinalHandler.save_result,
            # чтобы UI видел прогресс OSM snap по знакам, а не тишину
            handler.save_result(self.signs, self.turns, progress_cb=self.progress.emit)
            self.finished_ok.emit(len(self.signs))
        except Exception as e:
            self.error.emit(str(e))
```
- `MainWindow._on_finish_requested()` должен запускать `SaveThread`, **не блокируя UI**, отключать кнопку "Завершить" (см. 4.4), показывать прогресс-бар/спиннер с текстом "Сохранение результатов… (привязка к дорогам через OSM)" и обновлять его по сигналу `progress`.
- В `core/final_handler.py::save_result()` добавь опциональный параметр `progress_cb: Optional[Callable[[int,int],None]] = None` и вызывай его в цикле `_process_straight_signs`/`_process_turn_signs` (по количеству обработанных знаков) — учитывая, что именно OSM snap (`_snap_sign_coords`) — самая долгая часть per-знак.
- Верни/реализуй таймаут в `_deduplicate()` (как было описано в `FIX_SAVING_HANG.md`, но фактически отсутствует) — `TIMEOUT_SECONDS = 60`, с логом предупреждения и добавлением оставшихся элементов без дедупликации, если время вышло.
- Рассмотри также **опциональное** кэширование/батчинг OSM Overpass-запросов: если несколько знаков близко друг к другу (тот же `GRID_CELL_M`), не делать отдельный HTTP-запрос на каждый — `OSMSnapper._get_ways` уже кэширует по ячейке `(round(lat,3), round(lon,3))`, но проверь, что кэш реально работает эффективно при сохранении (сейчас `OSMSnapper` создаётся как синглтон через `get_snapper()` — убедись, что `FinalHandler` использует именно этот синглтон, а не создаёт новый `OSMSnapper()` при каждом вызове `snap_sign()`; если создаёт новый — кэш бесполезен между вызовами в рамках одного сохранения. Проверь `core/final_handler.py::_snap_sign_coords` — там `from core.osm_snap import snap_sign` (использует модульный синглтон `get_snapper()`) — это ок, но убедись, что это сохранится после рефакторинга).

### 4.4 Защита кнопки "Завершить" от повторного клика
Реализуй в `ui/widgets/processing_page.py`:
- Флаг `self._finish_clicked`, при первом клике — `setEnabled(False)` на `btn_finish` и `btn_pause`, смена текста на `"⏳  Завершение…"`.
- Сброс флага и текста в `set_active(False)` и при старте новой обработки.
- Дополнительная защита на уровне `MainWindow` (`_finish_requested_called` флаг), чтобы даже если сигнал придёт дважды — обработка `_save_results`/`SaveThread` не запускалась повторно.

### 4.5 Graceful shutdown (закрытие приложения)
- Добавь `MainWindow.closeEvent(self, event)`: останавливает `ProcessingController` (если запущен), вызывает `self.page_map.stop_server()`, дожидается корректного завершения `ServerThread` с разумным таймаутом (например `QThread.wait(3000)`), логирует всё через `logging`, затем `event.accept()`.
- Добавь `MapPage.stop_server(self)`: если `self._server_thread` существует и запущен — сигнализируй Flask-SocketIO серверу остановиться (например, через `socketio.stop()` вызванный из нужного контекста, либо через daemon-поток + `terminate`/graceful HTTP shutdown endpoint) и дождись завершения потока.
- Учти, что `ServerThread` сейчас daemon (`self.daemon = True` — надо ПРОВЕРИТЬ, что это выставлено, не как в старом баге `setDaemon()`), поэтому по-хорошему приложение и так не зависает при выходе, но корректное закрытие сокетов/HTTP-соединений всё равно нужно, чтобы браузерные вкладки (если открыты через "В браузере") не оставались с мёртвым сокетом без объяснения.

### 4.6 Общее правило для всего блока B
Любой вызов, который может занять >100мс (диск, сеть, парсинг больших файлов, тяжёлые вычисления) **не должен выполняться в слоте, вызванном напрямую из UI-сигнала** на главном потоке. Используй `QThread`/`QRunnable`+`QThreadPool`/`concurrent.futures` с обратной связью через `pyqtSignal`. Добавь везде, где это уместно, лёгкие индикаторы состояния (текст "…", спиннер, disabled-кнопки) — тишина во время долгой операции воспринимается пользователем как зависание, даже если технически поток жив.

## 7. Общие технические требования и ограничения (для всех блоков)

1. **Логирование**: используй `logging`, не `print()`. В проекте уже настроен `logging.basicConfig` в `main.py` с записью в `roadscan.log` — придерживайся этого, добавляй `logger = logging.getLogger(__name__)` в новые модули.
2. **Не ломай существующий REST API** карты (`/api/track`, `/api/signs`, `/api/sign/<id>` GET/PATCH/DELETE, `/api/jump`, `/api/sign_types`, `/api/img/...`, `/api/geojson_export`) — можно расширять ответы новыми полями, но не удалять/переименовывать существующие ключи без обратной совместимости на фронте.
3. **Координатные системы**: везде, где работаешь с координатами, сохраняй существующий паттерн EPSG:32635 (метры, для расчётов) ↔ EPSG:4326 (WGS84, для карты/GPX) через `core/converter.py::Converter`.
4. **Windows-специфичные воркэраунды** в `main.py` (`KMP_DUPLICATE_LIB_OK`, `OMP_NUM_THREADS=1`, `QT_OPENGL=software` и т.д.) — не удаляй без явной проверки, что краши (`0xC0000409` и т.п., см. `BUGFIX_GEOJSON_CRASH.md`, `CRASH_FIX_GEOJSON_BUTTON.md`) не возвращаются; если для многопроцессности (блок A) нужно скорректировать переменные окружения для дочерних процессов — делай это аккуратно и задокументируй.
5. **Обратная совместимость GeoJSON**: не меняй существующие ключи в `properties` (`type`, `length`, `side`, `azimuth`, `time`, `name_video`, `code`, `id`, `SEM250`, `MVALUE` и т.д.) без явной миграции/поддержки старого формата при чтении.
6. Пиши код так, чтобы **однопоточный режим оставался рабочим fallback'ом** (`processing_mode = "single_thread"`) — это критично для отладки и для систем, где multiprocessing проблематичен (антивирусы, ограничения окружения).
7. Обновляй `requirements.txt`, если добавляешь новые зависимости (например, `python-socketio` client-side уже используется, `Pillow` для JPEG-сжатия кадров уже в зависимостях).

## 9. Рекомендуемый порядок работы

1. Блок 2 (сверка регрессий) — быстро, даёт полную картину реального состояния кода.

4. Блок A, этап 1 (pipeline-параллелизм + вынос OCR) — среднего риска, тестируй на коротком видео перед длинным.
5. Блок D (карта) — можно делать параллельно с блоком A, так как файлы почти не пересекаются (кроме `emit_processing_finished`, которая зависит от блока B/4.3).
6. Блок A, этап 2 (process pool) — только если после этапа 1 производительности всё ещё недостаточно; наибольший риск, делай последним и за отдельным флагом (`processing_mode = "process_pool"`), не удаляя pipeline-режим.
7. Финальный сквозной регрессионный прогон по чеклисту раздела 8 на реальном тестовом видео целиком (Dashboard → обработка → завершение → карта → редактор ошибок → закрытие приложения).

## 10. Как тестировать вручную (сценарий)

1. Запустить `main.py`, выбрать папку с несколькими короткими mp4, GPX-трек, путь для GeoJSON.
2. Нажать "Начать обработку", наблюдать, что UI не подвисает, FPS в счётчиках растёт по сравнению с логами до изменений.
3. Открыть карту во время обработки, включить "Live", убедиться, что маркер движется.
4. Изменить настройки (например, `conf_cnn`) в Settings, сохранить, перезапустить приложение, убедиться, что значение восстановилось.
5. Нажать "Завершить" — убедиться, что кнопка сразу блокируется, UI отзывчив, по завершении карта сама обновляется с новыми знаками и уведомлением.
6. Открыть редактор ошибок, отредактировать/удалить знак, убедиться, что карта отражает изменения через SocketIO без перезагрузки страницы.
7. Закрыть приложение — убедиться, что закрытие происходит быстро и без зависших процессов в диспетчере задач.
