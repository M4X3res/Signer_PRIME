## БЛОК I — Дедупликация знаков (устранение "знак у дороги + призрак у центра")

### Проблема (контекст для агента)

Текущий пайплайн в `core/final_handler.py`:

```
_group_by_position()  →  _merge_duplicate_signs() (мерж ДО OSM-snap)  →  batch OSM snap  →  coefficient=2,3,4... растёт внутри группы
```

Дефекты:

1. `_are_duplicates()` мержит знаки **до** привязки к дороге, на сырых GPS-координатах (`car_x[-1]`, `car_y[-1]`). Если расстояние между дублями чуть больше `duplicate_merge_distance_m` (шум GPS), они не мержатся.
2. `_group_by_position()` группирует по ключу `f"{sign.car_x[-1]:.0f}_{sign.is_left}"` — **точное совпадение `is_left` обязательно**. Если сторона у двух наблюдений одного физического знака определилась по-разному, они попадают в разные группы и получают смещение в **противоположных направлениях** (см. `CoordinateCalculation.calculate_result_line`, где `is_left` определяет знак `dy`/`dx`).
3. Внутри одной группы `coefficient` растёт последовательно (2, 3, 4...) по порядку появления в списке — недомерженный дубль получает следующий по счёту coefficient и "размазывается" вдоль дороги вместо наложения на оригинал.
4. `SignHandler._set_side()` определяет `is_left` по пиксельному движению bbox (`pixel_x[0] - pixel_x[-1]` либо однокадровая XOR-эвристика при `observation_count == 1`) — ненадёжно, не привязано к геометрии дороги.
5. Финальный `_deduplicate()` (grid-дедуп по готовым `Feature`) тоже требует совпадения `side` в ключе ячейки — те же дубли, не пойманные раньше, не ловятся и здесь.

### Шаг I.1 — Геометрическое определение `is_left` через OSM-snap

**Файл:** `core/osm_snap.py`, `core/final_handler.py`, `core/sign.py`

1. В `SnapResult` (`core/osm_snap.py`) добавить поле `side_relative_to_way: Optional[bool] = None` (True = слева от направления way).
2. В `OSMSnapper._find_closest_segment()` — после нахождения ближайшего сегмента `p1→p2`, вычислить знак векторного произведения `(p2 - p1) × (point - p1)` в локальных метрах (переиспользовать существующий перевод в метры из `_project_point_to_segment`). Положительный знак = точка слева от направления движения поway, отрицательный = справа. Вернуть это как часть кортежа результата.
3. Прокинуть `side_relative_to_way` в `SnapResult`, `snap()`, `snap_batch()`.
4. В `FinalHandler._sign_to_feature_with_snap()` — **после** успешного snap пересчитать `sign.is_left` на основе `snap_result.side_relative_to_way` (с поправкой на направление движения машины: если машина едет "против" направления way, инвертировать). Старое значение `is_left` (из пиксельной эвристики) использовать только как fallback, если snap не удался (`snap_result.snapped == False`).
5. Добавить unit-тест: синтетический way (прямая линия север→юг), знак заведомо справа/слева от него по числовым координатам → проверить, что `side_relative_to_way` даёт ожидаемый результат в обоих направлениях движения.

### Шаг I.2 — Второй проход мержа дублей ПОСЛЕ snap

**Файл:** `core/final_handler.py`

1. Текущий `_merge_duplicate_signs()` вызывается один раз внутри `_group_by_position()`, до snap. Оставить его как первый (грубый) проход.
2. Добавить новый метод `_merge_duplicates_post_snap(self, signs: list[TrackedSign], snap_results: list, settings) -> tuple[list[TrackedSign], list]` — вызывается **после** `_batch_snap_signs()`, но **до** построения финальных `Feature` (`_sign_to_feature_with_snap` в цикле).
3. Критерий дубля во втором проходе:
   - тот же `best_cnn` (тип знака);
   - тот же `way_id` из `snap_result` (если snap успешен у обоих);
   - `abs(snap_result_a.distance_m - snap_result_b.distance_m) < 3.0` м (похожее удаление от дороги);
   - разница пост-snap азимутов `< settings.duplicate_azimuth_diff_deg`.
   - **`is_left` НЕ участвует** в этом сравнении (он уже пересчитан геометрически в Шаге I.1, но намеренно не используется как жёсткий фильтр — чтобы ловить случаи, где даже геометрический расчёт на границе).
4. При объединении — оставлять знак с большим `observation_count`, суммарно накапливая `abs_frame_numbers`/`text_results` через существующий `TrackedSign.merge()`/`_merge_signs()`.
5. Вернуть обновлённый список знаков + соответствующий обновлённый список `snap_results` (важно сохранить синхронизацию по индексам, так как `_sign_to_feature_with_snap` полагается на `sign_to_snap = {id(sign): result}`).
6. Обновить `_process_straight_signs()`, чтобы вызывать новый метод после `_batch_snap_signs()`.

### Шаг I.3 — Сортировка знаков внутри группы по cross-track расстоянию

**Файл:** `core/final_handler.py`

1. В `_process_straight_signs()`, перед циклом `for sign in items: coefficient += 1` — сортировать `items` по `snap_result.distance_m` (через `sign_to_snap`), а не оставлять в порядке появления в исходном списке. Знаки ближе к дороге получают меньший `coefficient` (=2), дальше — больший.
2. Если у знака snap не удался (`distance_m` недоступен) — ставить его в конец сортировки (наименее приоритетный порядок).
3. Тест: 3 синтетических `TrackedSign` с одинаковым `car_x`/`is_left`, но разными `snap_result.distance_m` (5м, 12м, 20м) → проверить, что итоговый порядок coefficient соответствует возрастанию расстояния.

### Шаг I.4 — Ослабление ключа группировки

**Файл:** `core/final_handler.py::_group_by_position`

1. Изменить ключ группировки с `f"{sign.car_x[-1]:.0f}_{sign.is_left}"` на группировку **только по позиции** (округление `car_x`/`car_y` до ближайших ~3-5 метров, а не только `car_x` до целого) — сторону использовать только для итогового атрибута результата, не для решения "объединять или нет" на этом этапе (так как Шаг I.2 уже корректно мержит дубли независимо от side).
2. Убедиться, что после этого изменения `coefficient`-логика (Шаг I.3) не создаёт слишком большие офсеты для знаков, которые физически на противоположных сторонах широкой дороги — сохранить существующий `_calc_max_coefficient()` (ограничение по ширине дороги), он уже должен сдерживать это; при необходимости дополнительно проверить, что офсет не позволяет знаку "перепрыгнуть" на другую сторону дороги (т.е. `effective_coefficient` для группы с разными `is_left` внутри — разделять на подгруппы по side ПОСЛЕ мержа, чтобы не создавать линию, начинающуюся на одной стороне и заканчивающуюся на другой).

### Шаг I.5 — Регрессионный тест дедупликации

**Файл:** `tests/test_deduplication.py` (создать)

Сценарии:
1. Два `TrackedSign` одного типа, координаты различаются на 6м (за порогом `duplicate_merge_distance_m=5.0`), но после (замоканного) snap оказываются на одном `way_id` с похожим `distance_m` → должны смержиться во втором проходе (Шаг I.2).
2. Два `TrackedSign` с изначально разным `is_left` (из-за шумной пиксельной эвристики), но геометрически (после Шага I.1) на одной стороне → должны получить одинаковый скорректированный `is_left` и смержиться.
3. Три реально разных знака на одной прямой (разное `distance_m`, разный `way_id` или большая разница азимутов) → НЕ должны смержиться, и `coefficient` должен быть по возрастанию расстояния (Шаг I.3).

## БЛОК J — Точность привязки к GPS и уверенность

### Проблема (контекст для агента)

1. `GPXHandler.get_point(index)` не интерполирует — берёт ближайшую по индексу точку GPX. Один и тот же `gps_index` используется для ~10-12 последовательных обработанных кадров (при `FRAME_STEP=5`, 60fps, GPS раз в секунду) — координата "ступенчатая", не плавная.
2. `gps_index = int(round(abs_frame / 60, 0))` в `video_reader.py` и `detector_thread.py` жёстко предполагает 60 fps видео — если реальный fps другой, вся привязка кадр↔GPS систематически смещена.
3. `GPSPoint` не хранит `time` из GPX, хотя `gpxpy` парсит его — интерполяция по времени невозможна без этого поля.
4. `course` (азимут) из GPS используется как есть, без сглаживания — шумный на низкой скорости, ближе к порогу `MIN_SPEED_KMH=2.0`.
5. `calc_confidence()` в `core/sign.py` не учитывает скорость машины при расчёте `az_score` — на стоянке/медленном движении курс GPS ненадёжен, но уверенность считается так же, как на трассе.
6. `SignHandler._update_azimuths()` использует необъяснённый сдвиг `INDEX_OF_GPS + 1` — вероятно компенсирует рассинхрон видео/GPS, но это magic number без калибровки.

### Шаг J.1 — Хранение времени точки и интерполяция

**Файл:** `core/gpx_handler.py`

1. В `GPSPoint` добавить поле `time_offset_s: float = 0.0` — секунды от начала трека (вычисляется относительно `points[0].time`, либо relative index * ~1с если `time` в GPX отсутствует).
2. В `GPXHandler._load()` — если у точек GPX есть `pt.time`, сохранять `time_offset_s = (pt.time - first_point_time).total_seconds()`. Если `time` отсутствует у всех точек — fallback на текущее поведение (индекс = секунда, `time_offset_s = index * 1.0`).
3. Добавить новый метод:
   ```python
   def get_interpolated(self, abs_frame: int, fps: float) -> GPSPoint:
       """
       Возвращает GPSPoint с линейно интерполированными lat/lon/course
       между двумя ближайшими GPX-точками по фактическому времени кадра.
       """
   ```
   - Вычислить `t = abs_frame / fps` (секунды от начала обработки/видео).
   - Найти две соседние точки трека, между `time_offset_s` которых попадает `t` (бинарный или линейный поиск — трек обычно отсортирован по времени).
   - Линейно интерполировать `latitude`/`longitude` (для коротких расстояний линейная интерполяция в градусах допустима; для курса — интерполировать через `CoordinateCalculation.bearing()` между двумя точками или sin/cos-усреднение углов, НЕ линейно по градусам напрямую, чтобы избежать разрыва на переходе 359°→1°).
   - `speed` — линейно интерполировать между двумя точками.
   - Возвращать новый `GPSPoint` с интерполированными значениями.
4. Обратная совместимость: старые методы `get_point`, `get_azimuth`, `get_current_coordinate`, `get_speed` оставить как есть (используются в местах, где `abs_frame`/`fps` недоступны напрямую, например `map_server.py`).

### Шаг J.2 — Реальный FPS вместо жёсткой константы 60

**Файлы:** `processing/video_reader.py`, `processing/detector_thread.py`, `processing/detector_process_pool.py`, `configs/config.py`

1. В `configs/config.py` добавить `VIDEO_FPS: float = 60.0` рядом с `FRAME_WIDTH`/`FRAME_HEIGHT` — обновляется при открытии видео, как и они.
2. В `video_reader.py::_read_all_videos()` — после `cap.set/get`, сохранять `config.VIDEO_FPS = cap.get(cv2.CAP_PROP_FPS)` (с защитой от `0`/`None` — fallback на 60.0, если метаданные видео некорректны).
3. Заменить все места, где `gps_index` вычисляется через захардкоженное `/ 60`, на использование `config.VIDEO_FPS`:
   - `video_reader.py`: `gps_index = int(round(abs_frame / 60, 0))` и `if (abs_frame - gps_index * 60) > 60`.
   - `detector_thread.py`: `current_second = raw.abs_frame_number // 60`.
4. Использовать `GPXHandler.get_interpolated(abs_frame, config.VIDEO_FPS)` вместо `get_point(gps_index)` в:
   - `detector_thread.py::_build_detected()` — источник координат для `DetectedSign`.
   - `detector_process_pool.py::ResultAggregatorThread._build_detected_signs()` — тот же путь для process_pool режима.
5. **Важно:** сохранить `config.INDEX_OF_GPS` (используется в `Turn`, `SignHandler`) как приблизительный индекс для обратной совместимости, но координаты/азимут для `DetectedSign` брать из интерполированного метода.

### Шаг J.3 — Сглаживание курса и учёт скорости в уверенности

**Файл:** `core/gpx_handler.py`, `core/sign.py`

1. В `GPXHandler._load()` — после загрузки точек, применить скользящее сглаживание курса (окно 3-5 точек, угловое усреднение через sin/cos-компоненты, не линейное) и сохранить как `course` каждой точки (либо добавить отдельное поле `course_smoothed`, если нужно сохранить сырое значение для диагностики).

3. В `FinalHandler` — там, где вызывается `sign.calc_confidence(...)`, передавать `speed_kmh` (взять из последнего доступного наблюдения знака — потребуется либо хранить `speed` в `TrackedSign` при `append()`, либо получать из `GPXHandler` по последнему `car_x/car_y` через обратный geocoding индекса; предпочтительно — хранить: добавить `speed_kmh: list[float]` в `TrackedSign`, заполнять в `SignHandler._add_sign`/`append`).

### Шаг J.4 — Кросс-валидация курса (self-consistency check)

**Файл:** `core/sign.py`

1. Добавить приватный метод `_calc_azimuth_self_consistency(self) -> float`:

   - Сравнить с усреднённым GPX-курсом (`self.azimuth` до перезаписи snap-азимутом).
   - Разница < 10° → score 1.0, разница > 45° → score 0.0, линейная интерполяция между.
2. Включить этот score как дополнительный компонент в `conf_placement` (переразбить веса аналогично тому, как уже было сделано для `conf_side` в "ЗАДАЧЕ 2" — например, 0.20×track + 0.15×length + 0.20×snap + 0.15×az + 0.15×side + 0.15×self_consistency; сумма весов должна остаться равной 1.0).

## БЛОК K — Производительность на CPU

### Проблема (контекст для агента)

1. `torch.set_num_threads(1)` и `OMP_NUM_THREADS=1`/`MKL_NUM_THREADS=1` выставлены **и в главном Qt-потоке** (обоснованно, против конфликта DLL), **и в изолированных worker-процессах** `detector_process_pool.py::_worker_process_frame` — там Qt физически отсутствует, конфликт невозможен, но производительность инференса урезана до одного потока.
2. `compute_image_hash()` в `core/detector.py` использует вложенные Python-циклы `for i in range(8): for j in range(8):` для сборки бит хеша — тривиально векторизуется.
3. Хеш для знаков-треугольников считается дважды (для основной CNN-модели и для саб-модели треугольников) — можно посчитать один раз.
4. Модели грузятся через `ultralytics.YOLO` (eager PyTorch) — на CPU это медленнее, чем экспортированные ONNX-модели.

### Шаг K.1 — Снять ограничение потоков в изолированных worker-процессах

**Файл:** `processing/detector_process_pool.py::_worker_process_frame`

1. Убрать (или сделать настраиваемым через `AppSettings`) принудительное `torch.set_num_threads(1)` внутри worker-функции — заменить на `torch.set_num_threads(os.cpu_count())` либо не трогать вовсе (оставить дефолт PyTorch).
2. `os.environ["OMP_NUM_THREADS"] = "1"` и `os.environ["MKL_NUM_THREADS"] = "1"` в начале `_worker_process_frame` — **обосновать явным комментарием**, что это workaround исключительно для конфликта с Qt в главном процессе, и в контексте отдельного worker-процесса без Qt их следует либо убрать, либо поднять до `os.cpu_count() // N_WORKERS` (чтобы не конкурировать друг с другом при нескольких воркерах одновременно — прямое снятие лимита в каждом из N процессов может привести к oversubscription CPU).
3. **Важно:** делать это изменение экспериментально — добавить настройку `AppSettings.process_pool_unlock_threads: bool = True` с возможностью откатить через UI, если на конкретной машине это вызовет конфликты/деградацию (некоторые связки BLAS+multiprocessing действительно чувствительны к oversubscription).
4. Прогнать `benchmark_detector.py` / `benchmark_end_to_end_cpu.py` до и после изменения, зафиксировать цифры FPS в отчёте.

### Шаг K.2 — Векторизация compute_image_hash

**Файл:** `core/detector.py`

1. Заменить:
   ```python
   hash_value = 0
   for i in range(8):
       for j in range(8):
           if diff[i, j]:
               hash_value |= (1 << (i * 8 + j))
   ```
   на векторизованный вариант через `numpy`:
   ```python
   bits = diff.flatten().astype(np.uint8)
   packed = np.packbits(bits)  # 8 байт для 64 бит
   hash_value = int.from_bytes(packed.tobytes(), byteorder="big")
   ```
   **Убедиться, что порядок бит совпадает с оригинальной реализацией** (или, если направление бит не критично для консистентности кэша — просто зафиксировать новый порядок и не переживать за обратную совместимость со старыми сохранёнными хешами, так как кэш пересоздаётся каждый запуск).
2. Добавить unit-тест: сравнить результат старой (можно временно оставить как `_compute_image_hash_naive` для теста) и новой реализации на нескольких случайных изображениях — хеши (после фиксации единого порядка бит) должны совпадать побитово, либо, если меняете порядок — просто проверить, что функция детерминирована и различает визуально разные изображения (через тест на хэммингово расстояние).

### Шаг K.3 — Не считать хеш дважды для треугольников

**Файл:** `core/detector.py::_run_cnn_model`, `_run_cnn_batch`

1. В `_run_cnn_model` — `img_hash` уже посчитан один раз в начале метода (`img_hash = compute_image_hash(crop32)`); внутри субклассификации треугольников для `sub_cache_key` считается **новый** `sub_hash = compute_image_hash(crop32)` на том же `crop32` — это тот же хеш, просто с другим префиксом ключа кэша. Убрать повторный вызов, переиспользовать `img_hash`:
   ```python
   sub_cache_key = f"sub_{result_type}:{img_hash}"
   ```
2. То же самое в `_run_cnn_batch` — там тоже пересчитывается `img_hash = compute_image_hash(crops32[i])` для основного кэша и `img_hash = compute_image_hash(crop)` (тот же `crop = crops32[i]`) для sub-кэша — оставить один вызов на кроп за проход батча.

### Шаг K.4 — (Опционально, отдельная веха) Экспорт моделей в ONNX

**Файл:** новый `scripts/export_models_onnx.py`, `configs/sign_models.py`

Это отдельная, более рискованная веха — выполнять только после K.1-K.3 и с одобрения по результатам бенчмарка простых оптимизаций.

1. Создать скрипт `scripts/export_models_onnx.py`, который для каждой модели в `sign_models.py` (`model_side_detect`, `rube_modal`, все из `model_dict`, `sub_models`) вызывает `YOLO(path).export(format="onnx", dynamic=False, simplify=True)` и сохраняет рядом с оригинальным `.pt`.
2. В `configs/sign_models.py::_LazyModel` — добавить опциональный режим загрузки через `onnxruntime.InferenceSession` вместо `ultralytics.YOLO`, переключаемый через `AppSettings.use_onnx_runtime: bool = False` (дефолт False — не менять поведение по умолчанию без явного включения пользователем, так как формат входа/выхода ONNX-инференса нужно аккуратно подогнать под текущий код `_classify_rube_batch`/`_classify_fine_batch`, которые полагаются на структуру ultralytics `Results` — `probs.top1conf`, `boxes.xyxy` и т.д.).
3. Если реализация ONNX-пути окажется существенно сложнее из-за разницы API — задокументировать это как отдельную веху в отчёте и НЕ блокировать остальной промпт; K.1-K.3 должны быть выполнены и оценены независимо.

### Шаг L.2 — Настоящие тени через QGraphicsDropShadowEffect

**Файл:** новый `ui/themes/elevation.py`, применение в `dashboard_page.py::StatCard`, местах с `#Card`/`#CardElevated`

1. Создать утилиту:
   ```python
   # ui/themes/elevation.py
   from PyQt6.QtWidgets import QGraphicsDropShadowEffect, QWidget
   from PyQt6.QtGui import QColor

   def apply_elevation(widget: QWidget, level: str = "md") -> None:
       """
       Применяет мягкую тень к виджету через QGraphicsDropShadowEffect.
       level: "sm" | "md" | "lg" — соответствует токенам shadow_sm/md/lg.
       """
       from ui.themes.theme_manager import theme_manager
       t = theme_manager.tokens

       params = {
           "sm": (8, 2),
           "md": (16, 4),
           "lg": (28, 8),
       }
       blur, y_offset = params.get(level, params["md"])

       shadow_token = t.get(f"shadow_{level}", "rgba(0,0,0,0.1)")
       color = _parse_rgba(shadow_token)  # вспомогательный парсер "rgba(r,g,b,a)" -> QColor

       effect = QGraphicsDropShadowEffect(widget)
       effect.setBlurRadius(blur)
       effect.setOffset(0, y_offset)
       effect.setColor(color)
       widget.setGraphicsEffect(effect)
   ```
   Реализовать `_parse_rgba()` — парсинг строки `"rgba(38, 36, 31, 0.05)"` в `QColor` с alpha в диапазоне 0-255.

## Порядок выполнения и зависимости

```
БЛОК I (дедупликация)  ──┐
                          ├── независимы друг от друга, можно параллелить
БЛОК J (GPS-уверенность) ─┘

БЛОК K (CPU-перформанс)  ── независим, но Шаг K.1 стоит тестировать
                             ПОСЛЕ Блоков I/J, чтобы бенчмарк отражал

БЛОК L (светлая тема)     ── полностью независим, можно делать в любой момент,
                             в том числе первым, если нужен быстрый видимый результат
```

Рекомендуемый порядок для одного агента, работающего последовательно: **I → J → K → L** (сначала данные корректны, затем быстро, затем красиво), но допустимо поменять L в начало, если нужен быстрый демонстрируемый результат для стейкхолдеров.
