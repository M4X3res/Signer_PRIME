# Промпт для ИИ-агента: реорганизация проекта, ужесточение лицензии, безопасная подготовка релиза

Скопируй всё содержимое этого файла целиком и отдай его ИИ-агенту (Claude Code
или аналогичному инструменту с доступом к репозиторию) как первое сообщение
в новой задаче.

---

## КОНТЕКСТ

Это Python/PyQt6-приложение "Signer PRIME" (RoadScanner) — детекция дорожных
знаков по видео + GPS. Лицензионный сервер уже развёрнут на Google Cloud Run
и работает (`signer-license-server/`), трогать его код не нужно, только
клиентскую часть (`licensing/`, `configs/settings.py`, `main.py`).

У тебя есть доступ к полному репозиторию. Работай итеративно,小步 (маленькими
коммитами/патчами), после каждого крупного шага прогоняй тесты
(`pytest tests/ -v`, а также `python tests/*.py` для файлов без pytest-обвязки)
и явно докладывай, что изменилось.

**НЕ трогай `signer-license-server/`** — это отдельный, уже задеплоенный сервис.

## ⚠️ ГЛАВНОЕ ОГРАНИЧЕНИЕ — ЧИТАЙ ПЕРВЫМ

Ты будешь запускать шаг подготовки релиза, который включает **обфускацию
через PyArmor** (`scripts/build/obfuscate_licensing.py`, вызывается из
`scripts/build/prepare_release.bat`). Это КРИТИЧЕСКИ опасная операция:
PyArmor умеет как копировать исходники в отдельную директорию перед
обфускацией (правильно), так и **перезаписывать файлы на месте** (неправильно
и катастрофично — теряется читаемый, поддерживаемый исходный код навсегда,
если нет git-истории или бэкапа).

Правила, которые нужно соблюдать неукоснительно:

1. **Обфускация имеет право писать ТОЛЬКО в `build/obfuscated/`** (или другую
   явно выделенную scratch-директорию, добавленную в `.gitignore`). Ни один
   файл в `licensing/`, `core/`, `configs/`, `ui/`, `processing/`, `server/`,
   `main.py` и т.д. **не должен быть изменён обфускатором на месте**.
2. Перед запуском обфускации убедись, что `git status --porcelain` в корне
   репозитория пустой (нет незакоммиченных изменений) — если не пустой,
   останови процесс и попроси пользователя закоммитить/застэшить изменения
   вручную. Никогда не коммить и не стэшить за пользователя без явной просьбы.
3. После запуска обфускации ОБЯЗАТЕЛЬНО проверь `git status --porcelain` /
   `git diff --stat` ещё раз — если хоть один файл вне `build/` изменился,
   **немедленно останови сборку**, сделай `git checkout -- <файлы>` чтобы
   откатить их, и явно сообщи пользователю, что обфускатор попытался писать
   в исходники (это баг конфигурации PyArmor — команда/флаги, куда именно
   класть output, см. `obfuscate_licensing.py`, там должен быть явный
   `--output`/`-O` в `build/obfuscated/...`, а не запуск "на месте").
4. Добавь автоматическую проверку прямо в скрипт подготовки релиза
   (`prepare_release.bat` и/или обёртку на Python): до обфускации — снимок
   SHA-256 всех файлов в `licensing/`, `core/`, `configs/`, `main.py`; после
   обфускации — пересчитать хэши тех же файлов вне `build/` и сравнить.
   При любом расхождении — упасть с ошибкой и не продолжать сборку.
5. Никогда не удаляй и не переименовывай оригинальные модули как часть
   "очистки" в рамках обфускации. Обфускация — это генерация ДОПОЛНИТЕЛЬНОГО
   артефакта для сборки, оригиналы в git должны остаться нетронутыми 1:1.
6. Если `pyarmor` не установлен или версия несовместима (в проекте уже есть
   защита в `prepare_release.bat`: `python -c "import pyarmor"` с fallback на
   `SKIP_OBFUSCATION=1`) — не пытайся "исправить" это апгрейдом/downgrade
   pyarmor самостоятельно без согласования, просто уважай существующий
   fallback-путь.

Держи это ограничение в голове на протяжении ВСЕЙ задачи, а не только на
этапе билда — если по пути тебе нужно что-то протестировать через PyArmor,
делай это в scratch-копии репозитория/временной директории, никогда в
рабочем дереве с реальными файлами.

## ЗАДАЧА 1 — Реорганизация структуры проекта

Цель: в корне репозитория остаётся `main.py` (точка входа) и минимальный
набор конфигурационных/метафайлов, всё остальное разложено по осмысленным
папкам. Часть структуры уже логична (`core/`, `configs/`, `processing/`,
`ui/`, `server/`, `licensing/`, `updater/`, `templates/`, `scripts/`, `tests/`),
но в корне и в `scripts/` накопился мусор. Сделай так:

1. **Сформируй инвентаризацию корня** (`ls` в корне репо) и рассортируй:
   - Точка входа: `main.py` — остаётся в корне.
   - Спеки сборки: `signer.spec`, `updater.spec` — оставить в корне (PyInstaller
     обычно ищет их там; либо вынести в `build/specs/` и обновить команды
     запуска — на твоё усмотрение, но задокументируй в README, если переносишь).
   - `version.json`, `build_config.json(.example)`, `requirements*.txt`,
     `.gitignore`, `.gitattributes`, `README.md` — остаются в корне
     (стандартные метафайлы проекта).
   - Любые разовые `.bat`/`.ps1`/`.py` скрипты разработки, лежащие прямо в
     корне (если найдёшь) — переносим в `scripts/dev/` или `scripts/build/`
     по смыслу (в репозитории уже есть `scripts/dev/`, `scripts/build/`,
     используй их).
   - Любые `*.md` отчёты/черновики агентов из корня (если есть, кроме
     `README.md`) — в `docs/` (создай `docs/archive/` для устаревших).
   - Проверь `assets/`, `installer/` — это нормальные папки для иконок и
     Inno Setup конфигурации, не трогай без причины.
2. **Модели и данные**: `CNN_side/`, `lane_guidance_models/`, `small_models/`,
   `sings/`, `sings_text/`, `static/`, `configs/data/` — это ассеты моделей,
   уже в `.gitignore` частично (см. `configs/small_models/`,
   `configs/lane_guidance_models/` заблокированы для дублей) — оставь как
   есть, только убедись что структура согласована с `signer.spec` (пути в
   `_project_dirs` там жёстко прописаны — если что-то переносишь, синхронизируй).
3. **После любого переноса файлов**:
   - Обнови все `import`/`from ... import` пути в затронутых модулях.
   - Обнови пути в `signer.spec`, `updater.spec`, `installer/SignerInstaller.iss`,
     `.gitignore`, `.gitattributes`, `scripts/build/*.bat`, `scripts/build/*.ps1`.
   - Прогони `python -m py_compile` по изменённым файлам и запусти тесты.
   - Проверь, что `app/utils.py::resource_path()` по-прежнему корректно
     резолвит пути и в dev-режиме, и в frozen (`sys._MEIPASS`) сборке — эта
     функция завязана на относительные пути от корня, будь аккуратен.
4. Не переноси и не переименовывай файлы внутри `signer-license-server/` —
   это отдельный поддеревом-проект со своей структурой, не трогаем.
5. Зафиксируй финальную структуру одним абзацем в `README.md`
   (секция "Структура проекта" там уже есть — актуализируй её).

## ЗАДАЧА 2 — Убрать возможность работы без действующей подписки офлайн

Сейчас (судя по коду) большая часть grace-period логики уже была вырезана
в прошлой итерации (см. комментарии в `configs/settings.py`:
`"ЗАДАЧА 2: Убрана офлайн-работа на несколько дней"`, и в
`licensing/license_manager.py::verify_access_async()` — сетевая ошибка при
старте уже возвращает `NETWORK_ERROR`, который в `main.py` блокирует запуск
до успешного ответа сервера). Но нужно **аудировать весь путь целиком** и
убедиться, что нигде не осталось лазейки на несколько дней офлайн-работы:

1. **`licensing/license_manager.py`**:
   - Проверь `LicenseStatus.GRACE_PERIOD` — судя по коду, это значение enum
     нигде фактически не присваивается (`_verify_access_internal()` всегда
     возвращает либо `VALID`, либо `NOT_ACTIVATED`/`EXPIRED`/`REVOKED`, либо
     `NETWORK_ERROR`). Если `GRACE_PERIOD` действительно мёртвый код — удали
     сам enum-член и все ветки обработки в `ui/widgets/license_dialog.py`
     (`_show_info_state()` проверяет `status == LicenseStatus.GRACE_PERIOD`)
     и в `tests/test_licensing.py` (там есть закомментированный блок про
     grace period тесты — убедись, что реального grace-period поведения
     не осталось нигде, включая закомментированные напоминания).
   - `check_local_status()` — это **только локальная** проверка (подпись,
     дата, откат часов) и **не должна** сама по себе разрешать запуск
     приложения. Убедись, что `main.py` действительно вызывает
     `verify_access_async()` (строгая онлайн-проверка) при каждом старте, а
     не `check_local_status()` напрямую — сейчас в `main.py` это так и есть,
     но перепроверь, что никакой другой код (например, `settings_page.py`,
     `_update_license_display()`) не используется как обходной путь для
     "запуска" функциональности без свежей онлайн-проверки. Обновление
     статуса в настройках — это ОК показывать, но не должно быть точкой,
     через которую можно продолжать работать без стартовой онлайн-проверки.
   - `RUNTIME_CHECK_INTERVAL_HOURS = 6` — раз в 6 часов во время работы
     запускается runtime-проверка (`start_runtime_monitor`). Если она
     возвращает `NETWORK_ERROR`, текущий код **не блокирует** уже запущенное
     приложение (только `EXPIRED`/`REVOKED` вызывают критический выход, см.
     `main.py::_on_license_status_changed`). Уточни у пользователя ожидаемое
     поведение: вариант А (мягче) — если сеть пропала посреди работы,
     позволить доработать текущую сессию до следующего успешного онлайн-чека
     (не рвать активную обработку видео); вариант Б (жёстче) — если N
     подряд идущих runtime-проверок дают `NETWORK_ERROR`, тоже блокировать.
     **Не решай это самостоятельно за пользователя** — реализуй вариант А
     по умолчанию (это разумный компромисс: обязательная онлайн-проверка
     при каждом старте уже закрывает многодневный офлайн-сценарий), но явно
     напиши в отчёте, какое поведение выбрано и почему, чтобы пользователь
     мог попросить ужесточить дальше.
2. **`licensing/license_client.py` / токен**: убедись, что `current_period_end`
   в токене — это дата окончания реальной подписки на сервере (а не
   искусственно продлённая grace-дата). Судя по `app/services/license_service.py`
   на сервере, это так. Ничего трогать на сервере не нужно, просто
   зафиксируй в отчёте, что source of truth — `current_period_end` из БД,
   без клиентского запаса.
3. **`configs/settings.py`**: подтверди, что полей вида
   `license_grace_period_days` / `license_refresh_interval_days` в
   dataclass'е `AppSettings` больше нет (по коду их уже нет — только
   `license_startup_retry_timeout_sec` для повторных попыток подключения
   при временном сбое сети на старте, это нормально и не является офлайн-
   работой, т.к. приложение не запускается, пока не получит `VALID`).
4. **Удаление локального токена**: убедись, что при `EXPIRED`/`REVOKED`
   (и любой другой критической ошибке от сервера, кроме сетевой) токен
   гарантированно удаляется (`_delete_token()`), чтобы нельзя было
   перезапустить приложение офлайн и получить старый `VALID` по кэшу —
   в `check_local_status()` это уже проверяется через `current_period_end`
   и подпись, но убедись, что нет пути, где протухший токен молча
   считается валидным при отсутствии сети (сейчас `check_local_status()`
   не обращается к сети вообще и сам по себе может дать `VALID` — ЕЩЁ РАЗ
   убедись, что этот метод используется ТОЛЬКО для быстрых UI-подсказок
   (`SettingsPage._update_license_display()`), а не для решения "пускать
   ли пользователя в приложение").
5. Напиши/обнови юнит-тест в `tests/test_licensing.py`, который явно
   проверяет: при `NETWORK_ERROR` во время `verify_access_async()` при
   старте пользователь не получает доступ к главному окну (замокай
   `LicenseClient.refresh`, чтобы бросал `ConnectionError`, и убедись, что
   `_verify_access_internal()` возвращает `NETWORK_ERROR`, а не `VALID`,
   даже если на диске лежит валидный по всем локальным признакам токен).

## ЗАДАЧА 3 — Чек-лист подготовки перед билдом

Собери (в виде markdown-файла `docs/RELEASE_CHECKLIST.md`, если такого ещё
нет, либо актуализируй существующий) пошаговый чек-лист и по возможности
автоматизируй проверяемые пункты прямо в `prepare_release.bat`:

1. `git status --porcelain` пустой в начале и в конце сборки (см. правило
   про обфускацию выше — это ОБЯЗАТЕЛЬНАЯ автоматическая проверка, не
   просто пункт в доке).
2. `build_config.json` существует, содержит реальный (не placeholder) URL
   лицензионного сервера — `prepare_release.bat` уже это частично проверяет
   (`findstr` на `license.signer-prime.com` и `your-license-server.run.app`),
   убедись, что там прописан именно актуальный Cloud Run URL, который
   реально развёрнут у пользователя; если пользователь его не дал явно в
   этой задаче — оставь плейсхолдер-проверку как есть и явно спроси URL,
   не изобретай его.
3. `licensing/public_key.py::LICENSE_PUBLIC_KEY_PEM` — публичный ключ
   соответствует приватному ключу реально работающего сервера (не dev-ключ).
   В файле уже есть runtime-защита `_check_production_key()`, которая
   роняет `RuntimeError` во frozen-сборке при совпадении с `DEV_KEY_SHA256`
   — это хорошо, не убирай эту проверку. Просто удостоверься перед сборкой,
   что ключ актуальный (спроси пользователя, если не уверен, не подставляй
   ключ от себя).
4. `version.json` — версия инкрементирована по сравнению с прошлым релизом
   (сверь с `installer/SignerInstaller.iss::AppVersion` и синхронизируй оба
   места, они сейчас независимы и могут разъехаться).
5. Все тесты зелёные: `pytest tests/ -v` (клиент) — не трогай тесты сервера,
   они отдельно гоняются в CI сервера.
6. Модели присутствуют на диске (`CNN_side/`, `lane_guidance_models/`,
   `small_models/`) — `signer.spec` уже печатает предупреждение, если папки
   нет, но билд не должен продолжаться "по-тихому" без моделей — рассмотри
   превращение `print`-предупреждений в `sys.exit(1)` в `signer.spec` для
   критичных моделей (без них приложение бессмысленно), либо явный
   интерактивный вопрос перед стартом PyInstaller.
7. `7z.exe`/`7z.dll` в `installer/` присутствуют (нужны и для инсталлятора,
   и для `Updater.exe`).
8. Прогони `scripts/dev/run_all_tests.bat` (уже существует) как финальный
   гейт перед `prepare_release.bat`.
9. Убедись, что режим лицензии **не** является mock/dev (`LICENSE_MOCK_MODE`
   упоминается в некоторых доках как флаг — если такой флаг всё ещё
   физически существует где-то в `licensing/license_client.py`, найди его
   и убедись, что он `False`/удалён для прод-сборки; по текущему коду файла
   такого флага уже нет — если найдёшь остаточные упоминания в
   документации (`CLIENT_INTEGRATION.md`, `docs/`), актуализируй текст, но
   не выдумывай функциональность, которой нет в коде).
10. Только после всех пунктов выше — запуск `scripts/build/prepare_release.bat`.
