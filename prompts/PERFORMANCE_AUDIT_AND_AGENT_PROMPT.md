## Часть 2. Детальный разбор по подсистемам

### 2.1 ML-пайплайн детекции — `core/detector.py`

```python
def detect(self, frame):
    raw_boxes = self._find_boxes(frame)          # YOLO #1 — один проход на кадр
    for box, is_side in raw_boxes:
        ...
        yolo_class = self._classify_rube(resized)   # YOLO #2 — на каждый бокс
        cnn_class  = self._classify_fine(resized, yolo_class)  # YOLO #3 — на каждый бокс
        text = self._read_text(crop, cnn_class, yolo_class)    # EasyOCR — на каждый бокс с текстом
```

**Проблема:** для кадра с N обнаруженными знаками выполняется 1 + 3×N последовательных forward-pass'ов разных моделей на CPU, каждый со своим overhead инициализации тензоров. Нет батчинга ни внутри кадра (несколько кропов одного типа `treugolnik` можно скормить `model_dict["treugolnik"]` одним батчем), ни между кадрами.

**Обоснование из логов:** FPS редко превышает ~2.9 даже при отсутствии знаков (чистый YOLO-проход), и почти всегда падает ниже 1.1 при появлении 2+ знаков в кадре одновременно.

### 2.2 EasyOCR — узкое место №1 по влиянию на UX

`core/detector.py::_ocr()` вызывает `_get_ocr().readtext(crop)` **синхронно** в основном потоке детекции. Лог:

```
14:01:52 [WARNING] easyocr.easyocr: Using CPU...
14:01:54 [INFO] ...FPS: 0.3, Cache: 2.1% (3/142)
```

FPS падает с ~2.8 до 0.1–0.3 (в 10–28 раз) на каждом знаке с текстом. `WHY_SINGLE_THREAD_FASTER.md` честно объясняет, что вынос OCR в отдельный `QThread` (Pipeline-режим) **не помогает** из-за GIL — Python не даёт параллелизма на CPU-bound задачах в потоках. Реальное решение требует либо `multiprocessing` (с фиксированными, а не по требованию, воркерами), либо уменьшения частоты OCR-вызовов, либо более лёгкой модели распознавания текста.

### 2.3 CNN-кэш — красивая метрика, нулевая польза

`processing/detector_thread.py` логирует `CNN кэш инициализирован: размер=1000`, но по всем сессиям (13:36–13:37, 14:38–14:42 и т.д.) `Cache Hit` держится в диапазоне **0.0–3.5%**, при этом сам кэш пухнет до 900+ записей. Это означает: ключ кэширования (скорее всего хэш сырого пикселя кропа) почти никогда не совпадает между кадрами, потому что каждый кроп немного отличается (движение камеры, компрессия, масштаб). Кэш тратит память и CPU на хэширование/lookup, не давая ускорения.

**Правильная идея кэширования:** кэшировать не по пикселям кропа, а по `TrackedSign` — если знак уже классифицирован N раз стабильно, не гонять его через дорогой pipeline на каждом кадре, а доверять уже накопленному большинству голосов (`best_cnn`) после порога уверенности.

### 2.4 OSM Snap — сетевой bottleneck в фазе сохранения

`core/osm_snap.py`:
- `MIN_REQUEST_INTERVAL = 0.3–0.5` сек между запросами к Overpass API (rate-limit)
- Кэш по ячейке `round(lat,3), round(lon,3)` (~111 м) — грубый, но лучше, чем ничего
- `FinalHandler._snap_sign_coords()` вызывает snap **для каждого знака отдельно** при сохранении

Для 100+ знаков минимальное время только на rate-limit — 30–50 секунд, плюс сетевая латентность до `overpass-api.de` (внешний публичный сервер, без SLA). `FIX_SLOW_SAVING.md` и `FIX_SAVING_HANG.md` подтверждают, что это была реальная проблема — решена «таймаутом 60 сек», то есть проблема замаскирована, а не устранена архитектурно.

### 2.5 Дедупликация — таймаут вместо архитектуры

`core/final_handler.py::_deduplicate()`:
```python
TIMEOUT_SECONDS = 60
...
if elapsed > TIMEOUT_SECONDS:
    result.extend(features[idx:])  # добавляем БЕЗ дедупликации
    break
```
Уже есть O(n) пространственная сетка (хорошо!), но `_feature_distance_m()` внутри вызывает `pyproj`-трансформацию **дважды на каждую пару кандидатов** без векторизации через numpy. При росте датасета (несколько тысяч знаков за длинный маршрут) 60-секундный таймаут будет срабатывать регулярно, тихо ухудшая качество дедупликации.

### 2.6 Чтение видео — блокирующий подсчёт кадров на старте

`processing/video_reader.py::_count_total_frames()` открывает **каждый** видеофайл через `cv2.VideoCapture` только чтобы прочитать `CAP_PROP_FRAME_COUNT`. Для 14 GoPro-файлов (как в тестовом логе) это 14 инициализаций декодера подряд перед стартом прогресс-бара. Метаданные можно получить быстрее через `ffprobe` без полного открытия декодера, либо закэшировать результат по пути+размеру файла.

Prefetch следующего видео **заявлен реализованным** в `COMPLETION_REPORT_100_PERCENT.md`, но `IMPLEMENTATION_SUMMARY.md` прямо пишет «Блок A.4 — НЕ НАЧАТО». Реальный код `video_reader.py`, приложенный к задаче, **не содержит** prefetch-логики (`_prefetch_next_video` нигде не определён в показанном файле) — значит при переключении между 14 видеофайлами возможна пауза на открытие следующего файла.

### 2.7 Карта / Flask-сервер

`server/map_server.py`:
```python
socketio = SocketIO(app, cors_allowed_origins="*", async_mode="processing")
```
`"processing"` — **не существующее** значение `async_mode` для Flask-SocketIO (допустимые: `threading`, `eventlet`, `gevent`, `gevent_uwsgi`, `None`). `AUDIT_REPORT.md` заявляет: «✅ УЖЕ ИСПРАВЛЕН — используется корректное значение `async_mode="threading"`» — то есть в какой-то момент это было исправлено, а в приложенном снапшоте регрессировало обратно. Это либо баг синхронизации версий, либо откат изменений. Нужно перепроверить и закрыть тестом.

`templates/map.html` рендерит каждый маркер по отдельности без `Leaflet.markercluster` — при треке 13 800+ точек и сотнях знаков браузер будет тормозить (сам файл содержит комментарий-план `«Clustering маркеров — для улучшения производительности»`, но не реализован).

### 2.8 Дублирование моделей и репозитория

Идентичные бинарники (совпадающий SHA256) присутствуют дважды:

| Файл | Размер | Пути |
|------|--------|------|
| `arrow_segment.pt` | 124.7 МБ | `lane_guidance_models/` (только тут) |
| `rude.pt` | 22.1 МБ | `small_models/` и `configs/small_models/` |
| `tabl.pt`, `tabl l.pt`, `blue.pt`, `krug.pt`, `red.pt`, `danger.pt`, `pimicanie.pt`, `suzenie.pt`, `tupic.pt`, `one_side.pt`, `5.38.pt`, `5.9.1-5.14.pt`, `servises.pt`, `treugolnik.pt`, `ogranich.pt` | ~11 МБ каждый | дублируются в обеих директориях |

Итого лишний вес в репозитории/Git LFS — **≈250+ МБ**, что напрямую увеличивает время клонирования, CI, и деплоя. `utils.resource_path()` резолвит путь через `os.getcwd()`, то есть реально используется только один набор файлов — вторая копия абсолютно бесполезна.

### 2.9 Технический долг, влияющий на скорость разработки

- `configs/models.py` (eager-loading модуль) **всё ещё существует** в дереве проекта, хотя `AUDIT_REPORT.md` утверждает его удаление. Случайный `import configs.models` вернёт краш `0xC0000409` на Windows (конфликт DLL YOLO+Qt в главном потоке) — задокументированный в `main.py` риск, который «удаление» должно было устранить.
- История правок `cnn_count` — три взаимоисключающих версии логики за один день (`FIX_CNN_COUNT_CALCULATION.md` → `CRITICAL_UPDATE_CNN_COUNT.md` → `REVERT_CNN_COUNT_TO_ORIGINAL.md` → `FIX_ZERO_CONFIDENCE.md`) без единого юнит-теста, фиксирующего ожидаемое поведение. Один `tests/test_confidence.py` не покрывает `cnn_count` conflict напрямую.
- Логи фиксируют реальный краш `DashboardPage: '_stats_cards'`, отсутствующий в приложенном исходнике `ui/widgets/dashboard_page.py` — значит в проде крутится другая версия файла, не та, что была передана на аудит. Это означает: **между репозиторием, документацией и запущенным приложением нет единого источника истины.**
- Логирование смешанное: часть модулей использует `logging`, часть — исторически `print()` (см. `WORK_SUMMARY.md`: "~100+ print() остались").
