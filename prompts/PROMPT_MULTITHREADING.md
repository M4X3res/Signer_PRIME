# Промпт для ИИ-агента: распараллеливание обработки видео (RoadScanner / Signer PRIME)

> Скопируй весь этот файл в контекст ИИ-агента, работающего непосредственно с
> репозиторием. Это отдельная задача от аудита багов — предполагается, что
> `core/turn.py`, импорты, `setDaemon`, `Qt` в `detector_thread.py` и остальные
> критические баги из предыдущего промпта уже исправлены. Если нет — сначала
> нужно исправить их, иначе распараллеливание сломанного кода даст
> распараллеленно сломанный результат.

---

## ЦЕЛЬ

Сейчас обработка видео идёт по схеме «один читает — один считает»:

```
VideoReaderThread (1 поток, читает кадры)
        │  frame_queue (maxsize=8)
        ▼
DetectorThread (1 поток: YOLO×N + OCR + трекинг + отрисовка превью)
        │  result_queue
        ▼
главный поток (UI, сбор знаков)
```

Всю тяжёлую работу — несколько последовательных вызовов YOLO-моделей на кадр,
OCR, логику трекинга — делает **один-единственный** `DetectorThread`. Это
основной ограничитель скорости. Нужно **увеличить пропускную способность
обработки (кадров/сек)**, задействовав несколько ядер CPU и/или GPU, **не
испортив при этом корректность результата** (тот же набор знаков, та же
привязка к GPS, тот же трекинг).

**Важно: производительность важна, но корректность важнее.** Ложное ускорение
ценой сломанного трекинга или пропущенных знаков — недопустимо.

## ЧАСТЬ 0. ОГРАНИЧЕНИЯ, КОТОРЫЕ НЕЛЬЗЯ НАРУШАТЬ

Прежде чем проектировать параллелизм, пойми, **какая часть pipeline'а
действительно stateless и параллелится, а какая — нет.**

### 0.1. Трекинг знаков (`core/sign_handler.py::SignHandler`) — строго последовательный

`SignHandler.check_the_data_to_add()` сопоставляет знаки текущего кадра с уже
отслеживаемыми знаками **по расстоянию в пикселях от последней известной
позиции** (`sign.pixel_vector_to(det)`), с допуском по разнице номеров кадров
(`gap = current_frame - sign.frame_numbers[-1]`, должно быть `< 7`).
Это **чисто последовательный, стейтфул алгоритм**: чтобы правильно сматчить
знак на кадре N с тем же знаком на кадре N-1, нужно обработать кадры строго по
возрастанию номера, без пропусков порядка. Если два воркера обработают кадры
150 и 151 параллельно и отдадут результат в случайном порядке — трекинг
сломается (задвоит знаки или потеряет их).

**Вывод: логику трекинга (`SignHandler`) распараллеливать НЕЛЬЗЯ.** Она должна
остаться в одном потоке и получать результаты детекции **строго в порядке
номеров кадров**.

### 0.2. Собственно детекция/классификация одного кадра — параллелится хорошо

А вот `Detector.detect(frame)` / `Detector.find_rectangles(frame)`
(YOLO-детекция bbox'ов → грубая классификация → точная классификация → OCR)
для одного кадра **не зависит** от результатов по другим кадрам — это чистая
функция `frame -> list[RawDetection]`. Именно эту часть и нужно распараллелить
между несколькими воркерами.

### 0.3. Глобальное мутируемое состояние в `configs/config.py`

`SignHandler._update_azimuths()` читает **глобальную** переменную
`config.INDEX_OF_GPS` напрямую (не параметр функции):
```python
sign.azimuth = self._gpx.get_azimuth(config.INDEX_OF_GPS + 1)
```
Сейчас это работает, потому что `DetectorThread._process_loop()` обновляет
`config.INDEX_OF_FRAME / INDEX_OF_All_FRAME / INDEX_OF_VIDEO / INDEX_OF_GPS`
непосредственно **перед** вызовом `sign_handler.check_the_data_to_add()`, и всё
это происходит в одном потоке строго по порядку.

**При редизайне это поведение нужно сохранить буквально**: тот единственный
поток/место, где вызывается `SignHandler.check_the_data_to_add()`
(«агрегатор», см. Часть 3), обязан **перед каждым вызовом** синхронно
проставлять эти глобальные переменные для текущего (по порядку!) кадра — точно
так же, как сейчас. Параллельные воркеры детекции **не должны** трогать эти
глобальные переменные вообще.

Также `config.FRAME_STEP` **читается** в `VideoReaderThread` и **пишется** в
`DetectorThread` (`config.FRAME_STEP = max(2, round(-0.5*speed + 10.9))`) —
это уже сейчас потенциальный data race между двумя потоками (без блокировки).
При редизайне либо защити это значение (`threading.Lock` или атомарный
контейнер), либо явно вынеси управление шагом кадра в отдельный, чётко
задокументированный канал (например, воркер-агрегатор кладёт новое значение
шага в `queue.Queue(maxsize=1)`, которую читает reader).

### 0.4. Модели — общие ленивые синглтоны на уровне процесса, а НЕ на воркер

Это самое важное архитектурное ограничение. Открой `configs/sign_models.py`:

```python
model_side_detect = _LazyModel(_p("CNN_side/best.pt"))
rube_modal = _LazyModel(_p("small_models/rude.pt"))
model_dict = {"blue": _LazyModel(...), ...}
...
```

Это **модульные (module-level) синглтоны**. `core/detector.py::Detector`
**не хранит собственных весов** — он лишь дергает эти общие объекты
(`model_side_detect.predict(...)`, `rube_modal.predict(...)` и т.д.). Значит,
если ты просто создашь `N` экземпляров `Detector()` в `N` потоках (threading),
все они **под капотом будут дёргать одни и те же объекты YOLO-моделей
одновременно** — это классический сценарий, для которого `ultralytics.YOLO` /
`torch` **не гарантируют потокобезопасность** конкурентных вызовов `.predict()`
на одном и том же объекте модели (есть открытые issue в репозитории
ultralytics на эту тему — если сомневаешься, проверь актуальное состояние, но
по умолчанию считай shared-instance concurrent predict небезопасным).

Аналогично, `core/detector.py::_get_ocr()`:
```python
_ocr_reader = None
def _get_ocr():
    global _ocr_reader
    if _ocr_reader is None:
        import easyocr
        _ocr_reader = easyocr.Reader(["be"], gpu=False)
    return _ocr_reader
```
Это **ленивая инициализация без блокировки** — если два воркер-потока
одновременно впервые вызовут `_get_ocr()`, получится состояние гонки при
создании `easyocr.Reader` (в лучшем случае — двойная инициализация и утечка
памяти, в худшем — краш). При любом варианте параллелизма этот код нужно
переделать.

**Из этого следует ключевое архитектурное решение, которое нужно принять
осознанно (см. Часть 2):**
- либо переходить на **процессы** (`multiprocessing`) — тогда каждый
  воркер-процесс при импорте `configs.sign_models` получит **свою собственную,
  изолированную** копию всех моделей автоматически, никакого общего состояния
  между процессами не будет, проблема решается сама собой;
- либо оставаться на **потоках**, но тогда придётся **переписать
  `configs/sign_models.py`**, чтобы вместо глобальных синглтонов появился пул
  из `N` независимых наборов моделей (по одному набору на воркер-поток), и
  явно передавать нужный набор в `Detector(models=...)` при создании инстанса
  на каждый поток. Это дороже по памяти (веса моделей грузятся `N` раз) и
  требует более инвазивного рефакторинга `core/detector.py`,
  `core/lane_detector.py`, `configs/sign_models.py`.

Как процессы обходят и «старую» причину ленивой загрузки моделей: в
`configs/sign_models.py` есть комментарий — модели грузили лениво специально
потому, что загрузка YOLO в главном потоке рядом с PyQt6/WebEngine на Windows
вызывала краш (конфликт DLL). Воркер-процессы **вообще не имеют доступа** к
Qt/WebEngine контексту главного процесса — они его даже не импортируют, так
что эта проблема при переходе на процессы исчезает полностью, а не просто
откладывается.

## ЧАСТЬ 1. ШАГ 0 — СНАЧАЛА ПРОФИЛИРОВАНИЕ, ПОТОМ ОПТИМИЗАЦИЯ

Не пиши параллельный код вслепую. Сначала измерь, куда реально уходит время на
один кадр. Добавь временную (потом можно убрать/спрятать за флагом) замеряющую
обвязку вокруг ключевых шагов в `core/detector.py::Detector.detect()`:

- `_find_boxes()` (модель `model_side_detect`)
- цикл по найденным bbox'ам: `_classify_rube()` (модель `rube_modal`)
- `_classify_fine()` (модели `model_dict[...]` / `LaneDetector.find_signs`)
- `_read_text()` (OCR через `easyocr`, если знак предполагает текст)
- время чтения кадра в `VideoReaderThread`
- время трекинга в `SignHandler.check_the_data_to_add()`

Собери статистику (среднее/p95 время каждого шага) на тестовом ролике минимум
на 1000-2000 кадров, с разным количеством знаков в кадре (пустые участки +
насыщенные перекрёстки со множеством знаков). Запиши результаты в
`docs/PROFILING.md` (или в конец `STATUS.md`, если он уже есть по итогам
первого промпта) — это будет твоим обоснованием выбора стратегии
параллелизма в Части 2, а не гаданием.

**Ожидаемая гипотеза** (проверь!): OCR (`easyocr`) и последовательные
маленькие YOLO-вызовы на каждый обнаруженный знак в кадре, вероятно, дают
основной вклад в задержку кадров с большим числом знаков, а не сам поиск
bbox'ов. Если так — это открывает **дешёвую оптимизацию без всякого
параллелизма** (см. Часть 1.1 ниже), которую стоит сделать в первую очередь,
она безопаснее threading/multiprocessing и может дать значительный прирост
сама по себе.

### 1.1. Низкорисковая оптимизация — батчинг классификации внутри кадра

Сейчас в `core/detector.py::Detector.detect()`:
```python
for box, is_side in raw_boxes:
    ...
    resized = cv2.resize(crop, (32, 32))
    yolo_class = self._classify_rube(resized)      # 1 вызов модели на знак
    cnn_class  = self._classify_fine(resized, yolo_class)  # ещё 1 вызов на знак
    text = self._read_text(crop, cnn_class, yolo_class)
```
Если на кадре 5 знаков — это 5 отдельных вызовов `rube_modal.predict(...)` и
до 5 отдельных вызовов моделей из `model_dict`. Ultralytics YOLO поддерживает
**батчинг** — передачу списка изображений в один вызов `.predict([img1, img2,
...])`, что для GPU почти всегда быстрее, чем N последовательных вызовов
(меньше накладных расходов на запуск kernel'ов/переключение контекста), а для
CPU тоже часто выигрывает за счёт лучшей загрузки векторных инструкций и
меньшего Python-оверхеда.

**Задача:** переписать `_classify_rube`/`_classify_fine`, чтобы сначала
собрать все `resized`-кропы кадра в список, прогнать через `rube_modal` одним
батч-вызовом, сгруппировать результат по категории (`model_dict[...]`) и
прогнать каждую группу тоже батчем. Это не требует потоков/процессов вообще и
безопасно для корректности (результат идентичен поштучной обработке, только
быстрее). Сделай это **до** перехода к многопоточности — возможно, этого
одного шага уже хватит для существенного ускорения, а риск внесения багов
почти нулевой по сравнению с многопоточным редизайном.

## ЧАСТЬ 2. ВЫБОР СТРАТЕГИИ: THREADS vs PROCESSES vs GPU-BATCHING

Приведи однозначное решение, подкреплённое цифрами из профилирования (Часть
1), а не «на глаз». Ориентиры:

### Если инференс идёт на GPU (проверь `torch.cuda.is_available()` и то, что
`ultralytics.YOLO` реально использует CUDA, а не CPU по умолчанию — сейчас в
коде нигде явно не указан `device=`, так что стоит проверить, что
автоопределение действительно выбирает GPU при его наличии, и по возможности
задать `device` явно и настраиваемо через `configs/config.py`):

- Предпочтительна стратегия **батчинга кадров**, а не запуска множества
  параллельных воркеров, конкурирующих за одну и ту же видеокарту. Один
  выделенный «инференс-поток/процесс» копит небольшую партию кадров (2-8,
  подбери экспериментально) и прогоняет через модели одним батч-вызовом.
  Несколько независимых процессов с отдельными копиями весов на одной GPU
  будут дублировать видеопамять и конкурировать за GPU-контекст — почти
  всегда хуже, чем один процесс с батчингом.
- Чтение видео (I/O, CPU) можно и нужно распараллелить с инференсом (уже
  частично сделано через `frame_queue`), но множить именно
  YOLO-инференс-воркеры на GPU обычно не даёт линейного прироста.

### Если инференс идёт на CPU (или GPU нет / слабый):

- Предпочтительна стратегия **процессов** (`multiprocessing` /
  `concurrent.futures.ProcessPoolExecutor`), а не потоков:
  - обходит GIL по-настоящему (в отличие от потоков, где выигрыш от
    параллельного Python-кода ограничен, хотя тяжёлые C++/CUDA-операции
    внутри `torch` действительно отпускают GIL — но остальной Python-код
    вокруг них, включая OpenCV `cv2.resize`/`cv2.rectangle`, работает уже не
    так однозначно параллельно);
  - решает проблему общих синглтонов моделей «бесплатно» (см. Часть 0.4) —
    каждый процесс при `import core.detector` получает собственные,
    независимые экземпляры моделей и `easyocr.Reader`;
  - обходит исходную причину DLL-конфликтов Qt+torch+OpenMP на Windows,
    которая раньше лечилась через `os.environ["OMP_NUM_THREADS"]="1"` в
    `main.py` — эта переменная сейчас **ограничивает** внутреннюю
    многопоточность каждого вызова `torch`/`MKL` до 1 потока, то есть даже
    единственный текущий `DetectorThread` не использует все ядра CPU
    эффективно. При переходе на отдельные воркер-процессы эту переменную
    можно (и нужно) **не** прописывать в дочерних процессах — там нет Qt, нет
    конфликта, значит `torch`/`MKL` внутри каждого воркер-процесса могут
    честно использовать несколько потоков. Здесь двойной выигрыш: N
    параллельных процессов, каждый из которых ещё и быстрее сам по себе.
  - минус — накладные расходы на межпроцессный обмен кадрами (numpy-массивы
    1920×1080×3 ≈ 6 МБ на кадр, «в сырую» пиклинг такого объёма через
    `multiprocessing.Queue` заметно дороже, чем передача по ссылке в потоках).
    Смягчение: 1) уменьшать разрешение кадра перед отправкой воркеру до
    минимально нужного моделям размера (`model_side_detect.predict(...,
    imgsz=608, ...)` — модель всё равно ресайзит внутри себя, можно
    закодировать кадр в JPEG перед отправкой и раскодировать в воркере,
    это на порядок уменьшит объём передаваемых данных ценой небольшой потери
    качества/CPU на (де)кодирование — измерь, что выгоднее); 2) использовать
    `multiprocessing.shared_memory.SharedMemory` для нулевого копирования
    больших кадров, если JPEG-кодирование даёт слишком большую потерю
    точности детекции.

**По умолчанию, если профилирование не покажет иного и модели гоняются на
CPU** — реализуй вариант с процессами (`ProcessPoolExecutor` или явный
`multiprocessing.Process` + очереди). Если в системе есть GPU и после
профилирования окажется, что именно GPU — узкое место, сделай упор на
батчинг (Часть 1.1, но на уровне нескольких кадров сразу, не только внутри
одного кадра) в одном выделенном инференс-потоке вместо пула воркеров.

Если сомневаешься — **реализуй оба режима за одним интерфейсом** (см. Часть
3), выбираемых конфигом (`configs/config.py::PROCESSING_MODE = "process_pool"
| "gpu_batch" | "single_thread"`), и оставь `single_thread` (текущее
поведение) как безопасный fallback/baseline для сравнения и на случай проблем
на конкретной машине пользователя.

## ЧАСТЬ 3. ЦЕЛЕВАЯ АРХИТЕКТУРА

```
VideoReaderThread (как сейчас, 1 поток, I/O)
        │  frame_queue: RawFrame(image, frame_number, abs_frame_number,
        │                        video_index, video_name, gps_index)
        ▼
┌───────────────────────────────────────────────────────────┐
│  Detection Worker Pool  (N потоков ИЛИ N процессов —       │
│  выбор согласно Части 2)                                   │
│                                                              │
│  Каждый воркер:                                             │
│    - имеет СОБСТВЕННЫЙ, независимый Detector()              │
│      (свои модели, свой easyocr.Reader — не общие синглтоны)│
│    - НЕ трогает configs/config.py                           │
│    - берёт RawFrame из общей очереди задач                  │
│    - вызывает Detector.find_rectangles(frame.image)         │
│    - отдаёт результат вместе с frame_number обратно          │
└───────────────────────────────────────────────────────────┘
        │  results (могут приходить НЕ по порядку!)
        ▼
┌───────────────────────────────────────────────────────────┐
│  Reorder Buffer                                              │
│  Складывает результаты в dict {frame_number: result},         │
│  выдаёт их наружу строго по возрастанию frame_number,         │
│  ждёт следующий по порядку, если он ещё не готов.             │
└───────────────────────────────────────────────────────────┘
        │  результаты СТРОГО в порядке кадров
        ▼
┌───────────────────────────────────────────────────────────┐
│  Aggregator (1 поток — ровно то, что раньше делал            │
│  DetectorThread, минус сама детекция):                       │
│    - обновляет configs/config.py (INDEX_OF_FRAME и т.д.)     │
│    - вызывает SignHandler.check_the_data_to_add(...)          │
│    - кладёт финализированные знаки в result_queue             │
│    - шлёт pyqtSignal-ы в UI (frame_ready, stats_updated и т.д.)│
└───────────────────────────────────────────────────────────┘
```

### Ключевые моменты реализации

1. **`RawDetection`/результат воркера должен быть picklable** (для
   `multiprocessing`) — сериализуй в простые типы (dataclass с примитивами и
   списками, никаких открытых файловых хендлов/Qt-объектов внутри).
   `core/frame.py::DetectedSign` уже `@dataclass(slots=True)` с простыми
   полями — подходит. Убедись, что из воркера наружу уходит именно это, а не
   сырые объекты YOLO-результатов (`ultralytics.engine.results.Results`),
   которые сериализовать через `pickle` дорого/не всегда возможно —
   конвертируй в `DetectedSign` **внутри воркера**, до отправки результата.

2. **Reorder Buffer**: реализуй как простой класс с `dict[int, T]` + указатель
   на следующий ожидаемый `frame_number`; при поступлении результата — если
   это ожидаемый номер, сразу отдать его (и попытаться отдать всё, что уже
   скопилось следом), иначе положить в буфер и ждать. Добавь метрику размера
   буфера (если он растёт бесконтрольно — воркеры продвинулись намного дальше
   самого медленного кадра, значит нужен верхний лимит на «забег вперёд»,
   иначе будет неограниченный рост памяти — см. пункт про backpressure ниже).

3. **Backpressure / ограничение памяти**: не позволяй воркерам обрабатывать
   произвольно много кадров вперёд, если Aggregator не успевает их
   consuming — иначе при разнице скоростей (детекция быстрее трекинга,
   например) буфер реордеринга будет неограниченно расти. Ограничь размер
   очереди задач для воркеров (`maxsize=...`) и/или размер reorder-буфера
   (например, не давай воркерам брать в работу кадр, если разрыв между самым
   маленьким необработанным номером кадра и самым большим выданным на
   исполнение превышает `N * 3`).

4. **`ProcessingController`** (`processing/processing_controller.py`) —
   публичный API (`start()`, `stop()`, `pause()`, `resume()`,
   `finish_and_save()`, `get_result_signs()`, `get_turn_data()`) должен
   остаться прежним для `ui/main_window.py` — вся многопоточность
   инкапсулируется внутри, замени только то, что раньше называлось
   `DetectorThread`, на новую связку «пул воркеров + reorder buffer +
   Aggregator», сохранив прежние сигналы (`frame_ready`, `progress`, `stats`,
   `video_switched`, `sign_found`, `finished`, `error`).

5. **`pause()`/`resume()`/`stop()`** должны корректно останавливать/возобновлять
   именно ПОДАЧУ новых кадров воркерам (не убивать процессы жёстко посреди
   инференса, если можно избежать) и не приводить к рассинхрону
   reorder-буфера. Продумай graceful shutdown: `stop()` должен дождаться
   штатного завершения текущих задач воркеров (с разумным таймаутом), а не
   убивать процессы `kill -9`-стилем, чтобы не терять частично посчитанные
   знаки и не оставлять зомби-процессы.

6. **Статистика (`stats_updated`)** — счётчики `frames_processed`,
   `signs_found`, `fps` считать в Aggregator (в порядке готовых результатов),
   а не пытаться агрегировать из воркеров с блокировками — Aggregator и так
   единственный, кто видит финальный, упорядоченный поток, это самое простое
   и надёжное место для счётчиков.

7. **Обработка ошибок в воркере**: если один воркер упал на конкретном кадре
   (например, необычный формат/повреждённый кадр) — не роняй весь пайплайн.
   Лови исключение внутри воркера, логируй (`logging`, не `print` — см.
   предыдущий промпт про антипаттерны), отправляй в Aggregator «пустой»
   результат для этого `frame_number` (0 детекций), чтобы reorder-буфер не
   завис в ожидании кадра, который никогда не придёт.

## ЧАСТЬ 4. ЧТО ПРОВЕРИТЬ/СДЕЛАТЬ ОТДЕЛЬНО

- **`configs/sign_models.py`**: если выбрана стратегия процессов — оставить
  как есть (ленивая загрузка сработает независимо в каждом процессе). Если
  выбрана стратегия потоков с изолированными моделями — переписать в фабрику
  `create_model_set() -> ModelSet`, вызываемую по разу на каждый воркер-поток.
- **`core/detector.py::_get_ocr()`** — убрать глобальный module-level
  синглтон без блокировки. Либо (а) сделать `Detector` владельцем своего
  `easyocr.Reader` (создаётся в `__init__`, если нужен — либо тоже лениво, но
  на уровне инстанса, не модуля), либо (б) при процессном подходе можно
  оставить module-level lazy-init как есть — гонки между процессами не будет
  (у каждого свой интерпретатор и своя глобальная переменная), но всё равно
  стоит поставить `threading.Lock` вокруг инициализации на случай, если внутри
  одного процесса когда-нибудь появится больше одного потока, использующего
  Detector.
- **`main.py`**: после перехода на процессы — пересмотри
  `OMP_NUM_THREADS=1`/`MKL_NUM_THREADS=1`/`KMP_DUPLICATE_LIB_OK` (см. предыдущий
  промпт, Часть 3) — эти переменные окружения должны либо не наследоваться
  дочерними воркер-процессами (передавай воркерам чистое окружение, либо явно
  переопредели `OMP_NUM_THREADS` на что-то вроде `max(1, os.cpu_count() //
  N_WORKERS)` для каждого воркера), либо, если workaround всё ещё нужен
  Qt-процессу — оставь его только в главном процессе.
- **Настройка количества воркеров**: вынеси `N_WORKERS` в
  `configs/config.py` или в UI настроек (`ui/widgets/settings_page.py` — там
  уже есть похожие поля вроде `frame_step`/`conf_threshold`), с разумным
  дефолтом (например, `max(1, os.cpu_count() - 1)` для процессов, поменьше для
  потоков/GPU-режима). Дай пользователю возможность откатиться на
  `N_WORKERS=1` (= текущее однопоточное поведение) как safety valve.
- **`processing/video_reader.py`**: сама по себе не бутылочное горлышко в
  типичном случае (диск/декодирование видео обычно быстрее инференса), но
  перепроверь после профилирования (Часть 1) — если окажется, что чтение
  нескольких видеофайлов подряд (`for video_idx, video_name in
  enumerate(config.VIDEOS)`) даёт паузы на переключении файлов, рассмотри
  небольшой prefetch следующего файла, но это низкий приоритет по сравнению с
  основным пулом воркеров.

## ЧАСТЬ 5. ТЕСТИРОВАНИЕ И БЕНЧМАРКИНГ

### 5.1. Регрессия корректности (обязательно, не пропускать)

1. Возьми фиксированный короткий тестовый ролик (или несколько) + GPX.
2. Прогони через **текущий однопоточный** код (`N_WORKERS=1` / старый
   `DetectorThread`, зафиксированный как baseline), сохрани получившийся
   `GeoJSON` как `tests/fixtures/baseline_signs.geojson`.
3. Прогони тот же ролик через новый параллельный код с разным `N_WORKERS`
   (2, 4, 8).
4. Сравни результаты: количество знаков, их типы, азимуты, порядок появления
   в треке. Небольшие расхождения в координатах/времени из-за
   недетерминизма таймингов допустимы, но **набор и типы знаков должны
   совпадать** с baseline с точностью до пренебрежимо малых краевых эффектов
   (задокументируй, если находишь систематические расхождения — это будет
   означать баг в reorder-логике или в передаче состояния трекеру).
5. Оформи это как автоматический тест/скрипт (`tests/test_processing_parity.py`
   или отдельный скрипт `scripts/compare_processing_modes.py`), который можно
   перезапускать при любых будущих изменениях пайплайна.

### 5.2. Бенчмаркинг производительности

Измерь и задокументируй (в `docs/PROFILING.md`/`STATUS.md`):
- FPS (обработанных кадров исходного видео в секунду, с учётом
  `config.FRAME_STEP`) для `N_WORKERS = 1, 2, 4, 8` (или сколько ядер
  реально есть на тестовой машине).
- Момент, после которого рост `N_WORKERS` перестаёт давать прирост
  (насыщение по CPU-ядрам/GPU/IO) — это твой рекомендуемый дефолт.
- Потребление памяти при разном `N_WORKERS` (важно для процессного варианта —
  веса моделей грузятся в каждый процесс).
- Однозначный вывод: во сколько раз ускорилась обработка по сравнению с
  исходным однопоточным `DetectorThread` на той же машине/том же ролике.
