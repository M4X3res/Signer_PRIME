# PROMPT: Реорганизация проекта, ужесточение офлайн-лицензии и починка сборки

## Контекст

Signer PRIME (RoadScanner) — десктопное PyQt6-приложение для детекции дорожных
знаков по видео + GPS. Лицензионный сервер (`signer-license-server/`, FastAPI +
PostgreSQL + Ed25519) уже развёрнут на Google Cloud Run и реально работает —
URL уже прописан в `configs/settings.py::license_server_url`. Его трогать не
нужно, серверная часть вне скоупа этой задачи.

Репозиторий сейчас захламлён: в корне вперемешку лежат код, десятки
одноразовых markdown-отчётов от предыдущих AI-сессий ("отчёт о выполнении",
"summary", "checklist" и т.д.), тестовые скрипты, bat-файлы для git и
конфигурация сборки. Отдельно — текущая система лицензирования разрешает
работу приложения **офлайн до нескольких дней** (grace period), что нужно
устранить: без действующей подписки, подтверждённой сервером, приложение
работать не должно.

Работай итеративно, маленькими проверяемыми шагами, и после каждого крупного
блока (реорганизация / лицензия / сборка) прогоняй существующие тесты
(`pytest tests/`) и структурные regression-тесты в `tests/`, которые проверяют
наличие конкретных строк/методов в файлах (`test_no_eager_model_loading.py`,
`test_performance_optimizations.py`, `test_cpu_thread_parity.py` и т.п.) —
эти тесты читают файлы по **жёстко прописанным путям**, поэтому при переносе
файлов их тоже придётся обновить.

## Задача 2 — Убрать полноценную офлайн-работу без активной подписки

### Текущее поведение (что нужно изменить)
- `configs/settings.py`: `license_refresh_interval_days = 1`,
  `license_grace_period_days = 3`.
- `licensing/license_manager.py::check_local_status()`: если с момента
  `issued_at` прошло больше `refresh_interval_days`, но меньше
  `grace_period_days` — статус `GRACE_PERIOD`, приложение свободно
  запускается **без единого обращения к серверу**. Только после истечения
  `grace_period_days` статус становится `EXPIRED`.
- `main.py`: на старте вызывается только `check_local_status()` (чисто
  локальная проверка подписи и дат из закэшированного токена). Если статус
  `VALID` или `GRACE_PERIOD` — приложение запускается сразу, сеть не
  используется вообще. Если `GRACE_PERIOD` — refresh запускается
  **асинхронно в фоне**, не блокируя работу.
- Итог: пользователь с ранее активированной лицензией может держать
  компьютер офлайн неограниченно долго, если делает это порциями меньше 3
  дней между случайными подключениями к сети (каждое успешное подключение
  сбрасывает `issued_at` на новый refresh) — то есть по факту может
  постоянно работать без интернета.

### Целевое поведение
1. **При каждом запуске приложения** обязательна попытка живого обращения к
   серверу лицензий (`LicenseClient.refresh`) **до** открытия главного окна.
   Просто наличие локально закэшированного валидного токена с датой
   окончания подписки в будущем **не должно быть достаточным** основанием
   для запуска.
2. Если сервер **подтвердил** активный статус — приложение стартует, токен
   обновляется, работа продолжается как обычно (в т.ч. дальнейшая работа с
   уже загруженными видео при кратковременных обрывах сети во время самой
   обработки не должна аварийно прерываться — это уже покрыто текущей
   логикой `_on_license_status_changed` / `finish_and_save`, её не ломать).
3. Если сервер **вернул** `LICENSE_EXPIRED` / `LICENSE_REVOKED` /
   `INVALID_LICENSE` / `DEVICE_DEACTIVATED` / `FINGERPRINT_MISMATCH` —
   показывается диалог активации (как сейчас), офлайн-доступа быть не может.
4. Если сервер **недоступен по сети** (`TIMEOUT`, `CONNECTION_ERROR`) —
   приложение **не должно тихо продолжать работать на закэшированных
   данных несколько дней**. Целевое поведение по умолчанию: показать
   пользователю блокирующий экран/диалог "Не удалось подключиться к серверу
   лицензий. Проверьте интернет-соединение." с кнопкой "Повторить попытку" и
   "Выход" — и не пускать в приложение, пока проверка не пройдёт успешно.
   Ограниченный технический допуск на *кратковременные* сетевые сбои (не
   "офлайн-дни", а секунды/минуты — например ретраи с backoff в пределах
   одной попытки запуска) — это нормально и его можно оставить, но
   поведение "работать сутками без единого успешного обращения к серверу"
   быть не должно.
5. **Уже запущенная и работающая обработка видео** не должна аварийно
   обрываться из-за потери сети в процессе (сохрани существующую логику
   мягкого завершения из `main.py::_on_license_status_changed` — она ждёт
   `results_saved`/таймаут 5 минут перед показом критического диалога). Это
   про runtime-мониторинг во время работы, а не про стартовую проверку.

### Конкретные изменения по файлам

**`configs/settings.py`**
- `license_grace_period_days`: убери как понятие "дни офлайн-работы". Вместо
  него введи `license_offline_tolerance_minutes: int = 0` (или похожее имя) —
  сколько времени/попыток разрешено на *сетевые ретраи при старте*, а не на
  полноценную офлайн-работу. Значение по умолчанию — минимально (0 или
  единицы минут), не дни.
- `license_refresh_interval_days` — либо убери (раз обязательный refresh
  теперь на каждом старте), либо оставь только для управления частотой
  **периодического runtime-мониторинга во время работы** (см.
  `RUNTIME_CHECK_INTERVAL_HOURS` в `license_manager.py`) — не для того, чтобы
  решать, можно ли стартовать офлайн.
- Убедись, что дефолт `license_server_url` остаётся текущим реальным URL
  Cloud Run — **не менять**, это уже рабочий продакшн-сервер.

**`licensing/license_manager.py`**
- `check_local_status()` оставь как есть *для внутренних целей* (парсинг
  токена, проверка подписи, определение истекла ли сама подписка,
  защита от отката часов) — но **перестань** трактовать `GRACE_PERIOD` как
  "можно работать офлайн X дней".
- Добавь новый публичный метод, например
  `verify_access(on_result: Callable[[LicenseStatus, str | None], None]) -> None`
  (асинхронный, через QThread по аналогии с `refresh_async`), который:
  1. Если токена нет вообще → сразу `NOT_ACTIVATED`.
  2. Если токен есть — выполняет `check_local_status()` для быстрой
     локальной отбраковки явно испорченных/отозванных/просроченных по датам
     токенов (это не требует сети и корректно ловит "подписка правда
     закончилась").
  3. Если локально токен выглядит валидным — **всё равно** обязательно
     пытается `client.refresh(...)`. Только успешный ответ сервера переводит
     статус в `VALID`. Обработай коды ошибок: `LICENSE_EXPIRED`/
     `LICENSE_REVOKED`/`INVALID_LICENSE`/`DEVICE_DEACTIVATED`/
     `FINGERPRINT_MISMATCH` → удали локальный токен, верни `EXPIRED`/
     `REVOKED`. `TIMEOUT`/`CONNECTION_ERROR` → верни отдельный статус
     `LicenseStatus.NETWORK_ERROR` (он уже объявлен в enum, но нигде толком
     не используется — используй его) и **не** переводи в `VALID`.
- Удали или явно задокументируй как deprecated использование
  `LicenseStatus.GRACE_PERIOD` в новой логике — если оставляешь значение enum
  ради обратной совместимости сериализации, не давай ему больше открывать
  доступ к приложению без сети.

**`main.py`**
- Замени блок `license_status = license_manager.check_local_status()` +
  условный показ диалога на новый блокирующий поток проверки:
  1. Показать лёгкий модальный индикатор/диалог "Проверка лицензии…"
     (можно переиспользовать паттерн `UpdateDialog`/`BackendVerifyThread` —
     см. `processing/backend_verify_thread.py` как пример QThread-обёртки).
  2. Вызвать `license_manager.verify_access(...)` и дождаться результата
     прежде чем создавать `MainWindow`.
  3. По результату:
     - `VALID` → создать `MainWindow` как сейчас.
     - `NOT_ACTIVATED` / `EXPIRED` / `REVOKED` → показать существующий
       `LicenseDialog` для активации; если пользователь отменил — выйти.
     - `NETWORK_ERROR` → показать диалог с текстом про отсутствие соединения,
       кнопками "Повторить" (снова вызывает `verify_access`) и "Выход"
       (`return`, приложение не запускается). **Не** предлагай "продолжить
       офлайн".
- Оставь текущий `start_runtime_monitor(...)` для периодической проверки во
  время работы (каждые `RUNTIME_CHECK_INTERVAL_HOURS`), но убедись, что при
  сетевой ошибке в рантайме приложение **не** считает это поводом закрыться
  немедленно (в отличие от стартовой проверки) — иначе кратковременный обрыв
  Wi-Fi будет убивать многочасовую обработку видео. То есть: строгая проверка
  — только на старте; во время работы — мягкий мониторинг, как сейчас.

**`ui/widgets/license_dialog.py`, `ui/widgets/settings_page.py`**
- Убери из UI формулировки про "grace period"/офлайн-работу
  (`"⚠️ Grace-период (нет связи с сервером)"` в `settings_page.py`,
  упоминания grace period в описаниях диалога). Замени на нейтральные
  сообщения об ошибке сети/необходимости подключения.
- В `SettingsPage._update_license_display()` актуализируй логику отображения
  статусов под новый enum-набор (`VALID`, `NOT_ACTIVATED`, `EXPIRED`,
  `REVOKED`, `NETWORK_ERROR`) без `GRACE_PERIOD`.

**Документация**
- `docs/LICENSING.md`, `docs/QUICKSTART_LICENSING.md`, `docs/LICENSE_SERVER.md`
  (и любые другие) — найди и убери/перепиши упоминания grace period
  (`grep -rn "grace" docs/ QUICKSTART_LICENSING.md docs/*.md`), в т.ч. старые
  цифры "10 дней" (уже расходятся с кодом, но раз мы убираем офлайн — нужно
  описать новую модель: "приложение требует активного подключения к серверу
  лицензий при каждом запуске").

**Тесты (`tests/test_licensing.py`)**
- Убери/перепиши `test_grace_period` и `test_grace_period_exceeded` — новая
  модель не имеет многодневного grace period.
- Добавь тесты на новое поведение: 1) сервер недоступен при старте → статус
  `NETWORK_ERROR`, приложение не открывает `MainWindow`; 2) сервер подтвердил
  `active` → `VALID`; 3) сервер вернул `revoked`/истёкшую подписку →
  локальный токен удаляется, показывается диалог активации. Мокай
  `LicenseClient` (сеть уже мокается через `sys.modules['requests'] = Mock()`
  в начале файла — используй этот же паттерн, не делай реальных HTTP-вызовов
  в тестах).

### Критерий приёмки Задачи 2
- Отключение сети **до** запуска приложения → приложение не даёт войти в
  `MainWindow` (кроме, возможно, первых секунд ретраев), показывает понятную
  ошибку, не предлагает "поработать офлайн".
- Отключение сети **во время** активной обработки видео → обработка
  завершается штатно (текущее поведение через `results_saved`/таймаут 5 мин
  сохраняется), процесс не обрывается на середине.
- Не осталось нигде в коде/UI/документации утверждения, что приложение может
  штатно работать сутками/днями без связи с сервером лицензий.

## Задача 3 — Подготовка к билду и починка сборочных скриптов

### 3.1. Ревизия `signer.spec`
- После реорганизации (Задача 1) убедись, что все относительные пути
  (`'assets'`, `'CNN_side'`, `'lane_guidance_models'`, `'small_models'`,
  `'sings'`, `'sings_text'`, `'static'`, `'templates'`,
  `'configs/data/signs.json'`, `'version.json'`, `'installer/7z.exe'`,
  `'installer/7z.dll'`) по-прежнему верны.
- Проверь секцию `hiddenimports` — она перечисляет `app`, `app.version`,
  `app.utils`, `updater`, `updater.updater`, `updater.updater_main`,
  `ui.widgets.update_worker`, `ui.widgets.update_dialog`. Добавь туда же
  явные `licensing`, `licensing.license_manager`, `licensing.license_client`,
  `licensing.device_fingerprint`, `licensing.public_key`,
  `ui.widgets.license_dialog` — PyInstaller иногда не подхватывает такие
  модули статическим анализом, если импорт лениво идёт из `main.py` внутри
  функции.
- Секция PyArmor-runtime (`build/obfuscated/**/pyarmor_runtime_*`) —
  проверь, что она по-прежнему актуальна после реорганизации; путь
  `build/obfuscated` не должен был измениться, но перепроверь, что
  `scripts/build/obfuscate_licensing.py` копирует **актуальный** набор
  файлов (`main.py`, `licensing/`, `ui/widgets/license_dialog.py`) — с учётом
  того, что после Задачи 2 в `main.py` появится новый блок проверки лицензии,
  он тоже должен войти в обфускацию.

### 3.2. Ревизия `scripts/build/prepare_release.bat`
- После переноса dev/test-скриптов (Задача 1) убедись, что скрипт по-прежнему
  находит `installer\7z.exe`, `signer.spec`, `updater.spec`,
  `scripts\build\obfuscate_licensing.py` относительно корня.
- Шаг `[0/5]` (проверка `build_config.json`) — уже требует реального URL и
  ругается на плейсхолдеры `https://license.signer-prime.com` и
  `https://your-license-server.run.app`. Добавь туда же проверку, что текущий
  задеплоенный URL (`configs/settings.py::license_server_url`) **совпадает**
  с указанным в `build_config.json`, либо явно предупреди в консоли, если
  они различаются — чтобы не собрать релиз, который стучится не туда.
- Нумерация шагов в файле частично сбита (встречаются `[1/5]` рядом с
  `[2.5/6]`, `[3/6]` и т.д. — остатки правок разных промптов). Приведи
  нумерацию к единому сквозному виду (`[1/7]`…`[7/7]`) без дублей и разрывов.
- Убедись, что шаг обфускации (`[2.5/6]` сейчас) корректно откатывается на
  сборку из необфусцированных исходников, если PyArmor не установлен —
  логика `SKIP_OBFUSCATION` уже есть, просто перепроверь после правок
  нумерации, что переменная `SKIP_OBFUSCATION` не потерялась.
- После правок прогони скрипт в режиме "сухого прогона" (можно временно
  закомментировать реальный `pyinstaller`/`7z` вызовы или просто пройтись
  по нему глазами построчно) и убедись, что каждый файл, на который есть
  ссылка (`docs\release_notes.txt`, `docs\BUILD_AUTOUPDATE.md`), существует
  по новому пути документации из Задачи 1.

### 3.3. `installer/SignerInstaller.iss`
- `#define RELEASE_TAG "v2.0.0"` и `#define SIGNER_PART_COUNT 41` — сверь с
  `version.json` (сейчас `"version": "2.0.0"`) и с реальным количеством
  частей в последнем опубликованном релизе на GitHub. Если версия/число
  частей разошлись — актуализируй оба значения и список `[Files]`
  (`Signer.7z.001` … `Signer.7z.0NN`) так, чтобы он строго соответствовал
  `SIGNER_PART_COUNT`.
- Убедись, что `RequiredSpaceMB` (в `[Code]`) и `ExtraDiskSpaceRequired` (в
  `[Setup]`) синхронизированы, как уже указано в комментарии рядом с
  `ExtraDiskSpaceRequired`.

### 3.4. `updater.spec`
- После Задачи 1 проверь, что `hiddenimports` (`'psutil'`, `'app.version'`) и
  `excludes` по-прежнему актуальны — `updater/updater_main.py` не должен
  тянуть тяжёлые зависимости (`torch`, `cv2`, `PyQt6` и т.д., уже в
  `excludes`).

### 3.5. Финальный чек-лист перед первым билдом после этих правок
1. `pip install -r requirements.txt -r requirements-dev.txt` в чистом venv.
2. `pytest tests/ -v` — зелёный.
3. `python scripts/dev/...` (перенесённые проверочные скрипты, если
   сохраняешь их полезность) либо `python test_fixes.py`-эквивалент из
   нового расположения — зелёный.
4. Ручной прогон `main.py` с выключенным интернетом при старте → должен
   показать блокирующий диалог, не открывать `MainWindow` (проверка Задачи 2).
5. Ручной прогон `main.py` с включённым интернетом и действующей активной
   лицензией на этом устройстве → приложение запускается как обычно.
6. `scripts\build\prepare_release.bat` — проходит все шаги без ошибок,
   `release\` содержит архив, чексуммы, release notes.
7. Установка через собранный `SignerInstaller.exe` на чистой машине —
   Signer запускается, лицензия проверяется.

## Общие правила для агента
- Не трогай серверную часть (`signer-license-server/`) — она уже развёрнута
  и работает, менять её не нужно и рискованно.
- Не меняй бизнес-логику детекции знаков (`core/`, `processing/`) — вне
  скоупа этой задачи.
- Все новые/изменённые тексты в UI и логах — на русском, в стиле уже
  существующих сообщений проекта.
- Каждое перемещение файла сопровождай обновлением всех мест, где на него
  ссылаются по строковому пути (импорты Python обычно переживут перенос
  автоматически через `git mv` + правку `import`, но текстовые пути в `.bat`,
  `.spec`, markdown-ссылках, `open("...")` в тестах — нет; их нужно искать
  через `grep -rn` по всему репозиторию и поправлять вручную).
- Коммить порциями по задачам (1 → 2 → 3), чтобы откат в случае проблемы был
  простым.
