## 1. P0 — КРИТИЧЕСКИЕ БЛОКЕРЫ (функциональность физически не работает)

### 1.1. Карта не запускается вообще — `ImportError` в `server/map_server.py`

**Файл**: `server/map_server.py`, самое начало файла (импорты).

**Текущий код**:
```python
from configs.sign_data import (
    TYPE_SIGNS_WITH_TEXT as type_signs_with_text,
    CODES_SIGNS as codes_signs,
    SIGNS_WITH_VARIOUS_TEXT as signs_with_various_text,
    TYPE_SIGNS_CITY as type_signs_city,
)
```

**Проблема**: в `configs/sign_data.py` НЕТ константы `SIGNS_WITH_VARIOUS_TEXT`. Там
объявлена `SIGNS_WITH_TEXT` (раздел "Знаки с текстом"). Это опечатка, допущенная при
рефакторинге BLOCK P.2 (переход с легаси-шима `sign_config.py` на прямой импорт из
`sign_data.py`, см. `CHANGELOG.md` → "P.2 — Прямые импорты из sign_data / sign_models").
Легаси-шим `configs/sign_config.py` корректно алиасит `SIGNS_WITH_TEXT as
signs_with_various_text` — но `map_server.py` от него отказался и попытался
самостоятельно повторить это имя, ошибившись.

**Последствие**: любой импорт `server.map_server` (а он происходит при каждом старте
Flask-сервера карты, см. `ServerThread.run()` → `from server.map_server import run`)
падает с `ImportError`. Исключение ловится в `try/except` внутри `ServerThread.run()`
и превращается в сигнал `error`, который `MapPage._on_server_error()` показывает как
"Ошибка сервера: cannot import name 'SIGNS_WITH_VARIOUS_TEXT' from 'configs.sign_data'".
**Раздел "Карта" в приложении не работает НИ В ОДНОМ режиме** — ни во время обработки,
ни после неё, ни через "В браузере".

**Как проверить, что баг есть** (до фикса):
```bash
python3 -c "import server.map_server"
# ImportError: cannot import name 'SIGNS_WITH_VARIOUS_TEXT' from 'configs.sign_data'
```

**Fix**:
```python
from configs.sign_data import (
    TYPE_SIGNS_WITH_TEXT as type_signs_with_text,
    CODES_SIGNS as codes_signs,
    SIGNS_WITH_TEXT as signs_with_various_text,   # было SIGNS_WITH_VARIOUS_TEXT
    TYPE_SIGNS_CITY as type_signs_city,
)
```
Больше нигде переименовывать не нужно — все дальнейшие использования
`signs_with_various_text` внутри `map_server.py` (в `_sign_img_path` /
`_render_text_sign`) уже написаны в расчёте на правильную семантику
("список типов знаков, у которых бывает произвольный текст на табличке").

**Как проверить, что баг исправлен**:
```bash
python3 -c "import server.map_server; print('OK')"
```
Затем end-to-end: запустить приложение, нажать "Начать обработку" (или просто открыть
вкладку "Карта" после того как `PATH_TO_GEOJSON` существует) — карта должна
загрузиться, а не показывать "Ошибка сервера".

### 1.2. Pipeline-режим с OCR через QThread не запускается — `ImportError` в `processing/ocr_worker.py`

**Файл**: `processing/ocr_worker.py`, импорты в начале файла.

**Текущий код**:
```python
from configs.sign_config import TYPE_SIGNS_WITH_TEXT, NAME_SIGNS_CITY
```

**Проблема**: `configs/sign_config.py` — легаси-шим, который реэкспортирует константы
из `sign_data.py` **под ДРУГИМИ (строчными) именами**:
```python
TYPE_SIGNS_WITH_TEXT as type_signs_with_text,
NAME_SIGNS_CITY      as name_signs_city,
```
Он НЕ содержит имён `TYPE_SIGNS_WITH_TEXT` / `NAME_SIGNS_CITY` в верхнем регистре —
`from module import X as Y` в Python создаёт в пространстве имён модуля только `Y`, не
`X`. Импорт в `ocr_worker.py` пытается взять из `sign_config` символы, которых там
физически нет.

Показательно, что "правильный" аналог этого файла — `processing/ocr_pool.py` (тот же
OCR, но через ProcessPool вместо QThread) — импортирует верно:
```python
from configs.sign_data import TYPE_SIGNS_WITH_TEXT, NAME_SIGNS_CITY
```
т.е. это чисто механическая рассинхронизация двух параллельных модулей после
BLOCK P.2/CPU-4.

**Последствие**: `ocr_worker.py` импортируется лениво внутри
`DetectorThread.run()` только при условии
`processing_mode == "pipeline" AND ocr_use_process_pool == False`
(галка "OCR в отдельном процессе" в Settings выключена — сейчас это НЕ дефолтное
значение, `ocr_use_process_pool: bool = True` в `AppSettings`, но переключатель есть в
UI и пользователь может его выключить, ожидая рабочий CPU-режим "Pipeline + OCR в
QThread"). Этот импорт обёрнут в `try/except` в `DetectorThread.run()`, поэтому
пользователь не увидит трассировку, а просто получит:
`Ошибка загрузки моделей: cannot import name 'TYPE_SIGNS_WITH_TEXT' from
'configs.sign_config'`, и обработка не стартует вообще.

**Как проверить, что баг есть**:
```bash
python3 -c "from configs.sign_config import TYPE_SIGNS_WITH_TEXT, NAME_SIGNS_CITY"
# ImportError: cannot import name 'TYPE_SIGNS_WITH_TEXT' from 'configs.sign_config'
```

**Fix** (просто выровнять с `ocr_pool.py`):
```python
from configs.sign_data import TYPE_SIGNS_WITH_TEXT, NAME_SIGNS_CITY
```

**Как проверить, что баг исправлен**:
```bash
python3 -c "import processing.ocr_worker; print('OK')"
```
Затем end-to-end: Settings → Многопоточность → "Режим обработки" = Pipeline,
"OCR в отдельном процессе" = выключено → запустить обработку короткого видео с
табличками (знаки из `TYPE_SIGNS_WITH_TEXT`, например `3.24`) — обработка должна
стартовать и распознавать текст на знаках, а не падать на загрузке моделей.

## 2. P1 — ОБРАБОТКА ЛОМАЕТСЯ ПРИ ШТАТНОЙ РАБОТЕ (напрямую связано с CPU-режимами)

### 2.1. Пороги трекинга `SignHandler` рассинхронизированы с адаптивным frame-skip `DetectorThread` (BLOCK CPU-1/CPU-2)

Это САМЫЙ важный содержательный баг в этом промпте — он объясняет исторические жалобы
на дубли/потерянные знаки (см. `CHANGELOG.md`, `BLOCK_M_Q_EXECUTION_REPORT.md`,
множественные упоминания "BLOCK DEDUP-FIX", "PROMPT_FIX_DUPLICATE_SIGNS_AND_GPS
_CONFIDENCE.md" в комментариях кода) и **уже зафиксирован как TODO прямо в исходниках**,
но никогда не был реализован:

```python
# processing/detector_thread.py, DetectorThread._calc_skip_interval()
#
# TODO (BLOCK DEDUP-FIX-PART1-STEP2): После подтверждения гипотезы
# инструментацией (см. DEDUP_FIX_STATUS.md), прокинуть эффективный skip
# в config или SignHandler:
#
#     config.CURRENT_EFFECTIVE_SKIP = config.FRAME_STEP * final_skip
#
# Это позволит SignHandler адаптировать пороги gap (сейчас жёстко 7)
# и DIFF_FRAMES_REMOVE (сейчас жёстко 5) к реальному интервалу между
# обработанными кадрами, который может достигать 25 (5×5).
```

**Механизм проблемы**

1. `VideoReaderThread` уже прореживает поток кадров: в очередь кладётся только
   каждый `config.FRAME_STEP`-й кадр (по умолчанию 5, `AppSettings.frame_step_mode
   == "auto"` → `ProcessingController._reset_config()` жёстко ставит `FRAME_STEP = 5`;
   в ручном режиме `frame_step_manual` можно выставить от 1 до **60** через
   Settings UI).
2. Поверх этого `DetectorThread` (это единственный воркер для `processing_mode ==
   "single_thread"` **и** `"pipeline"` — двух из трёх режимов, при этом
   `"single_thread"` явно рекомендован в тултипе UI как лучший для CPU: "⚡ Для CPU
   всегда выбирайте 'Один поток'") ДОПОЛНИТЕЛЬНО прореживает уже прореженный поток
   через `_calc_skip_interval(speed)` — адаптивный CPU-optimization механизм
   (`SKIP_INTERVALS`), пропускающий детекцию (`_should_process_frame()` возвращает
   `False`) на части кадров в зависимости от скорости движения и недавней активности.
3. `SignHandler` (в `core/sign_handler.py`) при этом использует ЖЁСТКО ЗАШИТЫЕ пороги
   в терминах разницы номеров кадров (`frame_number`, локальный номер внутри видео):
   - `_match_evidences`: `if gap < 7: sign.append(det)` — жёсткое число `7`;
   - `DIFF_FRAMES_REMOVE = 5` — через сколько кадров удалять "потерянный" знак;
   - `DIFF_FRAMES_MOVE = 5` — через сколько кадров финализировать знак.

   Эти пороги были откалиброваны в расчёте на то, что между двумя ОБРАБОТАННЫМИ кадрами
   проходит около 5 "сырых" кадров (т.е. ровно `FRAME_STEP`, без учёта
   `DetectorThread`-скипа).

**Численное подтверждение** (см. проверку ниже — пересчитано напрямую по формулам
из `detector_thread.py`):

| Скорость движения | `_current_skip` (адаптивный) | Итоговый разрыв (`FRAME_STEP=5 × skip`) | Порог `gap<7` |
|---|---|---|---|
| ~0 км/ч  | 1.0 | ≈5  | ok |
| ~30 км/ч | 1.5 | ≈8  | **нарушен** |
| ~60 км/ч | 2.5 | ≈12 | **нарушен** |
| ~90 км/ч | 3.5 | ≈18 | **нарушен** |
| ~120 км/ч| 4.5 | ≈22 | **нарушен** |

Т.е. уже на городской скорости 30 км/ч (а не только на трассе) фактический разрыв
между обработанными кадрами превышает порог, заложенный в `_match_evidences`. При
`frame_step_manual` > 6 (разрешено UI-спинбоксом вплоть до 60) порог нарушается
ПОСТОЯННО, независимо от скорости, даже при `_current_skip == 1`.

**Почему это не "падение до нуля знаков", но реальная деградация качества**: строгая
проверка `gap < 7` в `_match_evidences` — это первичный, "безопасный" матчинг с учётом
давности. Когда она проваливается, в дело вступает `_attach_unmatched()` — вторичный
фолбэк, который пересчитывает то же самое сырое пиксельное расстояние БЕЗ учёта
давности (`gap`) вообще. На практике это означает, что при разрыве >7 кадров трекинг
почти целиком держится на этом "запасном" пути, у которого нет вообще никакой защиты
от давности — а значит и сам смысл порога `gap<7` как "не путать с другим объектом,
если слишком много времени прошло" полностью теряется на типичной скорости движения.
А `DIFF_FRAMES_REMOVE = 5` в `_remove_lost_signs()` продолжает работать буквально:
если знак НЕ был обновлён в текущем обработанном кадре (ни через основной, ни через
запасной путь — например, из-за временной неверной YOLO-классификации на один кадр,
или потому что пиксельное смещение за 20+ реальных кадров превысило допуски), он
считается "потерянным" уже через один пропущенный цикл обработки и удаляется, если
успел накопить <4 наблюдений (`MIN_OBSERVATIONS`). Итог — фрагментированные /
задвоенные треки именно в сложных случаях (частичная окклюзия, погранично низкая
уверенность CNN на один кадр, резкое приближение), что и приводит к наблюдаемым
"дублям знаков" — именно той проблеме, которой посвящены исторические
BLOCK-DEDUP-исправления в проекте.

**Ирония**: единственный режим обработки, который НЕ подвержен этой рассинхронизации —
`process_pool` (`DetectorProcessPool` / `ResultAggregatorThread` в
`processing/detector_process_pool.py`), потому что там нет адаптивного skip вообще —
обрабатывается КАЖДЫЙ кадр, дошедший из `VideoReaderThread` (т.е. разрыв всегда ровно
`FRAME_STEP`). А именно `process_pool` в тултипах Settings прямо назван МЕДЛЕННЫМ на
CPU и не рекомендован к использованию.

**Как проверить, что баг есть**: запусти
```bash
python3 - << 'EOF'
FRAME_STEP = 5
SKIP_INTERVALS = {0:(1,1), 30:(1,2), 60:(2,3), 90:(3,4), 120:(4,5)}
for speed,(lo,hi) in SKIP_INTERVALS.items():
    avg_skip = (lo+hi)/2
    gap = FRAME_STEP*avg_skip
    print(speed, "km/h ->", gap, "кадров ->", "НАРУШЕН" if gap>=7 else "ok")
EOF
```
Либо: `--frame-step` через ручной режим Settings > 6 и обработать тестовое видео,
сравнить число уникальных физических знаков "на глаз" в видео с числом фичей в
итоговом GeoJSON — при этом баге их будет заметно больше (дубли) либо часть реальных
знаков вообще не попадёт в результат (обрезанные короткие треки < MIN_OBSERVATIONS).

**Fix (конкретный, минимально инвазивный дизайн)**

Шаг 1. `configs/config.py` — добавить глобальную переменную (ровно то, что предлагает
существующий TODO):
```python
# ── Многопоточность ───────────────────────────────────────────────
...
# BLOCK FIX-2.1: реальный интервал (в кадрах) между двумя ОБРАБОТАННЫМИ кадрами,
# = FRAME_STEP * текущий адаптивный skip DetectorThread. Обновляется из
# DetectorThread на каждой итерации цикла. SignHandler использует это значение,
# чтобы адаптировать пороги давности трека к реальному интервалу между
# кадрами, а не к жёстко зашитым числам, рассчитанным на FRAME_STEP=5, skip=1.
CURRENT_EFFECTIVE_SKIP: int = 1
```

Шаг 2. `processing/detector_thread.py`, в `_process_loop()`, сразу после строки
`self._current_skip = self._calc_skip_interval(speed)` добавить:
```python
config.CURRENT_EFFECTIVE_SKIP = self._current_skip
```
(Для `process_pool`-режима трогать не нужно — там `CURRENT_EFFECTIVE_SKIP` останется
равным дефолтному `1`, что и корректно, т.к. там нет доп. пропуска кадров.)

Шаг 3. `core/sign_handler.py` — заменить жёстко зашитые пороги на функцию, учитывающую
`config.FRAME_STEP * config.CURRENT_EFFECTIVE_SKIP`:
```python
# Было (класс SignHandler):
DIFF_FRAMES_REMOVE       = 5     # через сколько кадров удалять потерянный знак
DIFF_FRAMES_MOVE         = 5     # через сколько кадров финализировать знак
...
# базовое (нижняя граница) значение, ниже которого пороги никогда не опускаются —
# сохраняем прежнее поведение для FRAME_STEP=5/skip=1
BASE_MATCH_GAP_FRAMES    = 7     # было хардкод `7` внутри _match_evidences
SAFETY_MULTIPLIER        = 1.5   # запас поверх реального интервала между кадрами
MAX_MATCH_GAP_FRAMES     = 120   # защитный потолок, чтобы не потерять контроль
                                  # над давностью совсем (напр. при stationary после
                                  # долгого движения) — знак старше этого гарантированно
                                  # считается новым объектом

def _effective_gap_frames(self) -> int:
    """
    BLOCK FIX-2.1: реальный ожидаемый интервал (в номерах кадров внутри видео)
    между двумя ПОСЛЕДОВАТЕЛЬНО ОБРАБОТАННЫМИ кадрами, с учётом текущего
    адаптивного frame-skip DetectorThread (BLOCK CPU-1/CPU-2). Без этого пороги
    ниже (используемые для матчинга и удаления "потерянных" знаков) были
    откалиброваны только на FRAME_STEP=5/skip=1 и систематически нарушались уже
    на скорости ~30 км/ч (см. AGENT_FIX_PROMPT, раздел 2.1).
    """
    step = max(1, int(config.FRAME_STEP))
    skip = max(1, int(config.CURRENT_EFFECTIVE_SKIP))
    effective = step * skip
    gap = max(self.BASE_MATCH_GAP_FRAMES, int(effective * self.SAFETY_MULTIPLIER))
    return min(gap, self.MAX_MATCH_GAP_FRAMES)
```

Шаг 4. Заменить использования:
- в `_match_evidences`: `if gap < 7:` → `if gap < self._effective_gap_frames():`
- в `_remove_lost_signs`: `current_frame - s.frame_numbers[-1] > self.DIFF_FRAMES_REMOVE`
  → `current_frame - s.frame_numbers[-1] > self._effective_gap_frames()`
- в `_finalize_signs`: `current_frame - sign.frame_numbers[-1] >= self.DIFF_FRAMES_MOVE`
  → `current_frame - sign.frame_numbers[-1] >= self._effective_gap_frames()`

  (Можно оставить `DIFF_FRAMES_MOVE`/`DIFF_FRAMES_REMOVE` как публичные атрибуты класса
  для обратной совместимости, если их читает UI/другой код — проверь через
  `grep -rn "DIFF_FRAMES_REMOVE\|DIFF_FRAMES_MOVE" --include="*.py" .` — но саму логику
  веди через `_effective_gap_frames()`.)

Шаг 5. **Не трогай** `MAX_PIXEL_DISTANCE=800` и `delta_h > 10` в `_calc_evidence_matrix`
в рамках этого фикса — это отдельная, более рискованная эвристика (нелинейно зависит от
геометрии кадра и скорости приближения объекта, а не только от числа пропущенных
кадров). Она вынесена ниже отдельным пунктом (2.2) только там, где риск ложного
матчинга прямо ведёт к порче данных (см. ниже), а здесь трогать не нужно, чтобы не
сломать что-то ещё непроверенным изменением.

**Как проверить, что баг исправлен**:
1. Юнит-тест (добавь новый файл `test_sign_handler_gap.py` по аналогии с уже

### 2.2. Тот же корень проблемы в `Detector.detect_with_tracking` — фиксированный радиус 50px (BLOCK CPU-3/CPU-4)

**Файл**: `core/detector.py`, метод `Detector.detect_with_tracking()`.

**Проблема**: этот метод (используется ТОЛЬКО в `single_thread`/`pipeline` через
`DetectorThread`, т.е. в тех же CPU-оптимизированных режимах, что и раздел 2.1)
пытается пропустить повторный вызов CNN-классификации, если рядом (в пределах
фиксированных **50 пикселей**) уже есть `TrackedSign` со "стабильным" классом — это
BLOCK CPU-3. Тот же радиус в 50px используется чуть ниже ещё раз — для решения,
нужно ли повторно запускать OCR (BLOCK CPU-4):
```python
for (tracked_x, tracked_y), tracked_sign in tracked_signs.items():
    if abs(center[0] - tracked_x) < 50 and abs(center[1] - tracked_y) < 50:
        stable_class = tracked_sign.get_stable_cnn_class()
        ...
```
и повторно:
```python
for (tracked_x, tracked_y), tracked_sign in tracked_signs.items():
    if abs(center[0] - tracked_x) < 50 and abs(center[1] - tracked_y) < 50:
        ...
```

**Почему это опаснее, чем раздел 2.1**: там речь шла о фрагментации/дублях (плохо, но
не молча портит данные). Здесь же, если при большом разрыве между кадрами (см. таблицу
в 2.1 — до 20+ кадров) НОВАЯ детекция физически оказалась в пределах 50px от СТАРОЙ
позиции ДРУГОГО, соседнего знака (два знака рядом на одном столбе/группе — обычное
дело для табличек-указателей направления, `NAMES_SIGNS_FOR_SIDE` и подобных), метод
подставит `stable_cnn_class` от ЧУЖОГО знака вместо реального запуска CNN — т.е.
**молча присвоит неверный тип знака**, а не просто создаст лишний трек. Чем больше
реальный разрыв между кадрами (высокая скорость / большой `FRAME_STEP` /
`skip`), тем больше типичное смещение знака в кадре между двумя обработанными
кадрами — а порог остаётся неизменным (50px), т.е. риск ложного совпадения растёт
именно тогда, когда CPU-оптимизации наиболее агрессивны.

**Fix**: масштабировать радиус тем же коэффициентом, что и в разделе 2.1, с разумным
потолком (не давать радиусу расти бесконтрольно):
```python
# В начале Detector.detect_with_tracking(), один раз на вызов:
from configs import config
_skip_factor = max(1, int(config.CURRENT_EFFECTIVE_SKIP))
tracking_radius_px = min(50 * _skip_factor, 220)  # потолок — не даём радиусу
                                                    # расти бесконтрольно и
                                                    # склеивать соседние знаки
```
и заменить оба места `< 50` на `< tracking_radius_px`.

Не пытайся связать это с реальной геометрией/перспективой камеры (расчёт "настоящего"
углового смещения) — это отдельная, более сложная задача. Достаточно того, чтобы порог
рос вместе с реальным межкадровым интервалом линейно, с потолком.

**Как проверить**: юнит-тест на `Detector.detect_with_tracking` с двумя близко
расположенными (по X) `tracked_signs` разных типов и синтетическим `raw_boxes` рядом
с одним из них при `config.CURRENT_EFFECTIVE_SKIP` от 1 до 5 — убедиться, что при
`skip=1` поведение не изменилось (радиус == 50), а при `skip=5` вызывается реальный
CNN, а не подставляется класс соседнего знака, если расстояние больше нового
масштабированного порога.

## 3. P2 — ТОЧНОСТЬ GPS/АЗИМУТА И СОГЛАСОВАННОСТЬ CPU-BACKEND'ОВ

### 3.1. `video_reader.py`: хардкод "60 кадров на GPS-точку" вместо реального FPS

**Файл**: `processing/video_reader.py`, метод `_read_all_videos()`.

```python
gps_index  = int(round(abs_frame / config.VIDEO_FPS, 0))  # BLOCK J.2: используем реальный FPS
...
if (abs_frame - gps_index * 60) > 60:
    gps_index += 1
```

Начальное значение `gps_index` уже корректно учитывает реальный FPS (`config.VIDEO_FPS`,
BLOCK J.2), но приращение внутри цикла чтения кадров использует **захардкоженное
число `60`**, а не `config.VIDEO_FPS`. Это прямое противоречие в рамках одной и той же
функции: одна строка "по-новому" (через реальный FPS), следующая — "по-старому"
(магическое число). Для видео с GoPro (~59.94 fps, см. `video_debug.log` в проекте)
разница минимальна и на практике почти не заметна, но для любого источника с
существенно отличным FPS (30fps экшн-камера, смартфон) `gps_index` будет накопительно
уходить от реального положения — а от него зависит и `speed = self._gpx.get_speed(...)`,
используемая в `DetectorThread` для принятия решения "обрабатывать кадр вообще или
нет" (`MIN_SPEED_KMH`) и для адаптивного frame-skip (раздел 2.1!) — т.е. этот баг
косвенно усиливает баг 2.1 на нестандартных источниках видео.

**Fix**:
```python
if (abs_frame - gps_index * 60) > 60:
```
заменить на
```python
if (abs_frame - gps_index * config.VIDEO_FPS) > config.VIDEO_FPS:
```
(число точек GPS "примерно раз в секунду" остаётся тем же по смыслу, просто явно
привязано к реальному FPS, а не к предположению "60 fps == 1 точка/сек").

**Как проверить**: юнит-тест на `_read_all_videos`-подобную логику (или отдельная
чистая функция, если решишь вынести приращение gps_index в тестируемый хелпер) при
`config.VIDEO_FPS = 30.0` — `gps_index` должен расти вдвое быстрее относительно
`abs_frame`, чем при 60 fps.

### 3.2. `SignHandler._update_azimuths` игнорирует интерполяцию/сглаживание курса (BLOCK J.1/J.3)

**Файл**: `core/sign_handler.py`, метод `_update_azimuths`:
```python
def _update_azimuths(self, current_frame: int) -> None:
    for sign in self.signs:
        if sign.frame_numbers[-1] == current_frame:
            sign.azimuth = self._gpx.get_azimuth(config.INDEX_OF_GPS + 1)
```

Использует "сырой" курс через глобальный `config.INDEX_OF_GPS` и метод
`GPXHandler.get_azimuth()`, который берёт курс из точки трека БЕЗ интерполяции по
реальному кадру и БЕЗ сглаживания (`_smooth_course`, BLOCK J.3 — скользящее окно,
угловое усреднение sin/cos). При этом `DetectorThread._build_detected()` для
координат УЖЕ использует правильный, более точный путь —
`self._gpx.get_interpolated(raw.abs_frame_number, config.VIDEO_FPS)` (BLOCK J.2), но
для АЗИМУТА, который проставляется отдельно в `SignHandler._update_azimuths`, эта
интерполяция не используется вовсе.

Итог: азимут знака (используется и в геометрии линии в `coordinate_calculation.py`, и
в метрике уверенности `conf_placement` через `azimuth_delta` в `sign.calc_confidence`)
может быть более "дёрганым"/менее точным, чем задумано улучшениями BLOCK J.1/J.3,
несмотря на то, что вся инфраструктура для точного расчёта уже реализована и просто не
подключена в этом месте.

**Fix**:
```python
def _update_azimuths(self, current_frame: int) -> None:
    for sign in self.signs:
        if sign.frame_numbers[-1] == current_frame:
            # BLOCK FIX-3.2: используем интерполированный/сглаженный курс
            # (BLOCK J.1/J.3) вместо сырой точки по INDEX_OF_GPS, как это уже
            # сделано для координат в DetectorThread._build_detected().
            point = self._gpx.get_interpolated(current_frame, config.VIDEO_FPS)
            if point is not None:
                sign.azimuth = point.course
            else:
                sign.azimuth = self._gpx.get_azimuth(config.INDEX_OF_GPS + 1)
```
Обрати внимание: `current_frame` здесь — ЛОКАЛЬНЫЙ номер кадра внутри видео (см.
`check_the_data_to_add`: `current_frame = detections[0].frame_number`), а
`get_interpolated()` ожидает АБСОЛЮТНЫЙ номер кадра (`abs_frame`). Перед фиксом
проверь, доступен ли в `SignHandler` абсолютный номер кадра в момент вызова
`_update_azimuths` (есть `config.INDEX_OF_All_FRAME`, обновляемый и в
`DetectorThread._process_loop`, и в `ResultAggregatorThread._process_result`) — скорее
всего нужно передавать/использовать именно его, а не локальный `current_frame`.
Сверь на реальных данных (лог `abs_frame` vs `frame_number`), не полагайся только на
это описание.

**Как проверить**: сравнить значения `sign.azimuth` в итоговом GeoJSON (`properties.
azimuth`) до/после фикса на одном и том же тестовом видео — после фикса значения
должны быть более гладкими (меньше резких скачков между соседними по времени знаками
на прямом участке дороги).

### 3.3. `process_pool`-режим: полное дублирование моделей + EasyOCR на каждый воркер-процесс

**Файл**: `processing/detector_process_pool.py`, `_worker_process_frame()`.

Каждый воркер-процесс пула (по умолчанию `cpu_count - 1`, т.е. может быть 4–15+
процессов) создаёт СОБСТВЕННЫЙ полный `Detector()`, который лениво грузит: основную
detect-модель, rube-модель, ~10 classify-моделей `model_dict`, 3 суб-модели
`sub_models`, 2 lane-модели — и, если в кадре встретится знак с текстом,
ДОПОЛНИТЕЛЬНО собственный экземпляр `EasyOCR` (через `core.detector._get_ocr()`,
вызываемый изнутри `Detector.detect()`, который используется в
`_worker_process_frame` вместо `detect_with_tracking`). При 8 воркерах это 8 полных
копий всего модельного стека в памяти одновременно — это уже задокументировано как
причина, по которой `process_pool` медленнее на CPU, чем `single_thread`
(см. тултип в `settings_page.py`: "⚠️ Медленнее на CPU из-за overhead!"), но сам факт
дублирования EasyOCR (самая тяжёлая по памяти модель из всех) в каждом воркере нигде
явно не устранён и не описан как компромисс.

**Что сделать (в порядке возрастания риска — выбери то, что уместится в бюджет
задачи)**:
1. **Минимум**: явно предупреждать пользователя в UI/логах, если он выбирает
   `process_pool` при `use_cuda=False` — например, лог-warning при старте
   `ProcessingController.start()` вида "Process Pool на CPU: каждый из N воркеров
   загрузит собственную копию всех моделей (~X ГБ каждая). Рекомендуется 'Один поток'
   для CPU." Это не требует изменения логики, только явной коммуникации риска.
2. **Средне**: вынести OCR из `_worker_process_frame` в отдельный `OCRPool` (уже
   существует, используется в pipeline-режиме через `processing/ocr_pool.py`) —
   т.е. `_worker_process_frame` должен звать `detector.detect(image, skip_ocr=True)`,
   а OCR-детекции агрегировать и раздавать через общий `OCRPool` с малым
   фиксированным числом воркеров (1–2), как это уже устроено в pipeline-режиме.
   Это требует протянуть `OCRPool` из `ProcessingController`/`DetectorProcessPool` в
   `ResultAggregatorThread`, аналогично тому, как туда уже протянуты `SignHandler`/
   `GPXHandler` (см. `Fix 1.2` в существующих комментариях кода). **Не делай это,
   если не уверен, что успеешь протестировать** — здесь легко сломать поток данных
   между процессами (сериализация через `ProcessPoolExecutor`).
3. **Не делай** в рамках этого промпта: снижение дефолтного числа воркеров или смену
   архитектуры на shared-memory модели — это отдельная, более крупная задача.

Отметь явно в отчёте, какой из вариантов был реализован (или что реализован только
п.1 как минимально рискованный).

## 7. Что НЕ трогать в рамках этого промпта

- Не меняй `MAX_PIXEL_DISTANCE=800` и `delta_h > 10` в `SignHandler._calc_evidence_matrix`
  — риск непредсказуемых побочных эффектов без реальных данных для калибровки.
- Не переписывай двухуровневую схему матчинга (`_match_evidences` +
  `_attach_unmatched`) на что-то принципиально новое — только пороги внутри
  существующей схемы (раздел 2.1).
- Не трогай `configs/sign_data.py::CODES_SIGNS` — проверено скриптом-аналогом
  `check_sign_data_duplicates.py`, дублирующихся ключей в предоставленном снепшоте
  не найдено; трогать эти данные без отдельного запроса не нужно.
- Не меняй дефолтные значения `AppSettings` (например, `processing_mode`,
  `ocr_use_process_pool`) — фиксы должны работать корректно при ЛЮБых
  пользовательских настройках, а не менять то, что выбрано по умолчанию.
- Не удаляй легаси-шим `configs/sign_config.py` целиком — он всё ещё используется
  (как минимум `map_server.py::api_sign_types()`), только чини конкретные
  неправильные импорты из него/из `sign_data.py`.
