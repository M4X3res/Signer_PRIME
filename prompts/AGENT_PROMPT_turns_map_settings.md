## 0. Как пользоваться этим документом

Ниже четыре независимых, но связанных блока работ:

1. **[КРИТИЧНО] Производительность обработки поворотов** — найдена конкретная причина,

2. **[ВЫСОКИЙ ПРИОРИТЕТ] Определение стороны знака на перекрёстке через подложку** —

**Общее правило работы:** делай маленькие, изолированные коммиты по каждому пункту.
После каждого пункта — прогоняй существующие скрипты проверки, которые уже есть в

## 1. [КРИТИЧНО] Узкое место в обработке поворотов

### 1.1 Контекст

Пользователь жалуется, что обработка "на поворотах" — долгая. Разбор кода показывает,
что проблема не в геометрии/математике поворота (она дешёвая, чистый Python, O(1)–O(n)
на кадр), а в том, **как часто и как дорого перечитывается GPX-трек**.

### 1.2 Корневая причина (проверено по коду)

Файл `core/turn.py`:

```python
class Turn:
    def _gpx(self):
        """GPXHandler — создаётся лениво, всегда внутри QThread."""
        from core.gpx_handler import GPXHandler
        return GPXHandler()          # <-- НОВЫЙ экземпляр КАЖДЫЙ раз

    def _converter(self):
        from core.converter import Converter
        return Converter()           # это не проблема, см. 1.3
```

`GPXHandler.__init__` (`core/gpx_handler.py`) при создании **всегда** синхронно
парсит весь GPX-файл с диска:

```python
def __init__(self):
    self._points: list[GPSPoint] = []
    self._load()                      # gpxpy.parse(...) всего трека

def _load(self) -> None:
    ...
    with open(config.PATH_TO_GPX, "r", encoding="utf-8") as f:
        gpx = gpxpy.parse(f)
    for track in gpx.tracks:
        for segment in track.segments:
            for pt in segment.points:
                self._points.append(GPSPoint(...))
```

Метод `Turn.is_turn()` вызывает `self._gpx()` (то есть создаёт новый `GPXHandler`
и заново парсит весь файл) на **каждый** свой вызов. Методы `append_azimuths`,
`append_coordinates`, `add_points`, `update_sign_distance` делают то же самое.

Теперь смотрим, как часто вызывается `turn.is_turn()` — файл `core/sign_handler.py`,
метод `check_the_data_to_add` (это главный метод трекинга, вызывается на **каждом
обработанном кадре**, где есть хотя бы одна детекция — см. `detector_thread.py:403`
и `detector_pool.py:304`):

```python
def check_the_data_to_add(self, detections, turn):
    if not detections:
        return turn
    ...
    else:
        if turn.was_there_turn and not turn.is_turn():   # вызов #1 (условный)
            turn = self._handle_turn_end(turn, current_frame)
        ...
    ...
    if not turn.is_turn():                                # вызов #2 (почти всегда)
        self._finalize_signs(current_frame)
    ...
```

**Вызов №2 срабатывает на каждом обработанном кадре, где уже трекается хотя бы
один знак** — то есть не только "во время поворота", а на протяжении практически
всего видео (пока в кадре виден любой знак). Каждый такой вызов = полный повторный
парсинг GPX-файла с диска.

Итог: если в видео, скажем, 5000 обработанных кадров с активными знаками и трек на
3000 точек, вы получаете ~5000 полных парсингов XML на 3000 точек **только ради того,
чтобы прочитать один азимут**. Это и есть узкое место — оно физически "размазано"
по всему проходу видео, а не сосредоточено буквально на поворотах, но пользователь
ощущает его как "долго обрабатывается [в местах активности]", потому что именно там
знаки трекаются дольше всего и `is_turn()` дёргается чаще всего.

Тот же баг актуален для `detector_pool.py:277` (`turn = Turn()`) — там используется
тот же класс `Turn`, фикс в `core/turn.py` закроет оба места автоматически.

### 1.3 Что чинить НЕ нужно (проверено, не является проблемой)

- `core/converter.py`: `Converter()` — лёгкий класс без тяжёлого `__init__`,
  трансформеры кешируются на уровне модуля через `@lru_cache(maxsize=16)`
  (`_get_transformer`). Пересоздание `Converter()` на каждый вызов дешёвое.
  Трогать не нужно.
- `coordinate_calculation.py` (`calculation_four_dots`, `get_line`,
  `calculate_result_line`) — чистая математика без I/O, O(1) на знак. Не бутылочное
  горлышко.

### 1.4 Рекомендуемый фикс

**Шаг 1 (обязательный, минимальный, безопасный).** Мемоизировать `GPXHandler`
и (для единообразия) `Converter` на экземпляре `Turn`, вместо создания нового
объекта на каждый вызов:

```python
class Turn:
    def __init__(self):
        ...
        self._gpx_handler = None
        self._converter_instance = None

    def _gpx(self):
        """GPXHandler создаётся один раз за время жизни Turn (внутри QThread)."""
        if self._gpx_handler is None:
            from core.gpx_handler import GPXHandler
            self._gpx_handler = GPXHandler()
        return self._gpx_handler

    def _converter(self):
        if self._converter_instance is None:
            from core.converter import Converter
            self._converter_instance = Converter()
        return self._converter_instance
```

Важно: `Turn()` создаётся один раз на весь `_process_loop()` (см.
`detector_thread.py:320`, `detector_pool.py:277`), а не на каждый кадр — значит,
такой мемоизации достаточно, чтобы файл читался ровно один раз за обработку видео,
а не тысячи раз. Комментарий "создаётся лениво, всегда внутри QThread" в
оригинале сохраняется — просто ленивая инициализация теперь происходит один раз,
а не при каждом обращении.

Проверить, что после фикса `turn.clean()` (вызывается между поворотами) **не**
сбрасывает `self._gpx_handler`/`self._converter_instance` — трек не меняется в
рамках одного видео, пересоздавать эти объекты там не нужно.

**Шаг 2 (желательный, более основательный рефакторинг, если позволяет время).**
`SignHandler.__init__` уже создаёт один `GPXHandler` на весь прогон
(`self._gpx = GPXHandler()`, `sign_handler.py:53`). Сейчас получается, что GPX-трек
физически хранится в памяти дважды — один раз в `SignHandler._gpx`, второй раз (после
шага 1) в `Turn._gpx_handler`. Лучше прокинуть единственный экземпляр `GPXHandler`
(и `Converter`) из `SignHandler` в `Turn` явно (параметром конструктора или сеттером),
чтобы был один источник истины на весь пайплайн. Это не обязательно для устранения
бага производительности (шаг 1 уже его устраняет), но улучшает архитектуру и экономит
память на длинных треках.

**Шаг 3.** В `_handle_turn_end` (`sign_handler.py:382`) при `turn_use_bearing_geometry
= True` метод `turn.handle_turn()` (эвристика `_handle_sign`, назначающая
`sign.number`) всё равно вызывается и тратит CPU, хотя его результат нигде не
используется в bearing-режиме (используется только в `_process_turn_signs_legacy`).
Оберни вызов условием:

```python
from configs.settings import get_app_settings
settings = get_app_settings()
if not settings.turn_use_bearing_geometry:
    turn.handle_turn()
```

Это второстепенная экономия (чистый Python, дёшево), но раз уж чистим этот путь —
логично не считать то, что не используется.

### 1.5 Как измерить эффект (до/после)

В проекте уже есть `core/profiler.py` и в `detector_thread.py` уже обёрнут нужный
участок:

```python
with profiler.measure("sign_handler_tracking"):

```

- Включи `config.ENABLE_PROFILING = True` (см. `configs/config.py`), обработай

- Сравни `TimingStats` для `sign_handler_tracking` (mean/p95/total) — ожидается

- Дополнительно можно временно логировать количество созданий `GPXHandler` (счётчик
  в `__init__`) на прогон — до фикса это будет число, сопоставимое с количеством
  обработанных кадров, после фикса — единицы (1 на `Turn`, плюс 1 в `SignHandler`,
  пока не сделан шаг 2).
- В репозитории есть `benchmark_detector.py` — посмотри, можно ли переиспользовать
  его как основу для регрессионного бенчмарка "обработка ролика с поворотами",
  чтобы зафиксировать цифры до/после в PR.

## 2. [ВЫСОКИЙ ПРИОРИТЕТ] Определение стороны знака на перекрёстке через подложку

### 2.1 Важно: то, о чём просит пользователь, уже частично реализовано

В проекте есть блок с говорящим названием "BLOCK H", который **уже делает именно то,
что предлагает пользователь** — определяет сторону/направление знака на перекрёстке
геометрически через подложку OSM (карту дорожной сети), а не через
эвристику+нейросеть:

- `core/intersection_geometry.py` — `compute_sign_bearing()` (азимут от машины на
  знак с учётом FOV камеры), `raycast_to_ways()` (луч по этому азимуту до пересечения
  с рёбрами OSM-дорог — это и есть "подложка"), `aggregate_observations()`
  (устойчивость к шуму GPS через агрегацию нескольких наблюдений).
- `core/osm_snap.py` — `OSMSnapper` загружает дороги из Overpass API (batch по
  bounding box), кеширует по ячейке сетки.
- `final_handler.py::_process_turn_signs_bearing` — связывает всё вместе, это
  дефолтный путь (`AppSettings.turn_use_bearing_geometry = True`).
- Старый путь — `Turn._handle_sign()` (эвристика по изменению bbox) +
  `CoordinateCalculation.calculation_four_dots()` + Keras-модель
  `sign_classificator` (`configs/sign_models.py`) — остаётся как legacy-фоллбэк
  (`_process_turn_signs_legacy`), переключается флагом в настройках.

**Важная деталь**: Keras-модель `sign_classificator` (та самая "нейросеть", видимо,
имевшаяся в виду в постановке задачи) и методы `Turn.predict_sign_position` /
`Turn.resolve_with_distance` **нигде фактически не вызываются** в текущем пайплайне
(проверено grep по всему проекту) — это мёртвый код, оставшийся от более старой
архитектуры, ещё до появления bearing-подхода. Модель ленивая (`_LazyKeras`), поэтому
не грузится и не тратит время, но она вводит в заблуждение при чтении кода и должна
быть либо удалена, либо явно помечена как deprecated (см. 2.5).

Так что задача не "придумать подложку с нуля", а **довести до продакшн-состояния
уже начатую реализацию** и устранить её слабые места.

### 2.2 Найденные проблемы текущей реализации подложки

1. **Живая зависимость от сети на каждый прогон.** `OSMSnapper._get_ways_bbox` /
   `_get_ways` бьёт в `https://overpass-api.de/api/interpreter` (публичный,
   рейт-лимитируемый сервис) при каждой обработке видео. Есть ретраи
   (`MAX_RETRIES=2`), троттлинг (`MIN_REQUEST_INTERVAL=0.3`), таймаут (`3`–`10` сек
   для bbox-запроса) — но при недоступности/медленном ответе Overpass весь
   bearing-путь **молча** переключается на legacy-эвристику
   (`final_handler.py`, `_process_turn_signs_bearing`: `if not ways: ... return
   self._process_turn_signs_legacy(...)`) без предупреждения пользователю. Это
   значит, что качество определения стороны знака непредсказуемо зависит от того,
   насколько хорошо в момент обработки отвечал сторонний сервис.
2. **Захардкоженная ширина кадра.** В `final_handler.py::_process_turn_signs_bearing`:
   ```python
   frame_width = 1920  # TODO: брать из config/video metadata
   ```
   Если реальное видео снято не в 1920px по ширине, `compute_sign_bearing()`
   получает неверный `frame_width`, что искажает вычисленный азимут на знак и,
   соответственно, может привести к привязке к неверной стороне перекрёстка.
   Это надо чинить в первую очередь — баг тихий и системный, а не только про
   производительность.
3. **Нет локального/офлайн-кеша подложки между прогонами.** Кеш в `OSMSnapper`
   живёт только в памяти процесса (`self._cache`), пропадает при перезапуске.
   Если оператор обрабатывает несколько видео по одному и тому же маршруту (частый
   кейс для дорожной съёмки), Overpass запрашивается заново каждый раз.
4. **Линейный перебор сегментов дорог.** `raycast_to_ways()` и
   `OSMSnapper._find_closest_segment()` перебирают все сегменты всех `ways` в bbox
   линейно на каждый луч/точку. Для больших bbox (длинные маршруты, много перекрёстков)
   это O(знаков × сегментов). Не критично при типичных объёмах, но стоит учитывать,
   если маршруты станут длиннее.
5. **`turn_detection_radius_m`** — параметр объявлен, задокументирован
   ("Радиус вокруг OSM-узла перекрёстка для детекции turn signs"), выведен в
   настройки, но помечен как "пока не используется (зарезервировано)"
   (`settings_page.py:489-495`, контрол `setEnabled(False)`). Либо реализовать его
   заявленное назначение, либо убрать (см. блок 3).
6. **Мёртвый код**, вводящий в заблуждение — см. 2.1 (Keras-классификатор,
   `predict_sign_position`, `resolve_with_distance`, а также `Turn._handle_sign()`
   и производные от него методы `_calc_diff_x/_calc_max_size/_calc_min_size/
   _calc_coeff_frames/_calc_coeff_size`, которые используются **только** legacy-путём).

### 2.3 Рекомендуемое решение — довести подложку до продакшн-качества

Это основной путь, наиболее близко соответствующий формулировке пользователя
("ставить знаки... прямо через подложку"):

**2.3.1. Заменить живой Overpass на локальную/предзагруженную подложку (главное
изменение).** Вместо того чтобы на каждый прогон видео ходить в интернет за OSM
данными, сделать это по-настоящему "подложкой" — то есть статичным слоем,
подготовленным заранее:

- Перед обработкой (или один раз при первой обработке маршрута) выгрузить
  дорожную сеть для bounding box всего GPX-трека **один раз**, сохранить в локальный
  файл (`.geojson`/`.json`) рядом с проектом (например, `<video>_osm_ways_cache.json`).
  Формат — тот же, что уже возвращает `OSMSnapper._parse_ways` (`{"nodes": [...],
  "name": ..., "tags": {...}}`), так что `raycast_to_ways`/`_find_closest_segment`
  менять не придётся, поменяется только источник данных.
- При последующих запусках/переобработках того же маршрута — читать из локального
  файла, в Overpass не ходить вообще (полностью офлайн-режим).
- Добавить настройку (см. блок 3) и/или кнопку в UI (диагностика или карта) —
  "обновить OSM-подложку для этого маршрута" — принудительно перезапросить и
  перезаписать локальный кеш.
- Опционально: разрешить оператору импортировать свой `.osm`/`.geojson`-экстракт
  вручную (для мест без доступа в интернет на месте съёмки/обработки) —
  `OSMSnapper` в таком случае просто не должен обращаться к сети, если локальный
  файл уже есть.
- Такой подход одновременно решает и проблему производительности (нет сетевых
  задержек/ретраев в горячем пути), и проблему надёжности (нет тихого фоллбэка
  из-за недоступности стороннего сервиса), и делает поведение детерминированным
  между прогонами.

**2.3.2. Починить `frame_width`.** Прокинуть реальную ширину кадра из метаданных
видео (см. `video_reader.py` — там наверняка уже есть доступ к разрешению кадра
через OpenCV/`cv2.VideoCapture`) в `TrackedSign` или в `Turn`/`FinalHandler`,
вместо константы `1920`. Как минимум — брать из `config` (завести
`config.FRAME_WIDTH`, заполнять при инициализации чтения видео), как максимум —
хранить per-sign (на случай смешанных источников видео в одном проекте).

**2.3.3. Логировать и делать видимым фоллбэк.** Когда `_process_turn_signs_bearing`
уходит в `_process_turn_signs_legacy` (нет ways, нет lats и т.д.) — это должно быть

### 2.4 Другие варианты, которые тоже стоит рассмотреть

Пользователь прямо просил предлагать альтернативы, если они лучше. Вот варианты,
которые я вижу, с оценкой применимости:

- **Вариант A (рекомендуемый, описан в 2.3)** — довести существующую bearing/OSM
  подложку до продакшна: офлайн-кеш, фикс frame_width, видимость фоллбэков.
  Минимальные изменения архитектуры, использует уже написанный и, судя по всему,
  спроектированный с умом код (BLOCK H).

- **Вариант B — предварительный map-matching всего маршрута.** Вместо того чтобы
  на каждый знак кидать отдельный луч, один раз (в начале обработки видео) построить
  граф дорожной сети по всему bbox маршрута и "примагнитить" (map-match) весь GPS-трек
  к этому графу (например, через `osmnx`/аналогичный алгоритм). Тогда для каждого
  перекрёстка заранее известны все исходящие направления (N/E/S/W и т.д.), и
  привязка знака к стороне превращается в быстрый lookup по азимуту вместо
  повторного raycast на каждое наблюдение знака. Плюсы: быстрее в рантайме,
  устойчивее на нетиповых перекрёстках (кольца, T-образные), даёт "карту
  перекрёстков" как побочный полезный артефакт. Минусы: больше работы на
  реализацию, новая тяжёлая зависимость (`osmnx` тянет `networkx`, `geopandas` и
  т.п.). Имеет смысл как эволюция варианта A, если после варианта A точность
  всё ещё окажется недостаточной на сложных перекрёстках.

- **Вариант C — сделать ручную корректировку на карте равноправным способом
  простановки знаков, а не только автоматику.** Это прямо пересекается с блоком 4
  (редактируемая карта): вместо того чтобы стремиться к 100%-точной автоматике,
  явно принять, что часть знаков будет определена геометрией верно, часть — нет,
  и сделать так, чтобы оператору было **дёшево** поправить сторону/позицию знака
  вручную на карте (перетащить маркер, переключить сторону кнопкой). Тогда
  ошибки геометрии перестают быть блокирующей проблемой. Рекомендую реализовать
  это в любом случае (это и есть требование блока 4), независимо от того, какой
  из вариантов A/B выбран для автоматики — они дополняют друг друга, а не
  конкурируют.

**Рекомендация:** делать A (обязательно) + C (обязательно, это отдельно
востребовано в блоке 4). B — отложить, реализовать только если после A точность
на реальных данных пользователя окажется неудовлетворительной на нетиповых
перекрёстках.

### 2.5 Критерии приёмки блока 2

- [ ] Обработка тестового маршрута с несколькими перекрёстками не требует доступа
      в интернет при повторном запуске (используется локальный кеш подложки).
- [ ] `frame_width` в `compute_sign_bearing()` берётся из реальных метаданных видео,

- [ ] В логе/отчёте видно, сколько знаков на поворотах определены геометрически, а

### 4.1 Контекст и важная оговорка

Бэкенд карты — `server/map_server.py` (Flask + SocketIO) и `ui/.../map_page.py`

### 4.3 Чего не хватает на бэкенде для полноценного редактирования

1. **Редактирование позиции/стороны/азимута знака.** Сейчас `PATCH /api/sign/<id>`
   принимает только `type`/`description`:
   ```python
   new_type = body.get("type", feat["properties"]["type"])
   new_desc = body.get("description", feat["properties"].get("SEM250", ""))
   ```
   Нужно расширить, чтобы можно было перетащить маркер на карте (новые lat/lon),
   переключить сторону (`is_left`/`side`) и, если нужно, поправить азимут линии.
   Так как знак в GeoJSON хранится как `LineString` (две точки, а не одна точка +
   азимут), при смене позиции/стороны нужно **пересчитать саму линию**, а не
   просто переписать координаты первой точки — переиспользуй
   `CoordinateCalculation.get_line`/`calculate_result_line`
   (`core/coordinate_calculation.py`) с новыми lat/lon и `is_left`, а не городи
   отдельную формулу на фронтенде или в роуте. Примерный контракт:
   ```jsonc
   PATCH /api/sign/<id>
   {
     "type": "3.24",          // опционально, как сейчас
     "description": "50",     // опционально, как сейчас
     "lat": 53.9021,          // опционально — новая позиция знака
     "lon": 27.5612,          // опционально
     "side": "left",          // опционально — "left"/"right"
     "azimuth": 184.5         // опционально — ручная коррекция направления
   }
   ```
   При наличии `lat`/`lon`/`side`/`azimuth` в теле — пересчитывать `geometry`
   (LineString), при отсутствии — вести себя как сейчас (менять только properties).
   После сохранения — эмитить `sign_updated` (уже есть), фронтенд должен
   перерисовать линию/маркер у этого знака, а не весь список.

2. **Создание знака вручную.** Оператору может понадобиться добавить знак, который
   детектор пропустил. Сейчас такого эндпоинта нет. Добавить:
   ```
   POST /api/sign
   {
     "type": "2.1",
     "lat": 53.9021,
     "lon": 27.5612,
     "side": "right",
     "azimuth": 90,
     "description": ""          // если тип из type_signs_with_text
   }
   ```
   Генерировать новый `id` (`uuid4`, как в остальном коде), строить `LineString`
   через `CoordinateCalculation`, проставлять минимально необходимые properties
   (`type`, `code` из `codes_signs`, `azimuth`, `side`, `time` — текущее время,
   `name_video`/`abs_frame` — можно оставить пустыми/пометить как "добавлено
   вручную", это пригодится потом для аналитики точности). Добавлять Feature в
   `data["features"]`, сохранять через `_save_geojson`, эмитить `new_sign`
   (или отдельное событие `sign_created`, если фронтенду нужно отличать "новый от
   детектора" от "новый вручную" — реши на месте после изучения `map.html`).

3. **(Опционально, если объём знаков большой)** Клиентская кластеризация маркеров

   стоит рассмотреть, если на реальных данных пользователя список знаков —

Прежде всего — **инвентаризация**: открыть `templates/map.html` и всё из
`static/`, выписать: какие кнопки/элементы управления там уже есть, какие из них
подключены к обработчикам, какие нет ("не работают" в терминологии задачи), какая
JS-библиотека карт используется (похоже на Leaflet, судя по терминологии в
`map_server.py`, но нужно подтвердить), как сейчас рисуются маркеры/иконки знаков
(используется ли уже `/api/img/<id>` для иконок, или знаки рисуются дефолтными
Leaflet-пинами).

По итогам инвентаризации нужно закрыть следующие требования пользователя:

- **"Отображались поставленные знаки с иконками"** — каждый маркер на карте должен
  использовать реальную иконку знака через `/api/img/<type>` (а не дефолтный пин),
  с учётом знаков с переменным текстом (эндпоинт уже это умеет — `/api/img/<type>-<text>`).
  Проверить, что это уже так; если нет — реализовать через Leaflet `L.icon`/
  `L.divIcon` с `iconUrl` на `/api/img/...`.
- **"Работали все кнопки"** — пройтись по каждой кнопке в `map.html`/связанном JS
  и убедиться, что у неё есть обработчик и он реально вызывает соответствующий
  роут/действие (экспорт GeoJSON, прыжок по видео через `/api/jump`, фильтры по
  типу знака, переключение слоя трека и т.п. — конкретный список кнопок будет
  виден только после открытия файла). Для каждой найденной нерабочей кнопки —
  либо подключить обработчик, либо (если кнопка окончательно устарела) убрать её,
  не оставлять "мёртвые" элементы UI (та же логика, что в блоке 3 для настроек).
- **"Можно было на карте редактировать знаки"** — реализовать (или доделать, если
  частично есть) панель/попап редактирования знака по клику на маркер:
  - смена типа знака (выпадающий список из `/api/sign_types` — уже есть на
    бэкенде);
  - смена описания/текста для знаков с переменным текстом
    (`type_signs_with_text` уже прокинут через `/api/sign_types`/бэкенд);
  - **перетаскивание маркера** для правки позиции (draggable marker в Leaflet) —
    на `dragend` слать новый `PATCH` с `lat`/`lon` (см. 4.3, пункт 1);
  - переключатель стороны (лево/право) — тоже через тот же `PATCH`;
  - кнопка "Добавить знак" — режим "поставить точку на карте" → форма выбора
    типа → `POST /api/sign` (см. 4.3, пункт 2);
  - кнопка удаления знака — уже есть `DELETE /api/sign/<id>` на бэкенде, нужно
    только убедиться, что на фронте она подключена и есть подтверждение перед
    удалением;
  - после любого редактирования — обновлять маркер/линию на карте локально по
    ответу API и/или по прилетевшему сокет-событию `sign_updated`/`sign_deleted`/
    `new_sign` (не обязательно перезагружать всю карту).
- Учитывай уже работающие сокет-события (`position` — двигать маркер машины,
  `processing_state`/`data_ready`/`processing_finished` — показывать/скрывать
  состояние "идёт обработка") — не дублируй эту логику, если она уже реализована.

### 4.5 Критерии приёмки блока 4

- [ ] На карте каждый знак отображается собственной иконкой (не дефолтным пином),
      включая знаки с переменным текстом.
- [ ] Клик по знаку открывает редактор: смена типа, описания, позиции (drag),
      стороны, удаление — всё сохраняется через API и подтверждается визуально
      (маркер/линия обновляются без полной перезагрузки страницы).
- [ ] Есть способ добавить знак вручную через клик по карте.
- [ ] Все кнопки в UI карты либо выполняют реальное действие, либо удалены.
- [ ] `PATCH /api/sign/<id>` умеет обновлять геометрию (позицию/сторону/азимут),
      не только properties.
- [ ] `POST /api/sign` создаёт корректный Feature, видимый сразу на карте у всех
      подключённых клиентов (через сокет).
- [ ] Ручное добавление/редактирование не ломает `GET /api/geojson_export` и
      формат, который читает остальной пайплайн (`FinalHandler`,
      `check_sign_data_duplicates.py` и т.п. — проверить, что они по-прежнему
      корректно парсят файл после ручных правок).

## 5. Общие ограничения (что не трогать / на что обратить внимание)

- Проект — PyQt6-десктоп-приложение под Windows с завязкой на конкретные детали
  потоков: модели грузятся лениво и только внутри `QThread` (см. комментарии в
  `sign_models.py`, `gpx_handler.py`, `turn.py`) из-за исторических крашей DLL при
  загрузке в главном потоке вместе с Qt. **Не переноси** ленивую загрузку моделей/
  `GPXHandler` в конструкторы, вызываемые из main thread — сохраняй паттерн
  "ленивая инициализация при первом обращении внутри рабочего потока", просто
  делай её мемоизированной (не "убирай ленивость", а "убирай повторность").
- `configs/config.py` — глобальное изменяемое состояние, которое, по комментарию в
  файле, "изменяется только из ProcessingController и VideoReaderThread". Уважай
  это соглашение при добавлении `FRAME_WIDTH` и т.п. (блок 2.3.2).
- Формат `signs.geojson` читается несколькими независимыми скриптами
  (`check_sign_data_duplicates.py`, `diagnose_coordinates.py`,
  `diagnose_empty_geojson.py`, сам `map_server.py`) — любые изменения схемы полей
  properties должны быть обратно совместимы или сопровождаться миграцией.
- Существует много `.md`-отчётов о более ранних блоках работ (`BLOCK_*.md`,
  `BUGFIX_*.md`, `FIX_*.md` и т.п.) — прочитай `BLOCK_H_*` перед блоком 2,
  `BLOCK_C_SETTINGS_IMPLEMENTATION.md` перед блоком 3, они содержат историю решений
  и, возможно, объясняют часть находок выше (например, почему появился дублирующийся
  блок геттеров в settings_page.py).

## 6. Рекомендуемый порядок выполнения

1. Блок 1 (перформанс) — маленький, изолированный, безопасный, даёт немедленный
   ощутимый эффект. Сделать первым.
2. Блок 3 (чистка настроек) — тоже небольшой, не зависит от остального, снижает
   риск при дальнейших изменениях в блоке 2 (меньше мусора вокруг
   `turn_use_bearing_geometry`/`turn_detection_radius_m`).
3. Блок 2 (подложка) — после 1 и 3, использует расчищенные настройки.
4. Блок 4 (карта) — можно делать параллельно с блоком 2 (бэкенд API), но
   пункт про ручную коррекцию стороны знака на карте логично тестировать вместе
   с блоком 2 на реальных перекрёстках — они проверяют друг друга.

## 7. Финальный чек-лист приёмки всей работы

- [ ] Обработка видео с длинным GPX-треком и множеством знаков стала заметно
      (кратно) быстрее на этапе трекинга, результат идентичен по данным.
- [ ] Знаки на перекрёстках определяются геометрически через (офлайн) подложку по

      ML-кода в `turn.py`.

      `AppSettings` учтено в UI осознанно (показано или явно не показано и почему).
- [ ] Карта показывает знаки с иконками, все кнопки рабочие, знаки можно

      совместимы с остальным пайплайном.
