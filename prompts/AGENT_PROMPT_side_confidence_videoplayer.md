## ЗАДАЧА 1 — Сторона дороги / перекрёстка и дублирующиеся знаки на дорогах с 4+ полосами

### 1.1 Диагноз (что уже раскопано, используй как отправную точку)

Сторона знака определяется в **трёх независимых, несинхронизированных местах**, и ни одно из них не знает о реальной геометрии дороги (число полос, ширина проезжей части, реальная сторона относительно оси дороги):

1. **`core/sign_handler.py`, `SignHandler._set_side()`** — первичное определение `sign.is_left`. Это чисто пиксельная эвристика: сравнивается, в какой трети кадра (`SCREEN_WIDTH/3`) находится знак и куда он сместился между первым и последним наблюдением (`sign.pixel_x[0] - sign.pixel_x[-1] > 0`). На широкой дороге (4+ полосы) знаки на противоположных сторонах или на разделительной опоре могут дать одинаковый пиксельный паттерн — метод не различает «знак слева от машины» от «знак у слишком широкой дороги, но по ходу движения похож на левый».

2. **`core/sign_handler.py`, `SignHandler._is_duplicate()`** (радиус `settings.dedup_radius_track_m`, по умолчанию **8 м**) — трек-левел дедуп по `(best_cnn, is_left, расстояние < 8м)`. На дороге с 4+ полосами (ширина проезжей части легко 14–20 м) два **реально разных** физических знака (например, один и тот же информационный знак, продублированный слева и справа широкой дороги — обычная практика на многополосных трассах) могут получить одинаковый `is_left` (из-за огрехов эвристики п.1) и попасть в один и тот же 8-метровый радиус относительно позиции машины в разных кадрах → один из них **ошибочно удаляется как дубликат**, хотя это два разных знака.

3. **`core/final_handler.py`, `_group_by_position()` + `_sign_to_feature_with_snap()` → `core/coordinate_calculation.py`, `CoordinateCalculation.calculate_result_line()`** — на уровне финальной сборки знаки группируются по ключу `f"{car_x:.0f}_{is_left}"` (округление до метра + сторона), и внутри группы каждому знаку присваивается **инкрементный `coefficient` (2, 3, 4, …)**, который используется как множитель смещения перпендикулярно треку машины:
   ```python
   x1 = x_cur - dy * (coefficient - 1)
   y1 = y_cur + dx * (coefficient - 1)
   ```
   Проблема: `dx, dy` — это вектор между текущей и точкой «5 м назад по азимуту» (`point_at_distance(..., distance_m=5.0)` в `_line_straight`), то есть **не привязан к реальной ширине полосы**. Каждый следующий знак в группе улетает перпендикулярно треку примерно на ~5, ~10, ~15 м и т.д. Это было задумано как «разведение» знаков по воображаемым полосам, но:
   - никак не проверяет, сколько полос реально существует на этом участке дороги;
   - не знает, какая это сторона перекрёстка — просто продолжает лепить смещения по одной прямой;
   - при 4+ полосах и нескольких детекциях одного и того же знака (трекер потерял/снова поймал знак — обычная ситуация при плотном трафике/перекрытии другими машинами) эти детекции **разъезжаются на 10–20+ м** и перестают быть «близкими».

4. **`core/final_handler.py`, `_deduplicate()`** — финальный дедуп по сетке `GRID_CELL_M=20` с ключом `(cell_x, cell_y, type, side)`, радиус `dedup_radius_final_m=20 м`, порог по азимуту `dedup_azimuth_deg=45°`. Из-за пункта 3 разведённые по коэффициенту копии одного и того же знака легко **вылетают за пределы 20-метрового радиуса** и не схлопываются → на карте появляются 2–3 маркера одного и того же реального знака («дублирующиеся знаки», о которых идёт речь).

5. Знаки **на поворотах/перекрёстках** обрабатываются отдельно, в `_process_turn_signs_bearing()` (bearing/raycast, `core/intersection_geometry.py`) или `_process_turn_signs_legacy()` (эвристика `core/turn.py::_handle_sign`), в зависимости от `settings.turn_use_bearing_geometry`. Raycast-модуль (`compute_sign_bearing` + `raycast_to_ways` + `aggregate_observations`) физически корректнее (кидает луч по азимуту камера→знак и ищет первое пересечение с OSM way), но:
   - на больших перекрёстках с 4+ полосами и разделённой проезжей частью OSM обычно хранит **разные `way` для встречных направлений** (двойная линия / `dual carriageway`) — луч может зацепить не тот `way`, если геометрия не выровнена, а `angle_diff_deg`/`max_distance_m=40` не проверяют это явно;
   - легаси-эвристика `Turn._handle_sign()` вообще не смотрит на число полос, только на пиксельные размеры/кадры (`coeff_size`, `coeff_fr`) — на широких перекрёстках она особенно ненадёжна.

**Итог диагноза:** «сторона» сейчас определяется исключительно через пиксельную эвристику + произвольный геометрический фан-аут, без единого понятия «реальная ширина/число полос дороги», из-за чего на дорогах ≥4 полос одновременно (а) возникают ложные дубликаты одного знака и (б) знаки получают неверную сторону/офсет.

## ЗАДАЧА 2 — Пересчёт метрики GPS-уверенности в редакторе ошибок

### 2.1 Диагноз

Уверенность считается в **двух местах, которые не гарантированно согласованы**:

1. **`core/sign.py`, `TrackedSign.calc_confidence()`** — «источник истины», вызывается в `FinalHandler` после OSM-snap. Формула:
   ```
   conf_cnn        = cnn_count / observation_count
   conf_placement  = 0.30*track_stability + 0.25*length_score + 0.25*snap_score + 0.20*az_score
   conf_total       = 0.50*conf_cnn + 0.50*conf_placement
   ```
   Результат пишется в свойства GeoJSON (`conf_cnn`, `conf_placement`, `conf_total`) через `_build_feature()`.

2. **`ui/widgets/error_editor_page.py`, `SignRecord._calc_gps_confidence()` / `_calc_confidence()`** — при загрузке GeoJSON в редакторе **сначала пытается взять готовое значение** `conf_placement`/`conf_cnn` из properties (то, что посчитал `sign.py`), но если его нет — **пересчитывает по совсем другой, куда более грубой формуле** (`azimuth_score + obs_score + stability_score` на основе разброса координат линии), которая **не знает** ни про `snap_distance`, ни про `azimuth_delta`, ни про новую логику стороны/дубликатов из Задачи 1.

Проблема для этого запроса: сейчас в `conf_placement`/`conf_total` **нет вообще никакого сигнала о корректности определения стороны/полосы** — знак, у которого сторона определена ошибочно (см. Задачу 1) или который является плохо разрешённым дубликатом на многополосной дороге, получает точно такую же уверенность, как чистый однозначный знак на двухполосной дороге. Редактор ошибок сортирует знаки от «наименее уверенных» (`SignListModel.load`, сортировка по `total_confidence`) — то есть именно такие проблемные многополосные знаки должны бы всплывать первыми, но сейчас у них нет для этого механизма.

### 2.3 Критерии приёмки

- Знак с высокой согласованностью стороны (все наблюдения дают одну и ту же `is_left`) на узкой дороге — уверенность не должна упасть по сравнению с текущим поведением (регрессия недопустима).

## ЗАДАЧА 3 — Вернуть видеоплеер на карту с переходом по клику на знак

### 3.1 Диагноз текущего состояния

- В `server/map.html` уже есть верстка секции `#video-section` (строки ~554–568), но она — **заглушка**: `#video-placeholder` с текстом «Предпросмотр видео недоступен в этой версии» и подсказкой пользоваться кнопкой «⏩ К кадру», которая просто дёргает `/api/jump?seconds=...` (см. `jumpToFrame()` в `<script>`) — это переключает **основной PyQt-плеер** (через `_on_jump_to_second` колбэк → `MapPage.jump_to_second` сигнал), а не что-то внутри самой веб-карты.
- В `server/map_server.py` **нет ни одного роута**, который бы отдавал сам видеофайл браузеру (нет `send_file`/потоковой раздачи `config.VIDEOS[i]` с поддержкой `Range`-заголовков для перемотки) — есть только `/api/img/<image_id>` для превью-картинок знаков (использует `send_file`).
- Список видеофайлов лежит в `configs.config.VIDEOS`, конкретный видеофайл и позиция внутри него вычисляются из `absolute_frame_numbers` знака: `video_idx = abs_frame // 63600`, `frame_in_video = abs_frame % 63600` (см. `error_editor_page.py::SignRecord.abs_frame_for_video()`, та же константа `63600` используется в `final_handler.py::_build_feature` и `video_reader.py`). Уже сейчас в ответе `/api/signs` (`map_server.py::api_signs`) фронтенду отдаётся сырое поле `abs_frame` (строка вида `"[123, 128, ...]"`) и `name_video`/`time` — но перевода в конкретный `video_idx`/`frame_in_video`/секунды для HTML5-плеера нет.
- **Важно про FPS:** в `final_handler.py::_build_feature` время строится как `minute = frame_local // 3600; seconds = (frame_local // 60) % 60` — то есть предполагается **60 кадров/сек** внутренней шкалы (`3600 = 60*60`). Не доверяй этому вслепую — при реализации сикинга бери реальный FPS видеофайла через `cv2.VideoCapture(...).get(cv2.CAP_PROP_FPS)` (как это, по сути, делает `error_editor_page.py`, только та использует `CAP_PROP_POS_FRAMES` напрямую с «сырым» `frame_in_video`, без деления на fps — потому что это кадры, а не секунды). Для HTML5 `<video>` тебе нужны **секунды**, поэтому: `seconds = frame_in_video / real_fps_видео`.

### 3.2 Что нужно сделать

       if not config.VIDEOS or video_idx >= len(config.VIDEOS):

### 3.3 Критерии приёмки

- Клик по маркеру знака на карте открывает нужный видеофайл и сразу перематывает на нужный момент (с точностью до пары секунд — идеальная точность зависит от `FRAME_STEP` и реального FPS, это ок).
- Повторные клики по знакам из **одного** видео не перезагружают файл с нуля (нет визуального «мигания»/долгой буферизации каждый раз).
- Клик по знаку из **другого** видеофайла корректно переключает `src`.
- Перемотка (drag по нативному или кастомному слайдеру) работает благодаря `Range`-поддержке (`conditional=True` в `send_file`), не требует полной загрузки файла.
- Основной PyQt-плеер и кнопка «К кадру» продолжают работать как раньше (`/api/jump` не сломан).
- Открытие карты «В браузере» (`_open_in_browser` в `map_page.py`, отдельное окно) — тоже должно проигрывать видео (роут `/api/video/<idx>` доступен не только из `QWebEngineView`, а вообще с `127.0.0.1:3000`).
