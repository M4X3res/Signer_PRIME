# PROMPT для ИИ-агента: светлая тема, видео на карте, производительность CPU (ONNX/OpenVINO)

**Проект:** RoadScanner (Signer PRIME)
**Дата:** 2026-09-07
**Приоритет:** P1 (UX-регрессия видна пользователю на скриншотах) + P2 (перформанс)

Это техническое задание для агента (Kiro AI Agent / аналог), написанное в стиле существующих
`PROMPT_*.md` файлов в репозитории. Каждая задача содержит: диагноз, конкретные файлы/функции,
которые нужно менять, предлагаемый план исправления и критерии приёмки. Не изобретай новую
архитектуру там, где можно точечно исправить существующий код.

---

## Контекст: три независимые проблемы

1. **Светлая тема неполная** — часть элементов интерфейса остаётся тёмной после переключения
   темы (скриншоты Redactor ошибок, шапка "КАРТА", лог обработки).
2. **Видео на карте не воспроизводится** — при выборе знака в видеоплеере карты выскакивает
   `Video loading timeout (10s)`, при этом диагностика кодеков показывает `H.264+AAC: нет`.
3. **Низкая производительность CPU-инференса** (ONNX Runtime / OpenVINO backend) — нужно
   предложить и реализовать конкретные ускорения, не наступая на грабли из
   `docs/BATCHING_FAILURE_ANALYSIS.md`.

Ниже — подробный разбор каждой задачи.

## ЗАДАЧА 1. Светлая тема: тёмные элементы не перекрашиваются

### Диагноз (корневая причина)

`ThemeManager.apply()` (`ui/themes/theme_manager.py`) делает две вещи:
1. `app.setStyleSheet(qss)` — глобальный QSS, применяется ко ВСЕМ виджетам, у которых есть
   `objectName`, соответствующий правилам в `ui/themes/modern_styles.py` (например `#Card`,
   `#VideoLabel`, `#LogConsole`, `#PageTitle`...).
2. `theme_changed.emit(...)` — сигнал, на который **должны** подписаться виджеты, которые
   красят себя вручную через `widget.setStyleSheet(f"... {theme_manager.tokens[...]} ...")`
   вместо objectName.

Проблема: множество виджетов вызывают `setStyleSheet(...)` с токенами темы **один раз, в
`__init__`**, и никогда не подписываются на `theme_changed`. QSS для конкретного виджета,
заданный через `setStyleSheet()`, имеет приоритет над глобальным `app.setStyleSheet()` для
того же виджета — поэтому глобальная смена темы эти виджеты не трогает, и они навсегда
остаются в цветах той темы, что была активна на момент создания страницы.

Это объясняет все скриншоты:
- **Image 1** (Редактор ошибок): тёмная левая панель списка знаков и часть чипов фильтра —
  `ErrorEditorPage._build_list_panel()` красит `panel` инлайн-стилем
  (`ui/widgets/error_editor_page.py`), но не подписан на `theme_changed` для этого именно
  `panel` (только `_restyle_badges()` и `_show_record()` привязаны к сигналу — этого
  недостаточно).
- **Image 2** (шапка "КАРТА"): `MapPage.__init__()` в `ui/widgets/map_page.py` красит
  `topbar` строкой
  `topbar.setStyleSheet(f"background: {theme_manager.tokens['bg_secondary']}; border-bottom: 1px solid {theme_manager.tokens['border_subtle']};")`
  один раз при создании и **вообще нигде** не подписывается на `theme_manager.theme_changed`
  — во всём файле `map_page.py` нет ни одного `theme_changed.connect(...)`.
- **Image 3** (Обработка → лог): `ProcessingPage.__init__()` в `ui/widgets/processing_page.py`
  красит `self.log_console` инлайн-стилем с `theme_manager.tokens['bg_primary']` /
  `text_secondary` при создании; `ProcessingPage` тоже нигде не подписан на `theme_changed`.
  То же самое с `self.video_label.setStyleSheet(...)` — при этом в `modern_styles.py` уже
  существует корректное глобальное правило `#VideoLabel`, которое конфликтует с этим инлайн-
  стилем (два источника правды для одного и того же элемента).

### Как исправлять (два допустимых паттерна, используй существующий из `ErrorEditorPage`)

**Паттерн А (предпочтительный) — убрать инлайн-стиль, использовать objectName.**
Если для элемента уже существует правило в `ui/themes/modern_styles.py` (например `#Card`,
`#VideoLabel`, `#LogConsole`, `#FilePathBox`), удали инлайн `setStyleSheet(...)` полностью —
глобальный QSS уже красит его правильно при каждом вызове `theme_manager.apply()`. Это самый
надёжный способ, применяй его в первую очередь для `processing_page.py::video_label` (правило
`#VideoLabel` уже покрывает нужный цвет через `video_bg` — просто убрать дублирующий инлайн-

можно смело удалять инлайн-версию, оставив только `objectName("LogConsole")`).

**Паттерн Б — если нужен динамический/семантический цвет (не выражается через objectName),**
следуй паттерну, уже реализованному в `ErrorEditorPage`:
1. Добавь метод `_restyle_<название>()` в класс, который читает **свежие** `theme_manager.tokens`
   и переустанавливает стиль нужных виджетов.
2. Вызови этот метод один раз в конце `__init__`.
3. Подключи его к `theme_manager.theme_changed.connect(self._restyle_<название>)` (или расширь
   существующий `_on_theme_changed`, если он уже есть в классе).

Применить паттерн Б к: `MapPage` (topbar), `ErrorEditorPage._build_list_panel` (панель списка +
комбобокс фильтра), `Sidebar` (`logo_lbl`, `ver_lbl`, `nav_lbl`, оба `sep`/`sep2`),

## ЗАДАЧА 2. Веб-страница карты (`templates/map.html`) не следует теме приложения вовсе

### Диагноз

Это отдельная, более глубокая проблема, чем Задача 1. `templates/map.html` — это полностью
самостоятельная HTML/CSS/JS страница, которая рендерится внутри `QWebEngineView`
(`ui/widgets/map_page.py::_load_map()` открывает `http://127.0.0.1:{MAP_PORT}/`). Вся палитра
задана через CSS-переменные в `:root` (`--bg: #141414`, `--bg2: #1c1c1c` и т.д.) — она **вообще
не связана** с `ThemeManager`/`AppSettings.theme` приложения. Именно поэтому на скриншотах
4–6 вся правая панель карты ("ВИДЕОПЛЕЕР", "ЗНАК", фильтры, сама шапка "GPS-КАРТА ЗНАКОВ")
остаётся тёмной, даже когда остальной интерфейс Qt (сайдбар "Настройки" и т.п. на Image 6) уже
светлый.

### План исправления

1. **Добавить светлый набор CSS-переменных** в `templates/map.html`, зеркалящий
   `MODERN_LIGHT_TOKENS` из `ui/themes/modern_light.py` (bg_primary `#F9F8F5`, bg_secondary
   `#F2F0EA`, text_primary `#26241F`, border_default `#DAD4C7`, accent `#2F5D8A` и т.д.).
   Реализовать как `body.theme-light { --bg: ...; --bg2: ...; ... }` рядом с текущим `:root`
   (который становится дефолтом/тёмной темой).
2. **Передавать текущую тему при загрузке страницы.** В `MapPage._load_map()`
   (`ui/widgets/map_page.py`) добавить query-параметр к URL:
   ```python
   from ui.themes.theme_manager import theme_manager, Theme
   theme_param = "light" if theme_manager.current == Theme.LIGHT else "dark"
   url = QUrl(f"http://127.0.0.1:{MAP_PORT}/?theme={theme_param}")
   ```
   В `map.html` при `DOMContentLoaded` прочитать `new URLSearchParams(location.search).get('theme')`
   и добавить/убрать класс `theme-light` на `<body>` до инициализации карты.
3. **Живое обновление без перезагрузки страницы**, если пользователь переключил тему прямо во
   время просмотра карты:
   - Добавить в `server/map_server.py` функцию `emit_theme_changed(theme: str)`, аналогичную
     `emit_processing_finished`/`emit_position`, которая делает `socketio.emit("theme_changed", {"theme": theme})`.
   - В точке, где приложение переключает тему (`SettingsPage._on_theme_changed` /
     `theme_manager.set_theme`), вызвать этот эмиттер (по аналогии с тем, как уже вызывается
     `set_processing_state`) — можно подписать `theme_manager.theme_changed` сигнал на новый
     метод в `MapPage`, который дергает Flask-эндпоинт/функцию эмита.
   - В `map.html` добавить `socket.on("theme_changed", ({theme}) => document.body.classList.toggle('theme-light', theme === 'light'))`.
4. **Отключить инверсию тайлов OSM в светлой теме.** Сейчас `.leaflet-tile { filter:
   brightness(0.55) contrast(1.1) saturate(0.7) hue-rotate(180deg) invert(1); }` — это хак,
   который "перекрашивает" стандартные светлые тайлы OSM в тёмные. В светлой теме этот фильтр
   должен быть отключён (`body.theme-light .leaflet-tile { filter: none; }`), иначе тайлы карты
   останутся визуально тёмными/инвертированными независимо от остального UI.
5. **Побочный баг, который стоит исправить заодно** (обнаружен при чтении файла): функция
   `showConfirmDialog()` в `map.html` использует CSS-переменные `var(--bg-card)`, `var(--text1)`,
   `var(--text2)`, `var(--bg-hover)`, которых **не существует** ни в `:root`, ни где-либо ещё в
   файле (реально определены только `--bg, --bg2, --bg3, --text, --text2, --text3, --border,
   --border2, --accent, --success, --error, --warning`). Из-за этого модальное окно
   подтверждения удаления знака рендерится с дефолтными (прозрачными/непредсказуемыми)
   цветами браузера. Замени на реально существующие переменные (`--bg2`/`--bg3` для фона
   карточки, `--text`/`--text2` для текста, `--bg3` для hover).

### Критерии приёмки Задачи 2

- При запуске приложения в светлой теме и открытии вкладки "Карта" — вся веб-страница карты
  (шапка, фильтры, статус-бар внизу карты, правая панель "Видеоплеер"/"Знак", кнопки, чипы
  фильтра) отображается в светлой палитре, согласованной с остальным приложением, а не в
  чёрно-синей.
- Переключение темы в "Настройках" при открытой вкладке "Карта" перекрашивает содержимое карты
  "на лету" (без ручной перезагрузки через кнопку "Перезагрузить").
- Тайлы OSM в светлой теме выглядят как обычная светлая карта (без инверсии/тёмного хака),
  в тёмной теме поведение остаётся как было (фильтр применяется).
- Диалог подтверждения удаления знака (`showConfirmDialog`) отображается с корректными
  цветами в обеих темах, а не с "битыми" CSS-переменными.

## ЗАДАЧА 3. Видео на карте не проигрывается (`Video loading timeout (10s)`)

### Диагноз

По скриншотам 5–6 видно следующую последовательность:
1. Пользователь кликает на маркер знака → `map.html::selectSign()` → `loadVideoForSign()`.
2. `loadVideoForSign()` проверяет доступность источника через `fetch(videoSrc, {method:'HEAD'})`,
   читает `Content-Type: video/mp4`, и вызывает `video.canPlayType(contentType || 'video/mp4')`
   — это **обобщённая** (без явного кодека) проверка, которая в Chromium обычно возвращает
   `"maybe"` эвристически, по контейнеру/расширению, **не проверяя реальную поддержку декодера**.
   Проверка проходит, код продолжает грузить `<video>`.
3. Диагностика через кнопку "🔍" (`testVideoCodec()` → `/api/video_codec/<idx>`, Image 5)
   показывает: исходный файл — `video: h264 (High)`, `audio: aac (LC)` — совершенно стандартная,
   широко поддерживаемая комбинация. Но при этом та же диагностика делает **более строгую**
   проверку `video.canPlayType('video/mp4; codecs="avc1.42E01E, mp4a.40.2"')` и получает **пустую
   строку** (`H.264+AAC: нет`).
4. Реальная попытка загрузить `<video>` затем виснет: `loadedmetadata` никогда не срабатывает,
   через 10 секунд срабатывает таймаут из `loadPromise` в `loadVideoForSign()` → пользователь
   видит "Ошибка загрузки видео: Video loading timeout (10s)" (Image 6).

**Наиболее вероятная корневая причина:** `PyQt6-WebEngine`, установленный из PyPI, использует
сборку Chromium/QtWebEngine **без проприетарных кодеков** (H.264/AAC не собираются в публичные
wheel-пакеты по лицензионным причинам — эти кодеки включаются только при сборке Qt с флагом
`-proprietary-codecs`). Из коробки поддерживаются только открытые кодеки: VP8/VP9 (видео) и
Vorbis/Opus (аудио) в контейнере WebM. Это объясняет ВСЁ наблюдаемое поведение: обобщённый
`canPlayType('video/mp4')` "врёт" (говорит "maybe" по эвристике расширения), явный кодек-стринг
для H.264 корректно возвращает "не поддерживается", а реальная попытка декодирования зависает/
проваливается без явной ошибки MEDIA_ERR — то есть выглядит именно как таймаут, а не как явная
"формат не поддерживается" ошибка. Это же не проблема тегов Range/сети — раздача файла (по
`/api/video/<video_idx>` в `server/map_server.py`) с Range-запросами реализована корректно и не
является причиной.

Агенту: **обязательно подтверди эту гипотезу** перед тем, как писать код фикса — например,
проверь `video.canPlayType('video/webm; codecs="vp9,opus"')` в целевой сборке QtWebEngine (если
он непустой при пустом H.264 — гипотеза подтверждена), либо посмотри версию/флаги сборки
`PyQt6-WebEngine`, установленной в окружении проекта (`pip show PyQt6-WebEngine`, и если
возможно — версию Chromium, зашитую в неё).

### План исправления — три пути, реализовать основной (Путь A), задокументировать остальные

**Путь A (основной, минимально инвазивный): транскодировать короткий превью-клип в WebM
(VP9+Opus) на лету, с кэшированием на диске.**

1. Новый эндпоинт в `server/map_server.py`, например:
   ```
   GET /api/video_clip/<int:video_idx>?start=<float>&duration=<float>
   ```
   - `start` — секунда начала клипа (обычно `avg_frame / fps` знака минус небольшой отступ,
     например 3–5 секунд "до"), `duration` — длина клипа (например 15–20 секунд), значения по
     умолчанию нужно подобрать разумно (не тащить весь ролик).
2. Внутри эндпоинта — вызов `ffmpeg` (subprocess), например:
   ```
   ffmpeg -ss <start> -i <video_path> -t <duration> \
          -c:v libvpx-vp9 -b:v 1M -c:a libopus -f webm <cache_path>
   ```
   (конкретные битрейты/пресеты подобрать под баланс скорость-транскодирования / качество;
   учесть, что `-ss` перед `-i` даёт быстрый seek по ключевым кадрам).
3. **Кэшировать результат на диске**, ключ — `(video_idx, round(start))` (или хэш параметров),
   рядом с исходным видео или в отдельной директории кэша (см. паттерн `OSMSnapper`'а с
   персистентным JSON-кэшем `<video>_osm_cache.json` в `core/osm_snap.py` как референс для
   "кэш рядом с видео файлом"). Повторный клик на тот же знак не должен перезапускать `ffmpeg`.
4. **Проверка наличия `ffmpeg`** при старте (или лениво при первом обращении к эндпоинту) —
   если бинарник не найден в PATH, вернуть внятную JSON-ошибку (`{"error": "ffmpeg not found, ..."}`),
   а не падать 500-й без объяснений; в `map.html` показать пользователю понятное сообщение
   вместо "Video loading timeout".
5. В `templates/map.html::loadVideoForSign()`:
   - заменить обращение к `/api/video/<video_idx>` (весь файл + ручной `currentTime`) на новый
     `/api/video_clip/<video_idx>?start=...&duration=...`;
   - `source.type` сменить на `video/webm`;
   - т.к. теперь сервер уже возвращает клип, начинающийся с нужного момента (с небольшим
     оффсетом "до"), `video.currentTime` после загрузки нужно выставлять на этот оффсет
     (например 3–5 сек), а не на абсолютную секунду в исходном видео.
6. Оставить старый `/api/video/<video_idx>` эндпоинт как есть (для диагностики/полного скачивания
   при необходимости), не ломать `testVideoCodec()`.

Преимущества: не требует пересборки Qt/переустановки зависимостей у пользователя, работает с
уже имеющимся `PyQt6-WebEngine` из PyPI; побочный плюс — вместо скачивания сотен МБ/ГБ
исходного GoPro-файла в браузер отдаётся лёгкий короткий клип, что и быстрее, и меньше
нагружает диск/сеть локального Flask-сервера.

Недостаток: требует `ffmpeg` на машине пользователя — обязательно предусмотреть graceful
degradation (см. п.4) вместо краша карты.

**Путь B (альтернатива, не основной): использовать сборку Qt/QtWebEngine с проприетарными
кодеками.** Некоторые дистрибутивы (например, отдельные conda-forge сборки `qt-webengine`)
компилируются с `-proprietary-codecs` и умеют H.264/AAC "из коробки". Задокументировать это как
опцию для тех, кто ставит зависимости через conda, но **не делать основным решением**, так как
это меняет историю установки для существующих pip-пользователей и не гарантировано во всех
окружениях.

**Путь C (более инвазивный, на будущее): не использовать `<video>` внутри веб-страницы карты,
а проигрывать видео через нативный Qt Multimedia (`QMediaPlayer` + `QVideoWidget`) поверх/рядом
с `QWebEngineView`.** На Windows это будет использовать Media Foundation — тот же бэкенд, который
уже успешно используется для чтения GoPro H.264-файлов в `processing/video_reader.py`
(`cv2.CAP_MSMF`), то есть проблем с декодированием H.264 там в принципе не будет. Это решает
проблему кардинально, но требует встраивания отдельного Qt-виджета видео в макет
(`ui/widgets/map_page.py`) и синхронизации его с логикой "перейти к секунде" (`jumpToFrame()` в
`map.html` / `_on_jump_to_second` в `ui/main_window.py`), что заметно больше работы. Не
реализовывать сейчас, но не делать код Пути A таким, чтобы Путь C потом было сложно подключить
(держи логику "вычислить video_idx + секунду для знака" в одном легко переиспользуемом месте).

## ЗАДАЧА 4. Повышение производительности CPU-инференса (ONNX Runtime / OpenVINO)

### Текущее состояние

- Модели грузятся лениво через `_LazyModel` (`configs/sign_models.py`), backend выбирается через
  `AppSettings.cpu_inference_backend` (`torch` / `onnx` / `openvino`).
- Количество потоков ONNX intra-op / OpenVINO уже настраивается (`BLOCK CPU-5`,
  `configs/inference_threading.py`, вызывается из `main.py` и `processing/detector_process_pool.py`).
- Батчинг через `Detector._classify_rube_batch` / `_classify_fine_batch` / `_run_cnn_batch`
  (`core/detector.py`) уже группирует кропы по `yolo_class`, но батчинг реализован через
  высокоуровневый `ultralytics` API (`model.predict(list_of_crops)` / `model(crops, verbose=False)`),
  а не напрямую через сессию ONNX Runtime/OpenVINO.
- `docs/BATCHING_FAILURE_ANALYSIS.md` документирует, что батчинг через `rube_modal.predict(crops32)`
  на PyTorch/CPU оказался **медленнее** из-за overhead копирований внутри Ultralytics-обёртки —
  это важный прецедент, который нужно учитывать, но он **не обязательно переносится** на прямой
  вызов `InferenceSession.run()` в ONNX Runtime, так как там нет тех же слоёв Python-обёртки.

Ниже — приоритизированный список конкретных изменений. Для каждого требуется отдельный
бенчмарк до/после (расширить `scripts/benchmark_detector.py` и/или `scripts/test_cnn_batching.py`),
чтобы не повторить историю `BATCHING_FAILURE_ANALYSIS.md`, когда оптимизация "на бумаге" оказалась
регрессией на практике.

#### 4.1. Явная настройка SessionOptions для ONNX Runtime (низкий риск, средний выигрыш)

- Убедиться, что при создании ONNX-сессии (в `_LazyModel._load()`, `configs/sign_models.py`,
  и/или там, где Ultralytics внутренне создаёт `onnxruntime.InferenceSession` для `.onnx` файлов)
  явно выставлены:
  - `graph_optimization_level = onnxruntime.GraphOptimizationLevel.ORT_ENABLE_ALL`
  - `execution_mode = onnxruntime.ExecutionMode.ORT_SEQUENTIAL` (для мелких классификационных
    моделей 32×32 параллельный режим обычно добавляет накладные расходы синхронизации, а не
    ускоряет — сравнить с `ORT_PARALLEL` бенчмарком, не полагаться на предположение).
  - `enable_mem_pattern = True`, `enable_cpu_mem_arena = True` (обычно default, но зафиксировать
    явно, так как модели вызываются тысячи раз за видео — churn аллокатора заметен на масштабе).
- Если Ultralytics не даёт прямого доступа к `SessionOptions` через свой YOLO-wrapper — рассмотреть
  прямую загрузку `.onnx` через `onnxruntime.InferenceSession(path, sess_options=...)` в обход
  Ultralytics для маленьких классификационных моделей (`rube_modal`, `model_dict[*]`,
  `sub_models[*]`), оставив Ultralytics только для детекции (`model_side_detect`, где нужен
  постпроцессинг NMS/decode, который Ultralytics уже реализует).

#### 4.2. Кэширование скомпилированной/оптимизированной модели на диск (средний риск, большой выигрыш в Process Pool режиме)

- Для ONNX: использовать `SessionOptions.optimized_model_filepath` при первом запуске
  (`scripts/export_models_onnx.py`), чтобы граф с уже применёнными оптимизациями сохранялся
  рядом с исходным `.onnx` и переиспользовался, а не пересчитывался каждый раз.
- Для OpenVINO: включить `core.set_property({"CACHE_DIR": <путь>})` при инициализации `Core()`
  (там, где сейчас грузится `.xml`/директория `*_openvino_model` в `_LazyModel._load()`).
- **Почему это особенно важно:** в режиме `process_pool` (`processing/detector_process_pool.py`,
  `_worker_process_frame`) КАЖДЫЙ из N worker-процессов сейчас заново загружает и
  компилирует/оптимизирует ВСЕ модели с нуля при старте — это уже задокументированная проблема
  (`docs/WHY_SINGLE_THREAD_FASTER.md`, `docs/DETECTOR_POOL.md`). Для ONNX Runtime и особенно
  OpenVINO компиляция графа — заметно более дорогая операция, чем для "ленивой" загрузки
  PyTorch-весов, поэтому кэш на диск (общий для всех процессов, т.к. читается только для чтения)
  даёт кумулятивный выигрыш пропорционально числу воркеров.

#### 4.3. Настоящий батчинг на уровне сессии (средний риск, требует бенчмарка — см. предупреждение выше)

- Обойти высокоуровневый `.predict()`/`__call__` Ultralytics для мелких классификационных
  моделей backend'ов `onnx`/`openvino`: собрать `(N, 3, 32, 32)` тензор одним `np.stack(...)`
  (без Python-цикла с преобразованиями PIL/cv2 на каждый кроп) и вызвать
  `session.run(None, {input_name: batch})` напрямую.
- Это **другой** код-путь, чем измерялся в `docs/BATCHING_FAILURE_ANALYSIS.md` (там батчили
  именно через `rube_modal.predict(crops32)`, то есть через ту же тяжёлую Ultralytics-обёртку с
  копированиями) — поэтому прежний отрицательный результат **не обязательно переносится**, но
  и не гарантирует ускорения — обязательно измерить отдельно, используя
  `scripts/test_cnn_batching.py` как шаблон, но с прямым `session.run()` вместо `.predict()`.
- Для OpenVINO батчинг особенно выгодно сочетать с `PERFORMANCE_HINT=THROUGHPUT` (см. 4.4) —
  OpenVINO CPU-плагин сам распараллеливает несколько inference-запросов между потоками/ядрами.

#### 4.4. Специфичные настройки OpenVINO (средний риск, средний-большой выигрыш)

- Явно выставить `PERFORMANCE_HINT`:
  ```python
  core.set_property("CPU", {"PERFORMANCE_HINT": "THROUGHPUT"})
  ```
  для офлайн-обработки видео (в отличие от `"LATENCY"` — режима по умолчанию, оптимизированного
  под единичный запрос с минимальной задержкой). `THROUGHPUT` позволяет OpenVINO самому подобрать
  число параллельных inference-стримов (`NUM_STREAMS`) под доступные ядра — это лучше подходит
  под текущий паттерн нагрузки проекта ("классифицировать много независимых кропов за кадр"),
  чем поштучные low-latency вызовы.
- Не включать BF16-инференс "на автомате" — это выгодно только на CPU с нативной поддержкой
  BF16/AMX (сравнительно новые Intel Xeon/Core), на старых CPU может быть медленнее FP32.
  Сделать это отдельной, явно документированной опцией с проверкой поколения CPU, а не
  дефолтом.

#### 4.5. Квантизация (наибольший потенциальный выигрыш, требует осторожности и валидации точности)

- Мелкие категориальные классификаторы (`small_models/*.pt`, ~11 МБ каждый) и `rube_modal` —
  хорошие кандидаты на **динамическую INT8-квантизацию**:
  - ONNX: `onnxruntime.quantization.quantize_dynamic`.
  - OpenVINO: NNCF / Post-Training Optimization Toolkit.
  - Ожидаемый эффект: обычно 2–4× ускорение на CPU для простых классификационных CNN, с
    минимальной потерей точности (это не bbox-регрессия, где точность критичнее).
- **Не квантовать сходу `model_side_detect`** (основной детектор bbox) без отдельной валидации —
  для него точность важнее, ошибки детекции = пропущенные/задвоенные знаки. Если квантуется —
  обязательно прогнать `scripts/test_detector_regression.py` до/после и сравнить количество и
  bbox найденных знаков.
- Реализовать как **явный, опциональный** флаг в `scripts/export_models_onnx.py`
  (например `--quantize`), а не тихое автоматическое применение — чтобы пользователь мог
  осознанно сравнить точность до переключения продакшн-пайплайна.

#### 4.6. Проверить сквозную работу деления потоков между воркерами Process Pool

- `configs/inference_threading.py` + секция `BLOCK CPU-5` в `main.py` уже делят
  ONNX/OpenVINO-потоки на число воркеров, а `_worker_process_frame`
  (`processing/detector_process_pool.py`) применяет лимиты один раз на процесс через флаг
  `_threads_patched`. Проверить, что `num_workers`, используемый внутри
  `_worker_process_frame` для расчёта `intra`/`ov_threads`, **реально совпадает** с фактическим
  `max_workers` в `ProcessPoolExecutor(...)`, создаваемом в
  `DetectorProcessPool._detect_optimal_workers()`/`start()`, а не пересчитывается независимой
  (и потенциально другой) эвристикой внутри worker-процесса — иначе возможна пере- или
  недо-аллокация потоков на ядро.

### Требования к реализации Задачи 4

- Для каждого пункта (4.1–4.6), который реализуешь, — обязательный до/после бенчмарк на одном и
  том же тестовом видео, backend=`onnx` и backend=`openvino` отдельно, сравнение FPS и (для 4.5)
  количества/точности найденных знаков через `scripts/test_detector_regression.py`.
- Если какая-то оптимизация покажет регрессию (как в `docs/BATCHING_FAILURE_ANALYSIS.md`) —
  задокументировать это аналогичным markdown-файлом с цифрами и **откатить** изменение, не
  оставлять "оптимизацию", которая на практике замедляет обработку.
- Обновить `docs/PERFORMANCE_OPTIMIZATIONS.md` (или создать новый
  `docs/CHANGELOG_CPU_INFERENCE_PERF.md`) с итоговыми цифрами по каждому изменению.
