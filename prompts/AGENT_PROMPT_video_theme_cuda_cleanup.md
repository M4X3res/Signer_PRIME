# Промпт для ИИ-агента: RoadScanner — 5 задач (видео-плеер, редактор, тема, CUDA, чистка зависимостей)

## Контекст проекта

Десктопное приложение на **PyQt6** для обработки видео с дорожными знаками (детекция YOLO + классификация CNN + OCR EasyOCR), с картой на **Flask + Leaflet** (`server/map_server.py`, `map.html`), встроенной через `QWebEngineView`. Настройки хранятся в dataclass `AppSettings` (`configs/settings.py`) с персистентностью через `QSettings`. Темы UI — `ui/themes/theme_manager.py` + `modern_dark.py` / `modern_light.py` (словари токенов) + `modern_styles.py` (генерирует QSS).

Ниже — 5 независимых задач. Каждую можно делать отдельно и коммитить отдельно. Для каждой указаны: причина проблемы, файлы/строки, что сделать, критерии приёмки. Перед правками — открой указанные файлы и перепроверь номера строк (могли сместиться).

**Общие требования ко всем задачам:**
- Не ломать существующую функциональность (особенно уже рабочую логику в `map.html::loadVideoForSign()` — трогать только то, что описано).
- Все новые строки UI — на русском, в том же стиле, что и остальной интерфейс.
- После правок — ручная проверка сценария, описанного в «Критерии приёмки».
- Если правишь `AppSettings` — не забудь, что `load()`/`save()` работают через `__dataclass_fields__` автоматически, новых полей в них руками добавлять не нужно, только сам dataclass-field.

## Задача 1. Клик по знаку на карте не открывает видео в нужный момент

### Причина
В проекте два разных механизма, их нельзя путать:

1. **Автоматическая подгрузка видео в панель карты** — `map.html::selectSign()` → `loadVideoForSign()`. Стримит нужный фрагмент через `GET /api/video/<idx>` (`server/map_server.py`, роут `/api/video/<int:video_idx>`, строка ~371) прямо в `<video id="map-video">`. Код выглядит завершённым и рабочим — **сначала проверь в реальности, работает ли он вообще** (открыть карту, кликнуть на знак, посмотреть, подгружается ли видео и происходит ли `video.currentTime = seconds`). Если не работает — искать баг здесь: несовпадение `FRAMES_PER_VIDEO = 63600` с реальной длиной видеофайлов, кодек mp4 (не проигрывается в Chromium/QWebEngine), либо `config.PATH_TO_VIDEO` / `config.VIDEOS` не заполнены к моменту клика.

2. **Кнопка «⏩ К кадру»** (`map.html`, `id="btn-jump"`, функция `jumpToFrame()`, строка ~1143) — шлёт `GET /api/jump?seconds=...` → `map_server.py` (роут `/api/jump`) → callback `on_jump` → сигнал `MapPage.jump_to_second` (`ui/pages/map_page.py`) → **`main_window.py::_on_jump_to_second()` (строка 241)**. Этот обработчик — заглушка:
   ```python
   def _on_jump_to_second(self, seconds: int):
       """Карта просит прыгнуть к секунде — передаём в VideoPlayer (будущий)."""
       config.SECONDS_ALL_VIDEO = seconds
       self.page_processing.log(f"Переход к секунде {seconds}", "info")
       if self._controller and self._controller.is_running:
           self.page_map.update_position(seconds)
   ```
   Реального перехода к кадру/видео нигде не происходит — ни во время обработки, ни после. Отдельного класса `VideoPlayer` в проекте **нет вообще** (проверено — `processing_page.py::set_frame()` только отображает уже готовый `QPixmap`, поступающий из `ProcessingController.frame_ready`, это не seek-able плеер).

   Также баг с подпиской: `self.page_map.jump_to_second.connect(self._on_jump_to_second)` вызывается внутри `_on_single()` (строка 207) **при каждом старте обработки** — сигнал переподключается повторно (дублирование обработчика при повторных запусках). В `_on_multiple()` (массовая обработка) этой подписки нет вообще — сигнал там никто не слушает.

### Что сделать
1. Сначала протестируй и, если нужно, доведи до конца механизм №1 (`loadVideoForSign`) — это самодостаточный видео-плеер прямо на карте, не требующий доработки PyQt-стороны. Проверь:
   - что `/api/video_info/<idx>` отдаёт корректный `fps`;
   - что `video.src` реально грузится (нет CORS/404/кодек-ошибок — в консоли QWebEngine или `--remote-debugging-port` смотри логи `[loadVideoForSign]`);
   - что `avgFrame`/`FRAMES_PER_VIDEO` соответствуют реальной длине видеофайлов проекта (константа `63600` используется также в `final_handler.py:1032-1033`, `video_reader.py:107,250`, `error_editor_page.py:242-243` — если это не совпадает с фактическим FPS/длиной видео, поправь везде синхронно, лучше вынести в `configs/config.py` как единую константу `FRAMES_PER_VIDEO`).
2. Реши, нужен ли параллельно и «прыжок в реальном плеере PyQt» (кнопка «⏩ К кадру» и переход из редактора, см. Задачу 2) — если да, замени заглушку `_on_jump_to_second`:
   - Переключать на страницу с видео и реально открывать/перематывать видео на нужный кадр (например, через `cv2.VideoCapture` + показ кадра в `QLabel`, аналогично `error_editor_page.py::_load_frame()`, либо через отдельный `QMediaPlayer`, если видео должно проигрываться, а не быть статичным кадром).
   - Убрать повторное подключение сигнала из `_on_single()` — подписывать `jump_to_second` один раз (в `__init__` MainWindow или в месте первого создания `page_map`), и добавить такую же подписку для `_on_multiple()`.
3. Обнови комментарии-заглушки («будущий», «пока просто логируем») на реальное описание поведения.

### Критерии приёмки
- Открыть карту после завершённой обработки, кликнуть по маркеру знака → в панели карты либо сразу проигрывается видео на нужной секунде (механизм 1), либо (если реализован механизм 2) в основном приложении открывается/перематывается видео/кадр на тот же момент.
- Кнопка «⏩ К кадру» и переход из редактора ошибок (Задача 2) ведут к тому же результату, без ошибок в консоли и логах приложения.
- Повторный запуск обработки (single и multiple) не приводит к дублированию логов/обработчиков при клике по знаку.

## Задача 2. Кнопка «К кадру» в редакторе ошибок не работает

### Причина
`error_editor_page.py`:
- `SignRecord.abs_frame_for_video()` (строка 237) — корректно считает `(video_idx, frame_in_video)`.
- `_on_jump_to_frame()` (строка 1115) — корректно эмитит `self.jump_to_frame.emit(info[0], info[1])`.
- В `main_window.py` сигнал подключён: `self.page_errors.jump_to_frame.connect(self._on_editor_jump)` (строка 139).
- Но `_on_editor_jump()` (строка 515) — заглушка:
  ```python
  def _on_editor_jump(self, video_idx: int, frame_num: int):
      """Редактор просит перейти к кадру — логируем (VideoPlayer будет позже)."""
      self._switch_page("processing")
      self.sidebar.set_page("processing")
      self.page_processing.log(
          f"Переход: видео {video_idx + 1}, кадр {frame_num}", "info"
      )
  ```
  Реального открытия видео/кадра не происходит.

Обрати внимание: сам `error_editor_page.py` уже умеет показывать статичное превью нужного кадра (`_load_frame()`, строка 916, через `cv2.VideoCapture` + `CAP_PROP_POS_FRAMES`) — это работает и уже используется для миниатюры в самом редакторе. Кнопка «К кадру» — это отдельное действие «открыть контекст крупнее / в основном плеере», а не то же самое превью.

### Что сделать
1. Реализуй `_on_editor_jump(video_idx, frame_num)` так, чтобы реально открывался кадр/видео на нужной позиции — используй ту же логику, что решишь в Задаче 1 (переиспользуй один и тот же способ показа/перемотки видео, не дублируй код — вынеси в общий метод/класс, если он появится).
2. Если решение из Задачи 1 — это открытие видео на странице карты/обработки, вызови тот же метод здесь с `video_idx`/`frame_num`, предварительно переведённым в секунды (или проверь, что общий метод принимает и кадры, и секунды одинаково корректно).

### Критерии приёмки
- В редакторе ошибок выбрать знак → нажать «⏩ К кадру» → открывается реальный кадр/видео на нужной позиции (а не просто лог в консоли).
- Не ломает существующее превью кадра в самом редакторе (`_load_frame`).

## Задача 3. Светлая тема — убрать «чисто белый», сделать приятную палитру

### Причина
`ui/themes/modern_light.py` — `bg_primary` и `bg_elevated` буквально `#ffffff` (чистый белый), из-за чего в светлой теме резкий, «стерильный» контраст.

### Что сделать
1. В `MODERN_LIGHT_TOKENS` замени `bg_primary`/`bg_elevated` на тёплый/приглушённый оттенок белого (не чистый `#ffffff`), например в диапазоне `#f7f6f3`–`#faf9f6` (тёплый) или `#f8f9fb`–`#fafbfc` (холодный, ближе к текущей стилистике GitHub Light, которая и так используется как референс — см. комментарий в файле). Сохрани текущую иерархию: `bg_primary` должен оставаться **светлее**, чем `bg_secondary` (`#f6f8fa`) и `bg_tertiary` (`#f0f2f5`) — иначе сломается визуальная иерархия карточек/панелей. Если новый `bg_primary` окажется темнее или равен `bg_secondary`, сдвинь `bg_secondary`/`bg_tertiary` на тон ниже, чтобы иерархия сохранилась.
2. Заодно провалидируй контраст текста на новом фоне (`text_primary` `#1f2328`, `text_secondary` `#57606a`) — должен остаться читаемым (контраст ≥ 4.5:1 для основного текста, ориентир — WCAG AA).
3. `border_subtle`/`border_default` можно чуть смягчить под новый фон, если на глаз будет резать (не обязательно).
4. Тему менять только в `modern_light.py` — `theme_manager.py` и `modern_styles.py` трогать не нужно, они уже читают токены из словаря автоматически и применяются ко всему приложению через `build_modern_qss()`.
5. **Не трогай** `modern_dark.py` — тёмная тема не входит в задачу.

### Критерии приёмки
- Переключить тему на светлую (через UI) — фон не «слепит» чистым белым, при этом:
  - панели/карточки визуально отличимы от основного фона (иерархия `bg_primary` < `bg_secondary` < `bg_tertiary` по «затемнённости» сохранена);
  - весь текст читаем (не сливается с фоном);
  - ничего не сломано в тёмной теме.

## Задача 4. Настройка «Использовать CUDA» — для моделей нейросети и для обработки

### Причина
Сейчас в проекте нет способа явно отключить CUDA:
- `configs/sign_models.py` — `_LazyModel._load()` вызывает `YOLO(self._path_fn())` без параметра `device`, Ultralytics сам решает, использовать GPU или CPU (`model_side_detect`, `rube_modal`, `model_dict`, `sub_models`, `model_lane_detect`, `model_lane_segment` — все модели проекта идут через этот класс).
- `core/detector.py::_get_ocr()` (строка ~51) — EasyOCR инициализируется жёстко с `gpu=False`:
  ```python
  _ocr_reader = easyocr.Reader(["be"], gpu=False)
  ```
  То есть OCR **всегда** идёт на CPU, даже если CUDA есть и пользователь бы хотел её использовать.
- Кнопка диагностики «🔍 Проверить GPU» уже есть в `settings_page.py` (строка 547, метод `_check_gpu` строка 858) — **её нужно оставить как есть**, это просто индикатор доступности CUDA, не переключатель.
- Есть готовый паттерн добавления булевой настройки — посмотри на `ocr_use_process_pool` / `verbose_log` / `save_error_frames` в `settings_page.py` (компонент `ToggleButton`, строка 76) и `settings.py` (dataclass `AppSettings`).

### Что сделать
1. **`configs/settings.py`** — добавить в `AppSettings` новое поле, например:
   ```python
   # ── Вычисления (CPU/GPU) ────────────────────────────────────
   use_cuda: bool = True   # Использовать CUDA для моделей и OCR, если доступна
   ```
   (само поле подхватится `load()`/`save()`/`reset_to_defaults()`/`to_dict()`/`from_dict()` автоматически — они работают через `__dataclass_fields__`, руками ничего в этих методах менять не нужно).

2. **`configs/sign_models.py`** — при загрузке моделей учитывать настройку и реальную доступность CUDA:
   ```python
   def _resolve_device() -> str:
       try:
           from configs.settings import get_app_settings
           import torch
           settings = get_app_settings()
           if settings.use_cuda and torch.cuda.is_available():
               return "cuda:0"
       except Exception:
           pass
       return "cpu"
   ```
   Передавать `device=_resolve_device()` в `YOLO(...)` при загрузке (`self._model = YOLO(self._path_fn())`, дальше `.to(device)` либо передавать `device=` в сам вызов `.predict(...)`/`__call__` — уточни, какой вариант не ломает текущие вызовы в `detector.py` (строки ~325, 348, 427, 542, 683), т.к. там `.predict(...)` вызывается без `device`).
   Важно: `_resolve_device()` не должен пересчитываться на каждый вызов модели (кэшируй на уровне `_LazyModel` при первой загрузке, аналогично `self._model`), чтобы не терять производительность.

3. **`core/detector.py::_get_ocr()`** — убрать хардкод `gpu=False`, брать из настроек:
   ```python
   def _get_ocr():
       global _ocr_reader
       if _ocr_reader is None:
           from configs.settings import get_app_settings
           import torch
           settings = get_app_settings()
           use_gpu = settings.use_cuda and torch.cuda.is_available()
           import easyocr
           _ocr_reader = easyocr.Reader(["be"], gpu=use_gpu)
       return _ocr_reader
   ```
   (сохрани существующий try/except и логирование, если они там есть — не убирай обработку ошибок инициализации).

4. **`ui/widgets/settings_page.py`** — добавить переключатель рядом с блоком «Проверка CUDA/GPU» (строки ~544-571, группа `diag_group`), по аналогии с уже существующими тогглами:
   ```python
   self._cuda_toggle = ToggleButton(self._settings.use_cuda)
   diag_group.add_row(
       "Использовать CUDA",
       "Включить GPU-ускорение для моделей YOLO и распознавания текста (OCR), если доступна",
       self._cuda_toggle,
   )
   ```
   И добавить сохранение/восстановление значения там же, где остальные тогглы:
   - в методе сохранения настроек (см. строки ~676-682) добавить `self._settings.use_cuda = self._cuda_toggle.is_checked()`;
   - в методе сброса к дефолтам (~774-781) добавить `self._cuda_toggle.set_checked(defaults.use_cuda)`;
   - в методе загрузки из словаря/импорта настроек (~1001-1016) добавить `self._cuda_toggle.set_checked(settings_dict.get("use_cuda", True))`.
5. Проверь `configs/config.py::PROCESSING_MODE` (режим `"gpu_batch"`) — если этот режим где-то реализован и использует CUDA напрямую (детектор-пулы `detector_pool.py`/`detector_process_pool.py`), тоже прокинь туда `use_cuda`, чтобы настройка была консистентной для всех путей обработки, а не только для одиночных вызовов моделей.

### Критерии приёмки
- В настройках появляется переключатель «Использовать CUDA» рядом с кнопкой «Проверить GPU» (её функциональность не менять).
- При выключенном переключателе — YOLO-модели и EasyOCR реально работают на CPU (проверить через `nvidia-smi`/загрузку GPU во время обработки — не должна расти) даже если CUDA физически доступна.
- При включённом переключателе и доступной CUDA — модели и OCR используют GPU.
- Если CUDA физически недоступна, переключатель включённым быть может (это просто желание пользователя), но приложение не падает — просто фактически работает на CPU.
- Настройка сохраняется между перезапусками приложения (как остальные настройки).

## Задача 5. Очистка неиспользуемых зависимостей (чтобы не тащить лишнее в exe)

### Причина
Сверка `requirements.txt` с реальными импортами по всему коду (`grep` по всем `.py`) показала пакеты с **нулевым использованием**:

| Пакет | Импортов в коде | Комментарий |
|---|---|---|
| `tensorflow` | 0 | В `sign_models.py` явно написано, что Keras-модели уже удалены |
| `keras` | 0 | Там же |
| `scikit-learn` | 0 | В `sign_models.py` упоминается как уже удалённая зависимость |
| `scikit-image` | 0 | Не используется нигде |
| `matplotlib` | 0 в коде, но `main.py:37` содержит `logging.getLogger('matplotlib').setLevel(...)` — это НЕ импорт пакета, просто заглушка для будущих логов, реального импорта matplotlib нет |
| `pandas` | 0 | В `turn.py` есть комментарий, что pandas/csv оттуда уже убраны |
| `pygeoguz` | 0 | Не используется нигде |

Пакеты, которые **нужно оставить** (реально используются):
- `joblib` — используется в `processing_controller.py` (сохранение/загрузка чекпоинтов, `joblib.dump`/`joblib.load`).
- `flask-socketio`, `python-socketio`, `python-engineio` — используются транзитивно через `map_server.py` (`flask_socketio`).
- `pyproj` — `converter.py`, `diagnose_coordinates.py`.
- `geopy` — `coordinate_calculation.py`, `sign_handler.py`.
- `geojson` — `error_editor_page.py`, `final_handler.py`, `map_server.py`.
- `gpxpy` — `dashboard_page.py`, `gpx_handler.py`, `map_server.py`.
- `Pillow` (PIL) — `map_server.py`.
- Остальные (`PyQt6`, `PyQt6-WebEngine`, `opencv-python`, `ultralytics`, `easyocr`, `numpy`, `requests`, `flask`, `flask-cors`) — используются широко, не трогать.

### Что сделать
1. Убрать из `requirements.txt`: `tensorflow`, `keras`, `scikit-learn`, `scikit-image`, `matplotlib`, `pandas`, `pygeoguz`.
2. Перед удалением — на всякий случай ещё раз прогнать поиск по **всему** репозиторию (не только по файлам из этого дампа — в реальном репо могут быть подпапки `core/`, `configs/`, `ui/`, `server/`, `utils/`, которые здесь показаны плоским списком), например:
   ```bash
   grep -rniE "tensorflow|keras|sklearn|scikit|skimage|matplotlib|pandas|pygeoguz" --include="*.py" .
   ```
   и убедиться, что совпадения — только в комментариях/docstring'ах (как найдено выше), а не в реальном `import`.
3. Проверить, не тянет ли `ultralytics` `matplotlib` как свою обязательную транзитивную зависимость (`pip show ultralytics` → `Requires:`). Если тянет — удаление из `requirements.txt` не уменьшит размер exe само по себе, тогда для PyInstaller нужно явно исключать модуль через `excludes=[...]` в `.spec`-файле (см. следующий пункт), а не просто убирать из `requirements.txt`.
4. Найти актуальный PyInstaller `.spec`-файл сборки exe (в переданном дампе файлов его нет — вероятно, он лежит в другом месте репозитория или генерируется отдельно). В нём:
   - убедиться, что нет ручных `hiddenimports` для `tensorflow`/`keras`/`sklearn`/`matplotlib`/`pandas`;
   - добавить эти пакеты в `excludes` секции `Analysis(...)`, если PyInstaller всё равно их подхватывает как транзитивные зависимости других библиотек.
5. После правок — пересобрать окружение с нуля (`pip install -r requirements.txt` в чистый venv) и прогнать приложение целиком (обработка видео, карта, редактор, настройки) — убедиться, что ничего не сломалось из-за удалённых пакетов.
6. Пересобрать exe и сравнить размер до/после (для отчёта — не обязательное требование, но полезно зафиксировать выигрыш).

### Критерии приёмки
- Приложение запускается и работает во всех разделах (обработка, карта, редактор ошибок, настройки) в окружении без `tensorflow`/`keras`/`scikit-learn`/`scikit-image`/`pandas`/`pygeoguz`.
- Итоговый `.exe` не содержит эти пакеты (проверить, например, содержимое временной распаковки PyInstaller `--onefile`, или просто заметное уменьшение размера exe/папки сборки).
- `requirements.txt` содержит только реально используемые зависимости.
