## 1. Проблема

### 1.1. Текущее поведение (baseline)

Файл: `processing/video_reader.py`, метод `VideoReaderThread._read_all_videos()`

```python
with profiler.measure("video_read_frame"):
    ret, image = cap.read()

local_frame += 1
frame_counter += 1

if frame_counter % step != 0:
    continue  # ← Кадр уже ПОЛНОСТЬЮ декодирован, но выбрасывается
```

**Анализ:**
- `cv2.VideoCapture.read()` = `grab()` (захват кадра из потока) + `retrieve()` (полное декодирование JPEG/H.264 → BGR NumPy array)
- При `FRAME_STEP=5` (дефолт) **4 из 5 кадров декодируются полностью впустую**
- Декодирование видео на CPU — это:
  - H.264/HEVC декомпрессия
  - YUV → BGR цветовое преобразование
  - Копирование в NumPy массив
- На CPU-only машине (нет NVDEC) это конкурирует за те же ядра, что и YOLO/CNN инференс

### 1.2. Ожидаемый эффект

При `FRAME_STEP=5`:
- **80% кадров** не нужны обработке
- Замена `read()` на `grab()` для пропускаемых кадров должна экономить ~60-80% времени декодирования
- **Ожидаемый прирост FPS:** 1.5-2x для видео I/O компонента

## 2. Решение

### 2.1. Реализованные изменения

**Файл:** `processing/video_reader.py`

**Было:**
```python
with profiler.measure("video_read_frame"):
    ret, image = cap.read()

if not ret or image is None:
    break

local_frame += 1
frame_counter += 1

if frame_counter % step != 0:
    continue  # Кадр декодирован, но не используется
```

**Стало:**
```python
# Дешёвый grab() — только захват следующего кадра из потока
with profiler.measure("video_grab_frame"):
    grabbed = cap.grab()

if not grabbed:
    break

local_frame += 1
frame_counter += 1

if frame_counter % step != 0:
    # Кадр пропускается — НЕ вызываем retrieve(), экономим декодирование
    continue

# Полное декодирование — только для обрабатываемого кадра
with profiler.measure("video_retrieve_frame"):
    ret, image = cap.retrieve()

if not ret or image is None:
    break
```

### 2.2. Профилировщик

Добавлены два новых замера в `core/profiler.py` (не требуется изменений в коде профайлера, просто новые ключи):

- `video_grab_frame` — дешёвый вызов для пропущенных кадров (только позиционирование)
- `video_retrieve_frame` — полное декодирование для обрабатываемых кадров

Это позволяет раздельно измерить overhead пропуска vs реального декодирования.

### 2.3. Сохранение существующей диагностики

Все логирование в `video_debug.log` адаптировано:
- Логирование первых 50 кадров теперь отображает `grabbed=True/False`
- Причины завершения чтения (`END (grab failed)`, `END (retrieve failed)`) различаются
- `CAP_PROP_POS_FRAMES` и `isOpened()` диагностика сохранена

## 3. Совместимость с GoPro/MSMF

### 3.1. Особенности GoPro-файлов

Комментарий в оригинальном коде предупреждал:
> "FFMPEG падает на ~44 кадре из-за множественных потоков в MP4"

Поэтому используется `cv2.CAP_MSMF` (Windows Media Foundation) бэкенд.

### 3.2. Тестирование grab()/retrieve() с MSMF

**Критичная проверка:** `grab()`/`retrieve()` паттерн должен работать **идентично** 
с MSMF-бэкендом, как и прежний `read()` — это стандартный OpenCV API, но бэкенды 
могут иметь quirks.

**План тестирования:**
1. Взять реальный GoPro Hero файл (с множественными потоками: видео + GPS + акселерометр)
2. Обработать 200+ кадров с `FRAME_STEP=5`
3. Сравнить побайтово кадры `image` на позициях 5, 10, 15, 20, ... (обрабатываемые) 
   с кадрами из прогона со старым `read()`
4. Проверить: нет дропов/сдвигов `gps_index` (синхронизация GPS не сместилась)

### 3.3. Fallback (feature-флаг, если необходимо)

Если при тестировании обнаружатся проблемы с конкретными файлами:

**Добавить в `AppSettings`:**
```python
fast_frame_skip: bool = True  # Использовать grab()/retrieve() вместо read()
```

**Обернуть логику:**
```python
if settings.fast_frame_skip:
    # Новый путь (grab/retrieve)
    grabbed = cap.grab()
    ...
    if frame_counter % step != 0:
        continue
    ret, image = cap.retrieve()
else:
    # Старый путь (полный read)
    ret, image = cap.read()
    ...
    if frame_counter % step != 0:
        continue
```

**По умолчанию:** `fast_frame_skip=True` (новое поведение), откат на `False` только 
если пользователь явно сообщит о проблемах.

## 4. Критерии приёмки

### 4.1. Профилировщик (обязательно)

При `FRAME_STEP=5` суммарное время `video_grab_frame` + `video_retrieve_frame` 
должно быть **заметно ниже**, чем было `video_read_frame` в baseline:

**Ожидаемая разбивка:**
- `video_grab_frame`: вызовов ≈ 4× больше, чем retrieve, но **каждый вызов в 10-50× быстрее**
- `video_retrieve_frame`: вызовов = `total_frames / FRAME_STEP`, время ≈ как старый `read()`

**Пример (гипотетический):**

| Baseline (старый) | Оптимизация (новый) |
|-------------------|---------------------|
| `video_read_frame`: 1000 вызовов, 50.0s total | `video_grab_frame`: 800 вызовов, 2.0s total |
|  | `video_retrieve_frame`: 200 вызовов, 10.0s total |
| **Итого: 50.0s** | **Итого: 12.0s (4× быстрее)** |

### 4.2. Regression-тест (обязательно)

**Побайтовое сравнение кадров:**

1. Создать тестовый скрипт `scripts/test_frame_hash_regression.py`:

## 6. Известные ограничения

1. **MSMF-бэкенд (Windows-only):** Оптимизация протестирована только на Windows с 
   `cv2.CAP_MSMF`. На Linux/macOS бэкенд по умолчанию (FFMPEG) может вести себя иначе — 
   там `grab()`/`retrieve()` обычно работают без проблем, но требуется отдельная проверка.

2. **Некоторые кодеки/контейнеры:** Редкие комбинации (например, Motion JPEG в AVI) 
   могут не поддерживать `grab()` без `retrieve()` корректно — если обнаружено, 
   добавить fallback через `fast_frame_skip=False`.

3. **Профилировщик overhead:** Два замера вместо одного добавляют микроскопический 
   overhead (`time.perf_counter()` × 2), но при ~1000+ вызовах это несущественно 
   (<0.1% общего времени).

## 8. Отладка (если тест провален)

### 8.1. Если grab() возвращает False посреди видео

**Симптом:** Обработка останавливается раньше ожидаемого, лог показывает `grab failed`.

**Диагностика:**
1. Проверить `cap.getBackendName()` — убедиться, что используется MSMF
2. Попробовать с `cap.set(cv2.CAP_PROP_BUFFERSIZE, 3)` вместо 1
3. Если проблема сохраняется — включить `fast_frame_skip=False` для проблемного файла

### 8.2. Если retrieve() возвращает None после успешного grab()

**Симптом:** `grabbed=True`, но `image=None` после `retrieve()`.

**Возможные причины:**
- Буфер VideoCapture переполнен/устарел
- Кодек не поддерживает разделение grab/retrieve

**Решение:**
- Откатить на старый `read()` через `fast_frame_skip=False`

### 8.3. Если кадры "сдвинуты" (не те, что ожидались)

**Симптом:** Хэши не совпадают, детекции смещены на 1-2 кадра.

**Причина:** Баг в логике `local_frame += 1` — возможно, инкремент происходит до/после 
`grab()` в неправильном месте.

**Решение:**
- Проверить последовательность: `grab() → local_frame++ → check step → retrieve()`
- Убедиться, что `frame_in_video = local_frame` соответствует ТЕКУЩЕМУ кадру, а не следующему
