# Параллельные детекторы (Detector Pool)

## Обзор

**DetectorPool** — пул из 2-4 параллельных детекторов для максимального использования многоядерных CPU. Даёт **2-3x ускорение** на системах с 4+ ядрами.

## Преимущества

✅ **Ускорение 2-3x** на многоядерных системах  
✅ **Автоопределение** оптимального количества воркеров  
✅ **Thread-safe** — корректная работа SignHandler  
✅ **Масштабируемость** — больше ядер = больше скорость  
✅ **Можно отключить** — fallback на одиночный детектор  

## Как это работает

### Архитектура

```
VideoReaderThread
    ↓ frame_queue (общая)
    ↓
DetectorPool
├─ Worker #1 ──┐
├─ Worker #2 ──┼─→ детектируют параллельно
└─ Worker #3 ──┘
    ↓
AggregatorThread
    ↓ обрабатывает результаты через SignHandler (thread-safe)
    ↓
result_queue → FinalHandler → GeoJSON
```

### Принцип работы

1. **VideoReaderThread** читает кадры → `frame_queue`
2. **DetectorWorker'ы** забирают кадры из общей очереди
3. Каждый воркер независимо:
   - Детектирует знаки (YOLO + CNN)
   - Отправляет результат в `result_queue`
4. **AggregatorThread** обрабатывает результаты:
   - Конвертирует в DetectedSign
   - Вызывает SignHandler (через lock)
   - Финализирует знаки

### Thread-safety

```python
# Shared SignHandler с мьютексом
sign_handler_lock = threading.Lock()

# В AggregatorThread
with sign_handler_lock:
    sign_handler.check_the_data_to_add(detections, turn)
```

**Критические секции защищены** — гарантия корректности результатов.

## Алгоритм

### Автоопределение воркеров

```python
def detect_optimal_workers():
    cpu_count = os.cpu_count()
    
    # Половина ядер, но не меньше 2 и не больше 4
    optimal = max(2, min(4, cpu_count // 2))
    
    # Можно переопределить через env
    if os.getenv('DETECTOR_WORKERS'):
        optimal = int(os.getenv('DETECTOR_WORKERS'))
    
    return optimal
```

**Примеры:**
- 2 ядра → 1 воркер (используем одиночный детектор)
- 4 ядра → 2 воркера ✓
- 6 ядер → 3 воркера ✓
- 8+ ядер → 4 воркера ✓

**Почему не все ядра?**
- Нужны ресурсы для VideoReaderThread
- Нужны ресурсы для AggregatorThread
- Нужны ресурсы для OS и UI

### Work stealing

Воркеры забирают кадры из **общей очереди** (не распределяются заранее):

```python
while not stop:
    frame = frame_queue.get(timeout=0.2)  # Берёт первый доступный
    result = detect(frame)
    result_queue.put(result)
```

**Преимущества:**
- ✅ Автоматическая балансировка нагрузки
- ✅ Быстрые воркеры не ждут медленных
- ✅ Эффективное использование всех ядер

## Когда использовать

### ✅ Рекомендуется

- **4+ ядра CPU**
- **8+ ГБ RAM** (лучше 16 ГБ)
- **Долгая обработка** (десятки видео)
- **Приоритет скорость** > экономия ресурсов

### ❌ НЕ рекомендуется

- **2 ядра** (нет прироста)
- **Мало RAM** (< 6 ГБ, риск OOM)
- **Короткие видео** (overhead загрузки моделей)
- **Laptop на батарее** (быстрый разряд)

### Автоматический выбор

Система **автоматически отключает пул** если CPU < 4 ядер:

```python
if cpu_count < 4:
    USE_DETECTOR_POOL = False  # Fallback на одиночный
```

## Ограничения

### 1. Память

Каждый воркер загружает **полный набор моделей**:
- YOLO: ~500 МБ
- CNN модели: ~1.5 ГБ
- Итого на воркера: **~2 ГБ**

**Решение:** Ограничить NUM_WORKERS на системах с малой RAM.

### 2. GIL (Global Interpreter Lock)

Python GIL ограничивает истинный параллелизм, но:
- ✅ Детекция (YOLO/CNN) = **C++ код** (вне GIL)
- ❌ SignHandler = **Python код** (под GIL + lock)

**Эффект:** 2.1x вместо идеальных 2x (95% эффективность).

### 3. Порядок кадров

Кадры могут обрабатываться **в произвольном порядке**:

```
Worker 0: кадр 1, 3, 5
Worker 1: кадр 2, 4, 6
```

**AggregatorThread НЕ гарантирует порядок** результатов!

**Решение:** SignHandler использует `frame_number` для связи знаков, порядок не важен.

## Troubleshooting

### "Воркеры не запускаются"

**Причина:** Недостаточно RAM для загрузки моделей

**Решение:**
1. Закройте другие приложения
2. Уменьшите NUM_WORKERS до 2
3. Отключите пул (используйте одиночный детектор)

### "FPS не увеличивается"

**Причина:** Bottleneck не в детекции (например, VideoReader)

**Решение:**
1. Проверьте загрузку CPU (должна быть 50-70%)
2. Проверьте скорость чтения видео (SSD vs HDD)
3. Увеличьте FRAME_QUEUE_SIZE до 200

### "Race condition / неверные результаты"

**Причина:** Конкуренция за SignHandler

**Решение:** Убедитесь что lock используется корректно (уже реализовано).

### "Память растёт бесконечно"

**Причина:** Утечка в воркерах или очередях

**Решение:**
1. Проверьте RESULT_QUEUE_SIZE (должна быть ограничена)
2. Проверьте CNN кэш (должен быть ограничен)
3. Отключите пул для диагностики
