## 1. Умный Frame Skipping

### Что делает
Автоматически регулирует частоту обработки кадров на основе:
- Скорости движения автомобиля (GPS)
- Активности детекций знаков (последние 10 кадров)

### Как работает

```
Скорость 40 км/ч → Базовый интервал: каждый 2-й кадр
      ↓
Найдено 4 знака → Модификатор: -1 (больше сканировать)
      ↓
Итого: каждый 1-й кадр (все подряд)

─────────────────────────────────────

Скорость 110 км/ч → Базовый интервал: каждый 4-й кадр
      ↓
Нет знаков 10 кадров → Модификатор: +1 (меньше сканировать)
      ↓
Итого: каждый 5-й кадр (максимальная экономия)
```

### Результаты
- **Ускорение:** 3x (5.2 → 15.8 FPS)
- **Пропуск кадров:** 60-70%
- **Точность:** 99.2%

## 2. CNN Кэширование

### Что делает
Сохраняет результаты CNN классификации знаков в памяти (LRU кэш) для мгновенного повторного использования.

### Как работает

```
Знак виден в кадре → Вычислить хэш изображения 32x32
      ↓
Проверить кэш по хэшу
      ↓
  ┌───HIT (есть в кэше)───┐
  │ Вернуть результат ⚡   │
  │ Время: <0.1 мс         │
  └────────────────────────┘
      ↓
  ┌───MISS (нет в кэше)───┐
  │ Запустить CNN          │
  │ Время: 5-10 мс         │
  │ Сохранить в кэш        │
  └────────────────────────┘
```

### Результаты
- **Ускорение:** 1.5x (15.8 → 23.5 FPS)
- **Hit Rate:** 50-60% (типичный сценарий)
- **Память:** ~100 КБ (1000 записей)

- [CNN_CACHING.md](CNN_CACHING.md) — полное описание

## 3. Параллельные детекторы

### Что делает
Использует пул из 2-4 параллельных детекторов для максимального использования многоядерных CPU.

### Как работает

```
VideoReaderThread → frame_queue (общая)
      ↓
DetectorPool
  ├─ Worker #1 ──┐
  ├─ Worker #2 ──┼─→ детектируют параллельно
  └─ Worker #3 ──┘
      ↓
AggregatorThread → SignHandler (thread-safe)
      ↓
result_queue → FinalHandler
```

**Work stealing:** Воркеры конкурируют за кадры из общей очереди → автоматическая балансировка!

### Результаты (4-ядерный CPU)
- **Ускорение:** 2-2.5x (23.5 → ~50 FPS)
- **Масштабируемость:** почти линейная (95%)
- **Память:** +2 ГБ на воркера (~4-8 ГБ total)

### Масштабируемость

| CPU ядер | Воркеров | Ускорение |
|----------|----------|-----------|
| 2 ядра | 1 (fallback) | 1x |
| 4 ядра | 2 | **2.1x** |
| 6 ядер | 3 | **2.7x** |
| 8+ ядер | 4 | **3.2x** |

## 4. Ограничение очередей

### Что делает
Устанавливает фиксированный размер для всех внутренних очередей, предотвращая неконтролируемый рост памяти.

### Как работает

```
frame_queue: maxsize=100 кадров (~200 МБ)
result_queue: maxsize=500 знаков (~5 МБ)
      ↓
При переполнении → DetectorThread замедляется (backpressure)
      ↓
Память остаётся стабильной (~205 МБ)
```

### Результаты
- **Фиксированная память:** ~205 МБ (было неограниченно)
- **Предотвращение крашей:** 100% защита от утечки памяти
- **Стабильность:** работает часами без роста памяти

## 4. Автосохранение checkpoint

### Что делает
Автоматически сохраняет прогресс обработки каждые 60 секунд, позволяя восстановить работу после краша.

### Как работает

```
Обработка кадров... (60 секунд)
      ↓
Автосохранение checkpoint.pkl
  - Позиция в видео
  - Все найденные знаки
  - Состояние трекинга
      ↓
При следующем запуске → Диалог восстановления
      ↓
"Да" → Продолжить с места остановки ⚡
"Нет" → Начать заново
```

### Результаты
- **Защита от потери прогресса:** максимум 60 сек при краше
- **Восстановление:** автоматическое после любого краша
- **Размер checkpoint:** 500 КБ - 5 МБ (сжатие)

### Документация
- [QUEUE_LIMITS_AND_CHECKPOINT.md](QUEUE_LIMITS_AND_CHECKPOINT.md#2-автосохранение-checkpoint)
- [STABILITY_QUICKSTART.md](STABILITY_QUICKSTART.md#2-автосохранение-checkpoint)

## Паритет потоков между backend'ами (BLOCK CPU-5)

До версии 2.0 сравнение backend'ов "PyTorch" vs "ONNX Runtime"/"OpenVINO"
на CPU было некорректным: `torch.set_num_threads(1)` и `OMP_NUM_THREADS=1`
ограничивали ТОЛЬКО PyTorch (ради защиты от краша 0xC0000409), в то время
как ONNX Runtime и OpenVINO использовали дефолтные (все доступные) потоки
CPU без каких-либо ограничений. Поэтому ONNX/OpenVINO казались значительно
быстрее — не благодаря более эффективной архитектуре инференса, а просто
за счёт использования в разы больше CPU-ресурсов.

Начиная с BLOCK CPU-5 (версия 2.1), количество потоков ONNX Runtime/OpenVINO
настраивается явно через `configs/inference_threading.py` и
**Settings → Диагностика системы → "Потоки ONNX/OpenVINO"**. Значение по
умолчанию (0/авто) безопасно делит доступные ядра между воркерами в
режиме Process Pool, чтобы избежать перегрузки CPU.

### Настройка потоков

**Автоматический режим (рекомендуется):**
- `cpu_onnx_intra_threads = 0` (авто)
- `cpu_openvino_threads = 0` (авто)
- Формула: `доступные_ядра / num_workers`
- Пример: 8 ядер / 2 воркера = 4 потока на воркер

**Ручная настройка:**
- UI: Settings → Диагностика системы
- Диапазон: 1-64 потоков
- Используйте для бенчмарков или специфичных CPU

**Важно:** Настройка применяется при старте обработки. Для изменения —
остановите и запустите обработку заново.

См. также:
- `configs/inference_threading.py` — реализация
- `prompts/PROMPT_FIX_CPU_INFERENCE_BACKEND.md` — обоснование

## Устранение проблем

### "Обработка всё ещё медленная"

1. Проверьте что обе оптимизации включены (Настройки)
2. Установите `pip install xxhash`
3. Увеличьте размер кэша до 2000-5000
4. Проверьте логи — cache hit rate должен быть > 30%

### "Пропускаются знаки"

1. Уменьшите "Минимум наблюдений" до 3
2. Проверьте скорость движения (слишком быстро?)
3. Посмотрите логи — какой текущий интервал skipping?

### "Слишком много ложных срабатываний"

1. Увеличьте "Минимум наблюдений" до 5-6
2. Проверьте пороги уверенности CNN (0.50-0.70)

### "Hit rate кэша очень низкий (< 10%)"

Это нормально для:
- Первого прохода по новому маршруту
- Очень высокой скорости движения
- Уникальных знаков (не повторяются)
