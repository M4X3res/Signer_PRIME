## Детали исправлений

### A.1 БАГ №1: Потеря знаков при переполнении result_queue

**Причина:**  
В `processing/detector_thread.py` при переполнении очереди (`queue.Full`) цикл прерывался через `break`, но `self._sign_handler.result_signs.clear()` выполнялся безусловно, уничтожая все знаки (как отправленные, так и неотправленные).

**Исправление:**
- Основной цикл `_process_loop()`: знаки, не поместившиеся в очередь, откладываются в `remaining` и остаются в `result_signs` для повторной отправки на следующей итерации.
- Блок `finally` при завершении потока: используется блокирующий `put(timeout=2.0)` для каждого знака отдельно, без `break`, с явным логированием потерь.

**Изменённые файлы:**
- `processing/detector_thread.py` (строки 337-365, 187-207)

**Тест:**
- `tests/test_result_queue_no_loss.py` ✅ PASS

**Результат:**  
Ни один знак больше не теряется молча. Если очередь переполнена временно — знаки ждут освобождения места. Если переполнена критично (финальная отправка) — потери явно логируются с полным списком типов.

### A.2 БАГ №2: Восстановление из checkpoint не работало

**Причина:**  
`ProcessingController.start()` безусловно вызывал `_reset_config()`, который обнулял все индексы (`INDEX_OF_FRAME`, `INDEX_OF_VIDEO`, и т.д.), даже если они были только что восстановлены из checkpoint через `load_checkpoint()`. Данные знаков из checkpoint не передавались в `DetectorThread` вовсе.

**Исправление (7 шагов):**

1. Добавлены поля в `ProcessingController.__init__`:
   ```python
   self._resume_from_checkpoint: bool = False
   self._checkpoint_data: Optional[dict] = None
   ```

2. `load_checkpoint()` выставляет флаг `_resume_from_checkpoint = True` при успехе

3. `_reset_config()` проверяет флаг и **не сбрасывает** индексы если `_resume_from_checkpoint == True`

4. В конструктор `DetectorThread` добавлен параметр `checkpoint_signs: Optional[dict]`

5. В `DetectorThread.run()` знаки восстанавливаются в `SignHandler`:
   ```python
   self._sign_handler.result_signs = restored_result
   self._sign_handler.signs = restored_active
   self._sign_handler.turns = restored_turns
   ```

6. `_start_detector()` передаёт данные и **одноразово сбрасывает** флаг после использования

7. `_start_process_pool()` логирует предупреждение о неподдержке checkpoint (только индексы восстанавливаются, знаки — нет)

**Изменённые файлы:**
- `processing/processing_controller.py` (строки 67-68, 205-235, 268-291, 293-314, 446-448, 462-464, 470-472)
- `processing/detector_thread.py` (строки 47-54, 142-159)

**Тест:**
- `tests/test_checkpoint_resume.py` ✅ PASS (5 assertions)

**Результат:**  
Восстановление из checkpoint полностью функционально. При повторном запуске после краша пользователь действительно продолжает с места остановки (позиция в видео + все найденные знаки сохранены).

### A.3 БАГ №3: Одна повреждённая запись обнуляла весь пакет знаков

**Причина:**  
В `core/final_handler.py` метод `_batch_snap_signs()` строил список координат так:
```python
points = [(sign.car_y[-1], sign.car_x[-1]) for sign in signs]
```
Если хотя бы у одного знака пустые `car_x`/`car_y`, бросался `IndexError`, перехватываемый верхним `try/except` в `save_result()`, что приводило к `features = []` — **все** прямые знаки этого прогона терялись.

**Исправление:**

1. Добавлен метод валидации `_validate_signs_for_processing()`:
   - Фильтрует знаки без валидных `car_x`/`car_y`
   - Логирует список пропущенных (типы знаков)
   - Возвращает только валидные

2. `_process_straight_signs()` вызывает валидацию в начале, до `_batch_snap_signs()`

3. Заменён `logger.error(f"... {e}") + traceback.print_exc()` на `logger.exception(...)` для автоматического трейсбека

4. Добавлена итоговая сводка в конце `save_result()`:
   - Логирует соотношение входных/записанных знаков
   - Выдаёт ERROR если в файл попало < 50% знаков

**Изменённые файлы:**
- `core/final_handler.py` (строки 135-156, 94-101, 127-147)

**Тест:**
- `tests/test_final_handler_resilience.py` ✅ PASS (4 assertions)

**Результат:**  
Битый знак молча отфильтровывается с предупреждением в логе, все остальные знаки обрабатываются нормально. Критичные расхождения видны в логе сразу.

### A.4 БАГ №4: UI показывал недостоверное число сохранённых знаков

**Причина:**  
`SaveThread.run()` в `ui/main_window.py` эмитировал `len(self.signs)` (количество входных `TrackedSign`), а не реальное количество `Feature`, записанных в GeoJSON после дедупликации и возможных потерь. `FinalHandler.save_result()` ничего не возвращал (`-> None`).

**Исправление:**

1. `FinalHandler.save_result()` теперь возвращает `int` — количество записанных features:
   ```python
   return len(features)
   ```

2. `SaveThread.run()` использует возвращённое значение:
   ```python
   saved_count = handler.save_result(...)
   self.finished_ok.emit(saved_count)
   ```

3. `_save_results()` сохраняет входное количество в `self._last_input_sign_count`

4. `_on_save_finished()` сравнивает входное и сохранённое:
   - Если `saved < input * 0.5` → статус WARNING + лог с призывом проверить `roadscan.log`
   - Иначе → статус SUCCESS

**Изменённые файлы:**
- `core/final_handler.py` (строка 67, 148)
- `ui/main_window.py` (строки 434-436, 456-460, 496-516)

**Тест:**
- `tests/test_final_handler_return_value.py` ✅ PASS

**Результат:**  
Пользователь видит реальное количество знаков в файле. Если есть значительные потери — явное предупреждение в UI и указание на лог.

## A.5 Сквозное логирование

Добавлено явное логирование на каждой границе передачи данных:

| Точка | Что логируется | Уровень |
|-------|----------------|---------|
| `DetectorThread._process_loop()` | `len(result_signs)` перед put | DEBUG |
| `DetectorThread._process_loop()` | Количество знаков, ожидающих повторной отправки | WARNING |
| `DetectorThread.finally` | Список потерянных типов при критичном переполнении | ERROR |
| `ProcessingController.get_result_signs()` | Количество знаков из очереди | INFO (было DEBUG) |
| `FinalHandler.save_result()` | Входное количество (прямые + повороты) | INFO |
| `FinalHandler.save_result()` | Финальное количество features в файле | INFO |
| `FinalHandler.save_result()` | Итоговая сводка с соотношением | INFO/ERROR |

**Результат:**  
По `grep` в `roadscan.log` можно за минуту проследить судьбу каждого знака от детекции до файла.
